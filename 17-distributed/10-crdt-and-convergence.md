# 10 · CRDT 与自动收敛：不靠共识的最终一致

## 学习目标

- 能解释 CRDT 买到的东西：副本各自接受写、任意顺序合并都收敛——把 02 章"最终一致"里最贵的冲突裁决环节变成数学保证

- 能讲清 Redis CRDB 多活与 Redis 主从复制在分区期间的行为差异，以及 Cassandra LWW 在时钟漂移下静默丢写的原因与对策

## 1. 为什么需要 CRDT：把"冲突裁决"变成"自动合并"

### 1.1 已学两条路各自的痛

02 章给过最终一致的合同：停写后副本收敛。但合同里藏着一句话——**分歧必须能被裁掉**。已学系统的两种裁法都有代价：

- **单主复制**（Redis/MySQL 主从）：只允许一个写入口，分歧靠"以主为准"消除。分区时必须选边（哨兵 majority 授权，`../11-middleware/redis/02-persistence-and-ha.md` §6），旧主未复制的写在愈合后直接丢失（同章 §5 的 RPO 语义）。
- **无主多写**（Dynamo 系）：N 个副本都接受写，靠向量钟**检测**并发（`./01-failure-models-and-time.md` §3.3），检测出来之后呢？要么交给应用层写合并逻辑（购物车可以合并，账户不行），要么退化为 LWW 丢一边。

03 章的共识协议是第三条路：过半提交，彻底没有分歧。代价也背过——每次写过半 fsync、少数派分区期间停写、单 leader 是吞吐与延迟的串行点（`./03-consensus-and-replication.md` §2/§4）。

### 1.2 CRDT 的承诺

CRDT（Conflict-free Replicated Data Type，无冲突复制数据类型）做的事：**把数据结构本身设计成"无论谁先谁后合并，结果都一样"**。于是：

```
[图] 分区期间，三种技术的行为（串 00 章 §3.2 的 CAP 取舍）

 共识（etcd/Raft）          单主+异步复制（Redis）        CRDT（CRDB/Yjs）
 ─────────────────         ─────────────────────        ─────────────────
 A侧：凑齐过半，可写        A侧：旧主继续吞写             A侧：本地写，正常
 B侧：少数派，停写!         B侧：新主(哨兵切换)吞写        B侧：本地写，正常
      │                          │                            │
 愈合：无分歧（B侧写的         愈合：旧主降级全量同步，        愈合：双向同步，按数据
       请求本来就被拒）          旧主分区期间的写全丢           类型语义自动合并
```

三个推论，全部是运维语言：

1. **分区期间两侧都能写**（00 章 CAP 的 A 侧），且愈合后不需要人工裁决——这比"最终一致"更强，术语叫**强最终一致**（Strong Eventual Consistency）：收到同一批更新的副本必然处于同一状态。
2. **不需要选主，也就没有 failover**。Redis 主从的世界里"切主"是最大单点运维动作（哨兵、脑裂、`min-replicas` 一整套，redis 02 章 §6）；CRDT 世界里没有这个动作。
3. **写路径没有 quorum 往返**。本地接受写即应答，同步异步补——代价转嫁到了第 4 节讲的"合并语义"与元数据上。

一句话：**共识用"少数派闭嘴"换唯一真相，CRDT 用"数据结构自己会合并"换掉整个裁决环节**。06 章讲过 gossip 让成员状态"最终大家都知道"，CRDT 是同一哲学下沉到业务数据层——传播可以乱、可以重复、可以断续，合并照样收敛。

## 2. 数学直觉：只增不减 + 可交换合并

CRDT 的理论名字叫 join-semilattice（连接半格）。不推数学，记两个性质就够，它们分别挡住两类事故：

### 性质一：只增不减（单调）

状态只能"往上走"，永远不能回退。每条更新之后的必须包含之前的——像爬梯子，只能往上爬，没有下来的动作。这一条挡住的是**回退覆盖**：如果允许状态变小，一个拿着旧状态的慢副本在合并时就能把别人已经涨上去的状态拉回来（时间倒流，02 章 §2.2 的违反项）。

它有个反直觉的推论：**删除不能真的删**。集合里去掉一个元素是"状态变小"，破坏单调性——所以删除一律做成"加一块墓碑"（tombstone）标记它死了，状态本身还在涨。后果在第 4 节：墓碑是 CRDT 最主要的存储与 GC 压力来源。

### 性质二：合并可交换（谁先谁后都一样）

merge 操作满足交换律（`a ⊔ b = b ⊔ a`）、结合律（分组无关）、幂等律（`a ⊔ a = a`，重复合并自己无副作用）。挡住的是**顺序依赖**：副本间消息乱序、重复投递、分批到达（网络给的常态，00 章 §1.1），合并结果纹丝不动。幂等这条顺便白赚了 04 章的幂等重试——同步协议重发同一份状态毫无副作用。

```
[图] 三个副本各自计数（G-Counter），任意顺序合并都到同一格

 R1=(5,0,0)   R2=(0,3,0)   R3=(0,0,7)        每格=各副本自记的计数
      └──────────┼──────────┘
   任何分组合并: (R1⊔R2)⊔R3 = R1⊔(R2⊔R3) = (R1⊔R3)⊔R2
                 = (5,3,7)  总数 15           ← 顺序无关 = 收敛保证
```

判断口诀：**这份数据能不能表达成"只累积、不回退"，合并能不能写成取 max/并集/相加这类交换运算**——能，就是 CRDT 候选；要"覆盖旧值""扣减""按业务规则取舍"，就得另想办法（共识或应用层裁决）。

## 3. 四类基础 CRDT 速览

| 类型 | 状态长什么样 | 合并规则 | 日常类比 | 运维注意 |
|---|---|---|---|---|
| G-Counter（只增计数器） | 每副本一格：`R1=5, R2=3` | 逐格取 max，值=求和 | 景点多入口客流统计：每个入口一本计数册，总数=各册相加，对账时"谁的多听谁的" | 无损，永不丢计数；副本数多时状态向量变大 |
| PN-Counter（正负计数器） | 两个 G-Counter：P（加账）与 N（减账） | 分别合并，值 = P − N | 银行存/取两个台账：存款记 P 册，取款记 N 册，余额=相减 | "减法"其实是往 N 册加——单调性没破坏，代价是两倍空间 |
| G-Set（只增集合） | 元素只加不删 | 并集 | 宾客签名簿：签过的名字永远在，合并=两本簿子拼起来 | 想删元素 → 用带墓碑的变体（OR-Set），元数据立刻上来 |
| LWW-Register（最后写入者胜寄存器） | `(时间戳, 节点ID, 值)` | 时间戳大者胜，同戳比节点 ID 断胜负 | 值日排班表贴在墙上：谁最后改的听谁的 | **有损合并**：并发写只留一个；时间戳依赖时钟——第 4.3 节的坑全在这 |

这张表要带着一句话读：**前三个是无损合并（谁的更新都保留），LWW 是有损裁决（自动但会丢写）**。"用了 CRDT 就不丢数据"是面试常见口误——LWW 也是 CRDT，它丢的是时间戳小的那次写。

## 4. 工程化身三处

### 4.1 协同编辑：从 OT 到序列 CRDT

多人同时编辑一份文档是最极端的多主场景：每个人（每个浏览器标签页）都是一个独立写入口，离线还能继续写。两条技术路线：

- **OT（Operational Transformation，Google Docs 一脉）**：客户端把"在第 12 个字符后插入 X"这类**操作**发给**中央服务器**串行变换。服务器是唯一真相与顺序仲裁者——它就是一个软共识（单点串行化）。断网即不能编辑，中央服务的伸缩就是天花板。
- **序列 CRDT（Yjs / Automerge 一代）**：文档是一个字符序列 CRDT，每个字符分配**全局唯一 ID**，插入位置的算法（Yjs 用 YATA 一类）保证任何两个副本无论按什么顺序应用编辑，最终字符序完全一致。于是**服务器退化为接力棒**：只负责转发与存档，不仲裁、不需要共识，甚至可以 P2P。

运维视角的差异落到三件事：**可用性**（CRDT 天然离线可写，本地优先应用的卖点）；**服务端形态**（OT 的服务器是强状态串行点，CRDT 的服务端可以是无状态转发+对象存储）；**容量**（CRDT 文档只增不减——每个字符的 ID 与墓碑都是永久元数据，长文档/频繁删除的文档会持续膨胀，Yjs/Automerge 都有压缩与 GC 机制，效果随版本迭代，以官方文档为准）。

### 4.2 Redis Enterprise CRDB：Active-Active 地理多活

开源 Redis 的高可用答案在 11-redis/02 章：主从异步复制 + 哨兵多数派切主。它解决"一个地域挂了另一个顶上"，但**任一时刻只有一个主**——跨地域写延迟（每个写都要飞到主库所在洲）与切换丢写窗口是结构性代价。

Redis Enterprise 的 CRDB（Conflict-free Replicated Database，Active-Active 数据库）换思路：**每个地域一个独立可写的 Redis 实例，相互间异步双向同步**，同步的不是"主从字节流"而是 CRDT 语义操作，按数据类型自动合并（官方文档为准）：

| Redis 类型 | CRDT 合并语义 | 分区期间两地各写会发生什么 |
|---|---|---|
| Counter | 计数 CRDT（PN-Counter 思想） | 两边的 `INCRBY` 都保留，相加，**无损** |
| Set / Hash | OR-Set 式（观察删除）/ 逐字段合并 | 两边加的不同元素全保留；同字段改不同值按字段时间戳裁决 |
| String | LWW（按时间戳） | **有损**：时间戳大的赢，另一边这次写被静默丢弃 |

注意 String 这行：CRDB 官方明确要求各实例间**严格 NTP 同步**来压缩 LWW 的裁决错误——时钟漂移会直接"选错赢家"（01 章 §2 讲过的漂移/跳变在这里变成数据丢失的放大器）。运维三件事：NTP 纪律是数据正确性问题不是监控洁癖；多活写同一 String key 的业务要评审（该不该用 LWW 类型装关键数据）；CRDB 是商业版能力，开源版没有等价物，方案评审时别混。

### 4.3 Cassandra/Dynamo 的 LWW：时钟漂移陷阱

无主架构（Dynamo/Cassandra，一致性哈希 + NWR，`./05-sharding-and-rebalancing.md` §2）天然多主多写，那冲突怎么裁？两家走了不同的路：

- **原始 Dynamo 论文**：向量钟**检测**并发版本，并发版本全部交给应用层合并（购物车合并是论文里的原例）。工程太重，后继实现大多简化。
- **Cassandra**：干脆 LWW——同一个 key 的并发写，**写时间戳（timestamp）大的赢**，输的一方静默丢弃，连"发生过冲突"都不告诉你。删除也一样：delete 是写一个墓碑（tombstone），墓碑比数据新就遮住它，等 `gc_grace_seconds`（默认 10 天）过后才真正清除。

LWW 的坑精确对应 01 章的时钟模型：**写时间戳通常由客户端驱动按本机墙钟生成**。一个客户端钟慢 5 分钟，它"现在"的写带着 5 分钟前的时间戳，会被别人 4 分钟前发出的写覆盖——**没有任何报错，数据就是不翼而飞**。这是 LWW 与 G-Counter 的本质区别：G-Counter 的合并不依赖时间，LWW 的合并把时钟当裁判。

运维对策四条（前两条直接来自 01 章 §2 的纪律）：

1. 集群与客户端统一 NTP，对 `offset` 斜率与失联状态做告警（01 章 §2.2 的 PromQL 直接可用）；
2. 需要显式控制顺序的写用 `USING TIMESTAMP` 手工指定，不赌钟；
3. 计数场景**不要**用 LWW 字段做 `read-modify-write` 的 +=（并发必然丢更新），用 Cassandra 的 counter 表或改走单写者；
4. 理解墓碑：大量短 TTL 写会造出海量墓碑，读放大与修复风暴的经典来源（排障时先看墓碑数）。

### 4.4 三处化身的公共教训

协同编辑、CRDB、Cassandra 放在一起看，CRDT 落地的账单永远是同一张：**换来分区期间可写与无仲裁合并，付出的是元数据膨胀（墓碑/字符 ID）、有损类型的静默丢写（LWW 系）、以及"收敛"不等于"对"**（合并在数学上收敛，业务上未必是你想要的语义——购物车合并出两件商品是惊喜，账户合并出两倍余额是事故）。

## 5. CRDT vs 共识：选型一句话

**强一致读、读己之写、唯一性/互斥类约束（锁、选主、账户扣款、库存不超卖）走共识；高并发多写入口、可容忍最终一致、合并语义自然（计数、集合、协作文档）走 CRDT。**

展开成对照表，面试可以直接画：

| 需求 | 选谁 | 为什么 |
|---|---|---|
| 写完必须立刻读到（读己之写） | 共识 | CRDT 副本间异步同步，写己之写只在本副本保证 |
| 任何副本读到的都是最新 | 共识（线性读） | 同上，CRDT 只承诺收敛不承诺新鲜 |
| 全局唯一（主、锁、序列号段） | 共识 | "唯一"本质是全序仲裁，可交换合并给不了 |
| 多地域低延迟写、断网可写 | CRDT | 共识的跨地域 quorum 往返在延迟上不可行 |
| 计数、点赞、指标聚合 | CRDT（计数器） | 无损合并，天然可交换 |
| 多人协作内容（文档/白板/看板） | CRDT（序列/集合） | 合并语义自然，OT 需要中央串行点 |

两条边界再强调一遍：**CRDT 与共识不是二选一的关系，而是按数据分片的工程组合**——同一个系统里，配置与成员关系（要唯一）走共识，业务计数与协作内容（要可写）走 CRDT（下一章 Nacos 的 Distro/Raft 双协议正是这个模式的产品化）；**CRDT 收敛的是它管辖的那个数据结构**，协同文档收敛了，落库到 MySQL 的那一秒还是要单写者，别把两层混为一谈。

## 实战演练

一个纯离线脚本，把"交换律""时钟漂移丢写"亲手算一遍。不需要集群。

```bash
# [任意节点] 写出演示脚本并运行（本地 Windows 可存成 crdt_demo.py 用 python -X utf8 运行）
cat > /tmp/crdt_demo.py <<'EOF'
class GCounter:
    def __init__(self, node): self.node, self.v = node, {}
    def incr(self, n=1): self.v[self.node] = self.v.get(self.node, 0) + n
    def value(self): return sum(self.v.values())
    def merge(self, o):
        out = GCounter(None)
        for k in sorted(set(self.v) | set(o.v)):   # 排序只为输出稳定，合并本身与顺序无关
            out.v[k] = max(self.v.get(k, 0), o.v.get(k, 0))
        return out

# --- 1. G-Counter：三个副本分区期间各写各的，任意顺序合并都收敛 ---
r1, r2, r3 = GCounter("R1"), GCounter("R2"), GCounter("R3")
r1.incr(5); r2.incr(3); r3.incr(7); r2.incr(1)          # 分区期间各自累计
a = r1.merge(r2).merge(r3)                               # 合并顺序一
b = r3.merge(r1).merge(r2)                               # 合并顺序二
print("G-Counter 顺序一:", a.v, "值 =", a.value())
print("G-Counter 顺序二:", b.v, "值 =", b.value())
print("两种顺序状态相等:", a.v == b.v, "（交换律=收敛保证，总计数一次不丢）")

# --- 2. PN-Counter：减法 = 往 N 账本里加 ---
p1, n1 = GCounter("R1"), GCounter("R1")                  # 副本 R1 的存/取两本账
p2, n2 = GCounter("R2"), GCounter("R2")                  # 副本 R2 的存/取两本账
p1.incr(100)                                             # R1 侧存 100
p1.incr(50); n1.incr(30)                                 # R1 侧再存 50，取 30
p2.incr(20)                                              # 分区另一侧 R2 又存 20
P, N = p1.merge(p2), n1.merge(n2)
print("PN-Counter 余额 =", P.value() - N.value())        # (100+50+20) - 30 = 140

# --- 3. LWW-Register：慢 90 秒的钟，后写的被先写的覆盖 ---
def lww_merge(x, y):                                     # 元素 = (时间戳, 节点ID, 值)
    return x if (x[0], x[1]) > (y[0], y[1]) else y
w_a = (1000, "A", "库存=10")                              # A 在墙钟 1000 写
w_b = (910,  "B", "库存=9")                               # B 的钟慢 90s：真实时刻 1000 才写
merged = lww_merge(w_a, w_b)
print("LWW 合并结果:", merged[2], "← B 真实上写得【更晚】，但钟慢 → 被静默丢弃，无任何报错")
EOF
python3 /tmp/crdt_demo.py
```

预期输出：

```
G-Counter 顺序一: {'R1': 5, 'R2': 4, 'R3': 7} 值 = 16
G-Counter 顺序二: {'R1': 5, 'R2': 4, 'R3': 7} 值 = 16
两种顺序状态相等: True （交换律=收敛保证，总计数一次不丢）
PN-Counter 余额 = 140
LWW 合并结果: 库存=10 ← B 真实上写得【更晚】，但钟慢 → 被静默丢弃，无任何报错
```

验证方法：把合并顺序一改成 `r3.merge(r2).merge(r1)` 再跑，结果不变（交换律）；把 w_b 的时间戳改成 1100 再跑，LWW 结果翻转为"库存=9"（时间戳成为唯一裁判）——对照第 4.3 节，这就是 Cassandra/CRDB String 字段每天在做的事，而你的 NTP 质量决定它做得多对。

## 常见坑

| 症状 | 原因 | 解法 |
|---|---|---|
| Cassandra 计数字段偶发"少加" | 用 LWW 字段做 read-modify-write 的 +=，并发写互裁 | 换 counter 表或收敛到单写者；这类丢写无日志无痕迹 |
| 多活集群个别 String 更新"消失" | CRDB String 的 LWW 裁决 + 实例间时钟漂移 | 严 NTP 纪律；关键值改用 Hash 逐字段或计数类型；排查先对表（01 章 §5 三步法） |
| CRDT 集合删除后再加同元素，删掉的内容"复活" | 删除是墓碑；同 ID 元素再添加时合并语义复活旧成员 | 元素用唯一 ID（时间戳+序号）而不是业务值本身 |
| 协同文档/CRDT 存储越用越大 | 只增不减 + 墓碑与字符 ID 元数据不可回退 | 用实现自带的 GC/压缩能力，监控对象大小（随版本演进，以官方文档为准） |
| 写完从另一副本立刻读不到，判定集群故障 | CRDT 是异步收敛，没有跨副本读己之写 | 写后读钉在同一副本，或该数据改走共识存储（第 5 节对照表） |
| 协同文档内容收敛了，落库还是冲突 | CRDT 只保证它管辖的数据结构收敛，关系库不在此列 | 落库走单写者/队列串行化，两层分开设计 |
| 拿 CRDT 系统做分布式锁/选主 | 可交换合并给不了唯一性与互斥 | 锁/选主走共识（etcd/ZK；租约与 fencing token 见 `./06-gossip-membership-fencing.md` §4，动手实验 `./labs/02-distributed-lock-idempotency/task.md`） |

## 自测

1. 为什么 CRDT 里的"删除"必须实现成加墓碑，而不能把元素真的从集合里去掉？
<details><summary>答案</summary>

半格的单调性要求状态只增不减：真删会让状态变小，一个还没收到其他更新的慢副本在合并时就能把"已删"的事实覆盖回"存在"，甚至让其他副本刚加进去的合法更新被回退——时间倒流正是 02 章违反单调读的同族事故。墓碑把"删除"翻译成"追加一条死了的记录"，状态仍然在涨，合并时比较的是"加元素 vs 加墓碑"两个都可交换的事实。代价是元数据永不自动消失，必须依赖 GC（如 Cassandra 的 gc_grace_seconds、Yjs 的删除编码压缩）。
</details>

2. 两个副本分区期间对同一个 G-Counter 各做了 3 次 `INCR`，愈合后值是多少？为什么一次都不会丢？换成 LWW-Register 各写一次，结果又如何？
<details><summary>答案</summary>

G-Counter：值 = 两边各自计数的总和（各 +3 则 +6）。不丢的原因是每副本只改自己那一格，合并逐格取 max，两边的贡献在不同格子互不遮蔽——合并不依赖也不裁决"先后"。LWW-Register：只剩时间戳大的那个写，另一个彻底消失。这就是"无损合并 vs 有损裁决"的全部区别：同样是 CRDT，计数器保留全部历史，寄存器只保留赢家。
</details>

3. Redis 哨兵主从和 Redis Enterprise CRDB 都部署在两个地域，跨城光纤被挖断一小时。分别描述两侧在这一小时里能做什么、愈合后丢什么。
<details><summary>答案</summary>

哨兵主从：任意时刻只有一个主。若主在 A 地，B 地这一小时只能读（或强行手动切主）；若 B 侧凑齐哨兵 majority 完成切换，则 B 侧可写，愈合后 A 侧（旧主）这一小时的写全丢（降级+全量同步覆盖，redis 02 章 §6.4 的窗口语义）。CRDB：两侧这一小时都能读能写，计数类更新全部保留（相加），Set 的两侧新增全保留，同 key 的 String 写按时间戳只留一个赢家。丢的东西不同：主从丢的是"输掉选举那一侧的全部写"，CRDB 丢的是"并发写同一 LWW key 的输家"——粒度细一个数量级，但不是零。
</details>

4. Cassandra 集群里某台应用服务器时钟慢了 5 分钟，会发生什么？多久能发现？怎么防？
<details><summary>答案</summary>

该机器发出的写带着偏旧的时间戳，与并发写竞争时静默落败——数据"消失"且无任何错误日志，读旧值/丢写类工单查不到集群侧异常。没有主动手段能在数据库里"发现"它，必须从源头防：所有客户端/节点统一 NTP 并对 offset 斜率与失联告警（01 章 §2.2 的指标直接复用）；需要明确顺序的关键写用 `USING TIMESTAMP` 显式指定；计数类需求不用 LWW 字段自增。发现靠事后对账——这也是 LWW 类系统必须配对账任务的原因。
</details>

5. 为什么说"CRDT 给不了互斥和唯一性"？结合半格的两个性质说明。
<details><summary>答案</summary>

互斥/唯一（同一时刻至多一个 leader、锁只有一个持有者、余额不为负）本质上要求对并发操作做**全序仲裁**——必须有人判定"这两个并发请求谁先谁后，后者拒绝"。而 CRDT 的全部能力建立在合并可交换上：交换律意味着合并结果与顺序无关，等价于主动放弃了对顺序的仲裁权。所以 CRDT 能保证"副本收敛到同一状态"，但不能保证"这个状态满足全局唯一约束"——两个副本各自授予同一把锁，合并后两边都留着自己的授权记录，收敛了但双主了。锁/选主必须回到共识（03 章）或加 fencing（06 章 §4）。
</details>
