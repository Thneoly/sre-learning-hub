# 03 · On-call 与事件管理：让半夜的 page 变得可承受

> 模块：13-sre-methodology ｜ 建议时长：4 小时 ｜ 关联认证：PCA-告警（severity 路由复用 08-pca）/ —（流程本身无考点，是 SRE 岗位面试高频）

## 学习目标

- 能算出 24/7 轮值所需的最少人数，并设计 primary/secondary 双层值班表
- 能按"用户影响 × 预算消耗速度"给告警定级，并设计带时限的升级路径（escalation path）
- 能说出事件指挥（Incident Command）各角色的分工与"IC 不敲键盘"的原因
- 能搭建一次事件沟通桥：频道、播报节奏、对外三段式话术模板
- 能列出至少 5 个"应该立刻升级而不是继续硬扛"的判据

## 1. On-call 轮值设计

### 1.1 先算账：24/7 是很贵的

一周 168 小时。一名工程师每周可持续投入约 40 小时，且不能 7×24 连轴转。只算粗账：

```
24/7 primary + secondary 双层值班，每周轮换：
  每周 primary 168h + secondary 168h = 336h 值班容量
  按"每人每周值班不超过 1 周、值完至少隔一周"的健康节奏：
  ┌────────────────────────────────────────────┐
  │ W1   W2   W3   W4   W5   W6   W7   W8      │
  │ A/B  C/D  E/F  A/B  C/D  E/F  ...          │
  └────────────────────────────────────────────┘
  → primary/secondary 各 1 人轮转，最少需要 6 人（3 组）才不透支
  小于 4 人的"24/7 on-call"必然演变成轮流烧伤
```

结论：**人手不足时宁可缩小值班范围**（只对 SEV1 级别的少数告警 24/7，其余次日处理），也不要让 3 个人硬撑 7×24。

### 1.2 轮值设计要点

| 项 | 推荐做法 | 反例 |
|----|----------|------|
| 班次长度 | 一周一轮，交接固定在周中低峰（如周三 10:00） | 月班（恢复力差）、日班（交接成本高） |
| 层级 | primary 响应 + secondary 备援 + manager of duty 升级出口 | 只有一层，primary 睡着就没人管 |
| 时区 | 跨时区团队用 follow-the-sun，各自值白天班 | 无时区资源却要求"均匀"分夜班 |
| 补偿 | 夜间 page 补偿调休/补贴（组织问题，不是福利问题） | "责任心"抵睡眠 |
| 页数上限 | 每班 actionable page ≤ 2 次（Google 的经验值）；超标即触发告警治理 | 把告警噪声当正常 |

页数上限值得展开：**告警量决定轮值可持续性**。一个班 10 次 page 的团队，三个月内必然出现漏响应；正确的响应不是"加强责任心"，而是回去用第 2 章的燃烧率分档删掉不可操作（not actionable）的告警。

### 1.3 交接班（handover）

固定模板，5 分钟完成，写进共享文档：

```text
<!-- 交接班模板 · 存放于团队 wiki，每次交班追加 -->
日期/班次：2026-08-20 周三 白班 → 夜班
1. 未关闭事件：#INC-1024 CoreDNS 告警，已缓解待观察，午夜若复发按 runbook rb-06 处理
2. 近 24h 变更：portal v2.3.1 发布（15:20）；monitoring 告警规则变更（16:00）
3. 风险项：node1 磁盘 82%，明日扩容窗口已约
4. 静默中的告警：GrafanaDown 静默至 22:00（维护窗口）
```

第 2 条"近 24h 变更"是排障第一线索——绝大多数故障由变更触发，交接不带变更清单等于让下一班从零开始。

## 2. 告警分级与升级路径

### 2.1 分级：用影响定级，不用技术细节定级

| 级别 | 判定（满足其一） | 响应方式 | 首响时限 |
|------|------------------|----------|----------|
| SEV1 | 用户大面积不可用；SLO 快火档燃烧（预算 2%/1h 在烧）；资金/数据损失风险 | page + 启动事件指挥 + 状态页 | 5 分钟 |
| SEV2 | 部分用户受损或降级；中火档燃烧（5%/6h） | page | 15 分钟 |
| SEV3 | 无用户影响的隐患：单副本失败但服务正常；慢火档燃烧（10%/3d） | 工单，工作时间处理 | 4 小时 |
| SEV4 | 信息级：趋势、容量预测 | 看板/周报 | 无 |

判定锚点是第 2 章的 SLI/燃烧率，不是"进程挂没挂"——进程挂了但流量被别的副本接住、SLI 不动，就是 SEV3；进程都在但用户全 503、燃烧率爆表，就是 SEV1。

**可操作性原则**：每个 page 都必须对应一个可执行动作。如果一个告警每次响起的处理都是"忽略它"，它就该被删除或降级为 ticket——不可操作的 page 训练出来的是"狼来了"免疫，真正 SEV1 时没人当真。

### 2.2 升级路径：带时限的阶梯

```
T+0min   告警 page primary（含 runbook 链接）
T+5min   primary 未 ack → 自动 page secondary
T+15min  仍未控制（未定位根因或影响未止）→ 通知值班 manager，
         同时拉对应 SME（如网络/DBA/云厂商接口人）进沟通桥
T+30min  SEV1 仍未缓解 → 升级到部门负责人；涉及外部依赖时
         开供应商支持工单；对外发状态页首报
```

时限写在值班手册里并做成**自动升级**（告警系统的 escalation policy），不依赖人的意志。Alertmanager 侧对应的机器配置：

```yaml
# [master] alertmanager 路由片段：SEV1 page 且每 5 分钟重发，直到有人处置
# （kube-prometheus-stack 里通过 alertmanager secret 修改后 amtool check-config 校验，
#  完整路由机制见 08-pca/05-alerting-alertmanager.md）
route:
  routes:
    - matchers:
        - severity = "critical"
      receiver: oncall-phone
      group_wait: 0s
      repeat_interval: 5m      # 5 分钟无人处理就再喊一遍——机器侧的升级节拍
      continue: false
    - matchers:
        - severity = "warning"
      receiver: ticket-queue
      group_wait: 5m
      repeat_interval: 12h
```

注意 `repeat_interval: 5m` 只解决"再喊一遍"，"喊更高层级的人"需要告警平台的 escalation policy（PagerDuty/自研值班系统）或在 Alertmanager 上游接多个 receiver——面试里能说清这两层区别是加分项。

## 3. 事件指挥：Incident Command 角色分工

规模到 SEV1/SEV2 时，"所有人都在救火"是最差状态。Google 的实践是把响应拆成角色（Chapter 6 of SRE Book, Managing Incidents）：

| 角色 | 职责 | 不做什么 |
|------|------|----------|
| IC（Incident Commander 指挥） | 掌握全局态势，拆解任务并指派，决定升级与对外口径，宣告事件开始/结束 | **不敲键盘做操作** |
| OL（Operations Lead 操作） | 执行止血动作：重启、回滚、切流 | 不做需要长时间离开键盘的分析 |
| CL（Comms Lead 沟通） | 对内定时播报、对外状态页、答复高管问询 | 不掺和排障决策 |
| Scribe 记录员 | 维护时间线：谁在何时做了什么、观测到什么 | 不评价对错 |
| SME 顾问 | 提供领域判断（网络/DB/某服务内幕） | 按需被 IC 拉入，不主动抢指挥 |

两条铁律：

1. **IC 不操作**：一旦 IC 开始敲命令，就没有人在看全局——影响面、升级时限、对外口径全部失焦。角色可以由同一人在小事件里兼任，但只要事件升级，先把手上的活交出去再指挥。
2. **指挥通道与操作通道分离**：事件频道里只允许态势与决策，"我去重启了"这种执行细节去操作频道/直接做——保证指挥频道里每条消息都值得所有人读。

角色认领的第一句话模板：**"我是本次事件的 IC"**——公开认领，避免出现两个都以为自己在指挥的人。

## 4. 沟通桥

"桥"指为单一事件开辟的常驻同步通道（视频会/电话会）+ 异步频道（聊天室），外加面向外部的状态页。

```
        ┌── 内部事件频道 #inc-1024 ── 态势与决策（IC 主导）
事件 ───┤
        ├── 操作频道 #inc-1024-ops ── 执行细节（OL 与执行者）
        ├── 桥（视频/电话）───────── IC/CL/SME 小范围同步
        └── 对外状态页 ──────────── CL 每 30 分钟更新（SEV1）
```

播报节奏表：

| 事件级别 | 对内播报间隔 | 对外更新间隔 |
|----------|--------------|--------------|
| SEV1 | 每 30 分钟整点 | 每 30~60 分钟，或状态有实质变化时 |
| SEV2 | 每 2 小时 | 按需，影响客户时至少首报+终报 |
| SEV3 | 交班时汇总 | 不对外 |

对外三段式模板（CL 直接套）：

```text
<!-- 状态页首报 -->
[首报] 2026-08-20 14:05
我们观测到部分用户无法访问课程页（约 30% 请求失败）。
工程师已介入，下一条更新最晚 14:35。

<!-- 进展报 -->
[进展] 2026-08-20 14:32
根因初步定位为网关配置错误，已开始灰度回滚，恢复中。
下一条更新最晚 15:00。

<!-- 终报 -->
[解决] 2026-08-20 14:47
服务已于 14:45 全面恢复。故障期间约 12% 的请求受影响，持续 40 分钟。
详细复盘将在 48 小时内发布。
```

写法纪律：**只播报事实、时间点与下一步，猜测必须标注"疑似/待确认"**；永远给下一条更新的时间（没消息就是最大的消息）；失败比例和持续时长如实写——这两行数字就是第 2 章 SLI 的口径，事中和事后对得上，复盘才有公信力。

## 5. 升级时机：硬扛是最贵的选项

新手最常见的失误是把升级当失败、把求助当丢脸。判据清单（满足任意一条就升级）：

1. **时限到了**：15 分钟内连根因方向都没有（SEV1 是 5 分钟）——按第 2.2 节阶梯走，这是流程动作不是能力评价。
2. **影响在扩大**：受影响流量/用户数还在上升，或波及第二个系统。
3. **需要你没有的权限**：改机房网络、动生产 DB、找云厂商后台——等待授权的时间应计入升级。
4. **需要外部依赖**：第三方接口、供应商工单——先开单再排障，并行不串行。
5. **触及知识边界**：需要某组件的 SME 才能解释的日志/内核行为。
6. **疲劳判据**：连续处置超过 2 小时或凌晨 3 点后判断力下降——换人比硬撑快。
7. **两难决策**：要不要全量回滚、要不要丢缓存——需要业务方拍板的止损决策，升级给能拍板的人。

升级话术要带上下文，不要只喊"救命"：**"INC-1024，CoreDNS 解析失败影响全集群，已排查 X/Y 排除，怀疑 ConfigMap 被改，需要你帮忙看 Z，当前影响 30% 请求"**——收到的人不用反问就能进场。

## 实战演练：一次 20 分钟的迷你事件推演

环境：kubeadm 集群 + 靶场脚本。单人也可做：分时戴帽（前 10 分钟只当 IC，只指派不操作；后 10 分钟换 OL 帽执行）。

### Step 1 开局：注入故障（由"导演"角色执行）

```bash
# [master] 注入：Service 找不到后端（对外表现是访问拒绝/超时）
sudo bash scripts/faults/break-endpoints.sh
date '+%F %T'   # 记为 T0，时间线起点
```

### Step 2 事件响应（IC + OL 分角色）

```bash
# [master] IC 视角：先定影响面——演示业务在 fault-ep 命名空间
kubectl -n fault-ep get pods -o wide
kubectl -n fault-ep get endpoints

# [master] OL 视角：复现用户路径，确认"现象 → 影响"链
kubectl -n fault-ep run curl-test --image=curlimages/curl:8.10.1 \
  --restart=Never --rm -it -- curl -sS --max-time 3 \
  http://fault-web-svc.fault-ep.svc.cluster.local/ -o /dev/null -w '%{http_code}\n'
```

预期：Pod 全部 Running/Ready，但 curl 返回 000（connection refused），endpoints 为空——"服务全绿但用户不可用"，正好用来体会"用影响定级而不是用进程状态定级"。全程把每一步按时间戳记进时间线（模板见 Step 3）。

### Step 3 收敛与关闭

排障与修复的完整路径在 `scripts/faults/FIXES.md` 故障 7——本演练**先不偷看**，用自己的路径走到修复（提示：`kubectl -n fault-ep describe svc fault-web-svc` 对比 Pod label），修完再看 FIXES.md 对答案。恢复验证后 IC 宣告关闭：

```text
<!-- 事件时间线（Scribe 模板，演练时边做边记） -->
T0      注入 break-endpoints（导演操作）
T+2m    告警/演练开始；IC 认领，指派 OL 复现用户路径
T+5m    OL 确认：Pod 2/2 Ready，curl 000，影响面=fault-ep 全部流量 → 定级 SEV2
T+9m    检查 svc describe → selector 与 pod label 不匹配
T+12m   修复 selector；endpoints 恢复 2 个地址
T+14m   curl 200，持续 2 分钟无复发 → IC 宣告关闭，转复盘（第 4 章）
```

### Step 4 演练后 5 问（写在时间线末尾）

1. 从 T0 到"确认用户受影响"用了几分钟（MTTD）？到修复用了几分钟（MTTR）？
2. 有没有哪一步是在没有验证影响面的情况下先钻进技术细节？
3. IC 有没有忍不住自己敲命令？（单人演练尤其容易）
4. 对外话术演练了吗——如果这是生产，状态页首报该在 T+? 写出来。
5. 这次排障哪一步下次可以直接抄 runbook？（答案写进第 4 章的 runbook 作业）

## 常见坑

| 症状 | 原因 | 解法 |
|------|------|------|
| 半夜 page 没人响应 | 单层值班 + 无自动升级 | secondary + 时限驱动的 escalation policy（2.2 节阶梯） |
| 告警风暴时所有人都在救火 | 没有角色分工，IC 缺位 | 第一动作是认领 IC，再把执行分派出去 |
| 事件频道 500 条消息没人看得懂 | 指挥与执行混流 | 分频道：指挥频道只放态势与决策 |
| 复盘时"当时谁做了什么"吵不清 | 没有 Scribe 时间线 | 指定记录员，边处置边记时间戳 |
| 高管在频道里追问细节拖慢处置 | 对外沟通无专人 | CL 挡在 IC 前面，高管问询由 CL 统一答复 |
| 升级被当成能力问题没人用 | 文化问题 + 无判据 | 公开升级判据清单（第 5 节），复盘时检查"该升未升" |
| 每班十几个 page 团队麻木 | 不可操作告警太多 | 页数上限超标即启动告警治理，删或降级 |

## 自测

<details><summary>1. 为什么"IC 不敲键盘"是铁律，小团队也要遵守吗？</summary>

IC 的稀缺资源是全局注意力：影响面评估、任务指派、升级时限、对外口径都需要它。IC 一旦开始执行操作，就进入"单线程深钻"状态，全局失焦——而事件最怕的不是某个操作慢，是没人看着时钟和影响面。小团队可以让同一人在不同时刻切换角色，但同一时刻只能戴一顶帽子：要敲命令就先把指挥权交出去。
</details>

<details><summary>2. 告警系统里 repeat_interval=5m 和值班系统的 escalation policy 是什么关系？</summary>

前者是"同一接收方被重复提醒"，解决"睡着了没听见"；后者是"超时后把通知发给更高/更广的接收方"，解决"听见了但没行动"。只有 repeat 没有 escalation 时，一个弃疗的 primary 会让告警每 5 分钟空响一整晚；只有 escalation 没有 repeat 时，深夜一次未被听到的 page 会在 5 分钟后被越级。两层要同时配置，且时限与第 2.2 节的阶梯一致。
</details>

<details><summary>3. SEV1 事件进行中，CEO 直接在事件频道里问"什么时候能好"。正确处理是什么？</summary>

不由 IC 回答，更不因此中断处置。由 CL 统一答复，内容用三段式口径：已确认的事实、当前动作、下一条更新时间；没有 ETA 就明说"暂无预计，下一条更新 15:00"。高管问询全部由 CL 挡在指挥频道之外，是保护 IC 注意力的机制，也是对外的单一信息源原则。
</details>

<details><summary>4. "每班 actionable page ≤ 2"这个上限的用途是什么？超标说明什么？</summary>

它是轮值可持续性的红线，也是告警质量的度量。超标说明告警体系在透支团队：要么大量不可操作的告警混进 page 通道（该删或降级），要么系统确实不稳定到需要工程投入（回到错误预算：烧穿就冻结发布还可靠性债）。把页数当指标管理，倒逼告警从"多多益善"转向第 2 章的燃烧率分档。
</details>

<details><summary>5. 交接班模板里为什么必须有"近 24h 变更"清单？</summary>

因为变更是最常见的故障源（业界普遍把过半故障归因于变更）。下一班接手一个新告警时，"昨晚 22 点网关发过版"这类信息能把排查范围从全系统缩小到变更面，直接决定 MTTD。反向要求：变更流程必须把入口收拢到可被交接清单自动聚合的地方（CI/CD 记录、变更工单），散在个人手里的"我顺手改了下"是交接盲区的最大来源。
</details>

## 靶场联动：靶场是这些方法论的练习场

靶场的 12 个 break 脚本天然就是"事件素材库"：`break-kubelet.sh` 练的是 SEV2（单节点劣化），`break-apiserver-port.sh`/`break-etcd-endpoint.sh` 一上来就该按 SEV1 处置。推荐的练法：随机抽一个脚本注入，掐表走完"定级 → 认领 IC → 时间线 → 升级判据检查 → 关闭"全流程，把 MTTD/MTTR 记进表格横比——第 3 章练的是流程熟练度，它直接决定第 4 章复盘素材的质量。
