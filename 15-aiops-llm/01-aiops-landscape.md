# 01 · AIOps 全景与 LLM 的真实位置

> 模块：AIOps/LLM 运维（15）｜ 建议时长：1.5 小时 ｜ 前置：无（建议配合 13-sre-methodology/03 值班与故障管理一起读）｜ 关联认证：—（无直接考点，岗位差异化能力）

## 学习目标

- 能画出运维自动化的五级演进路线（人工→脚本→监控体系→AIOps→Agent），并说出每一级"解决了什么、遗留了什么"，能用落地成熟度表（M0~M4）自评团队所处位置
- 能解释 LLM 在运维中改变的到底是哪一层（认知层），以及它绝对没改变的三件事（决策权、责任、变更安全）
- 能列举 LLM 带来的三项具体收益：告警降噪、上下文聚合、建议生成
- 能把一份典型 AIOps Agent 岗位 JD 拆解成"背后真实技能清单"，并映射到本学习中心的对应模块
- 能在练习集群上完成一次"事件上下文聚合"实验：脚本做确定性聚合，LLM 做摘要与建议

## 1. 五级演进：从人肉到 Agent

运维自动化的历史不是一次革命，而是五次"把上一级的遗留问题交给下一级解决"：

```
L0 人工        L1 脚本        L2 监控体系      L3 AIOps        L4 LLM/Agent
(1990s-)       (2000s-)       (2010s-)         (2018-)          (2023-)
   │              │               │                │                │
 登机器看      cron+bash       metrics/logs     异常检测/告警    自然语言接口
 拍脑袋改      固化重复劳动    告警+面板        压缩/根因        +工具调用
   │              │               │                │                │
 遗留:          遗留:           遗留:            遗留:            遗留:
 知识在人脑     判断仍靠人      告警风暴、       场景定制重、     决策与责任
 不可复制       不会自己跑      MTTA 受限于      冷启动慢、       仍必须归人
                               人的注意力       可解释性差       （当前边界）
```

逐级拆开看：

| 级别 | 核心能力 | 典型工具 | 解决了什么 | 遗留了什么 |
|---|---|---|---|---|
| L0 人工 | 登机器、看日志、凭经验改 | ssh、top、grep | — | 知识锁在人脑，人走了经验就走了 |
| L1 脚本自动化 | 把重复动作固化成代码 | bash、cron、Ansible | 重复劳动、手误 | 脚本不会自己判断"该不该跑" |
| L2 监控体系 | 指标/日志/告警/面板 | Prometheus、Grafana、ELK | "坏了才知道"变成"坏了马上知道" | 告警风暴；注意力瓶颈；MTTA 受限于人读告警的速度 |
| L3 AIOps（传统机器学习） | 异常检测、告警压缩、根因排序 | 各类时序 ML 平台 | 把 300 条告警压成 3 个事件 | 每个场景要单独建模；冷启动要大量历史数据；结果不可解释，值班不敢信 |
| L4 LLM/Agent | 自然语言接口 + 工具调用 | LLM API、Function Calling、MCP | "读告警、拼上下文、写初稿"这类认知劳动 | 决策权、责任、变更安全——见第 3 节 |

关键结论：**L4 不是替代 L2/L3，是长在它们上面的**。LLM 自己不采集任何数据——metrics 还得靠 Prometheus（08 模块），trace 还得靠 OTel（09 模块），日志还得靠 Loki（10 模块）。LLM 消费的是这些系统的输出。

## 2. LLM 到底改变了什么：认知减负

把值班的 8 小时拆开，真正动手敲命令的时间往往不到 1 小时，剩下的是认知劳动：

- **读**：把 47 条告警读成"其实是一个问题"
- **拼**：去 events、logs、metrics、变更记录四个地方拼出完整故事
- **查**：翻 wiki/复盘/IM 记录找"上次这个告警怎么处理的"
- **写**：故障通报、工单、复盘初稿

LLM 改变的正是这四类劳动。落到运维场景就是三件事：

```
              ┌──────────────────────────────────────────┐
   30 条告警 │ 1. 告警降噪/聚合：30 条 → 1 段摘要         │
   4 个数据源 │ 2. 上下文聚合：events+logs+metrics → 1 个故事│
   一堆历史工单│ 3. 建议生成：历史相似 incident → 候选动作   │
              └──────────────────────────────────────────┘
                     全部是"把信息压成人能快速决策的形态"
                     ——所以叫认知减负，不叫自动修复
```

| 能力 | 输入 | 输出 | 人的角色 |
|---|---|---|---|
| 告警降噪/聚合 | Alertmanager 告警列表、事件流 | "这 30 条告警源于 worker1 节点 NotReady" | 判断摘要是否可信 |
| 上下文聚合 | Pod events + 容器日志 + 相关 deployment 的最近变更 | 一段按时间线组织的问题陈述 | 补充 LLM 拿不到的内网信息 |
| 建议生成 | 现象 + 历史复盘 + runbook | 排查假设列表 + 每条的验证命令 | 逐条验证后执行（第 2 章的纪律） |

放到一次真实的 P2 值班里，注意力分配的变化是这样的：

```
没有 LLM 的 30 分钟                     有 LLM 的 30 分钟
─────────────────────                  ─────────────────────
读 30 条告警  ████████ 8min            读 1 段摘要  ██ 2min
四处拼上下文  ██████████ 10min          验证摘要要点  ███ 4min
翻历史工单    █████ 5min                验证 AI 假设  ██████ 7min
动手修复      ███ 3min                  动手修复      ███ 3min
写通报        ████ 4min                 审改 AI 草稿  ██ 2min
                                         └► 剩余 12min 处理下一个工单
```

注意右侧多出来的两类动作——**验证摘要**和**验证假设**——不是浪费，这正是把幻觉挡在决策之前的成本。省下的时间被验证吃掉一半，剩下一半才是净收益；谁宣传"AI 让排障时间缩短 90%"，先看他把验证成本藏到哪里去了。

注意三项能力的共同点：**LLM 产出的是"给决策做输入的文本"，不是决策本身**。这是评估一切 AIOps 功能是否靠谱的第一刀：如果产品宣传"AI 自动修复"，先问修复动作谁审批、谁兜底。

## 3. LLM 没改变什么

这一节比上一节重要，因为它直接决定你敢不敢在值班时用 LLM。

| 没改变的事 | 含义 | 实操纪律 |
|---|---|---|
| 决策权 | "要不要重启生产数据库"的拍板永远是人的 | LLM 的任何建议只是建议；采纳前必须有验证证据 |
| 责任 | 复盘报告的 owner 字段不会写"ChatGPT" | AI 参与的过程要留痕（哪个 prompt、什么输出、你怎么验证的） |
| 变更安全 | 变更流程（审批/灰度/回滚）不因 AI 参与而豁免 | AI 生成的变更命令走和人写命令完全相同的评审路径 |
| 数据质量 | LLM 只能摘要你喂给它的数据 | 监控覆盖没做好的系统，AI 也变不出根因 |
| 确定性 | 同样输入可能得到不同输出 | LLM 不能当数据库/计算器用；数字必须回源核对 |

一个直接的推论：**CKA/CKS 教你的那些排障基本功一个都不能少**。LLM 让你从"记不住 kubectl 语法"里解放出来，但"该看哪个对象、输出说明什么、下一步查哪"的判断链，仍然建立在你理解集群机制的基础上。基础不牢的人用 LLM，只会把错误结论生成得更流利。

## 4. 岗位画像解构：AIOps Agent JD 拆解

下面这份 JD 是按 2025-2026 年公开招聘信息中"AIOps 算法/平台工程师"、"智能运维 Agent 开发"类岗位的共性整理的样本，不指向任何具体公司：

> **岗位：AIOps / LLM 运维 Agent 开发工程师**
> 1. 负责 AIOps/LLMops 平台建设，将大模型应用于告警治理、根因定位、智能问答场景；
> 2. 负责运维知识库建设与 RAG 检索链路优化，提升检索命中率与回答准确性；
> 3. 设计运维 Agent 工具链（Function Calling/MCP），接入审批流与安全管控；
> 4. 建设 prompt 模板与评测集，持续迭代模型效果，负责线上效果运营；
> 5. 任职要求：熟悉 Kubernetes 生态与可观测体系；扎实的 Python 工程能力；了解 RAG/Agent 技术栈；有大模型应用落地经验优先。

## 5. 落地成熟度自评：你的团队在哪一级

把前四节合成一张可以对着打勾的成熟度表。自评时取"你已经稳定做到的最低一级"，不是"做过一次的最高一级"：

| 级别 | 特征 | 典型表现 | 下一级的门槛 |
|---|---|---|---|
| M0 无沉淀 | 知识在个人脑里 | 排障靠"问老王" | 把重复处理的故障写成第一份 runbook |
| M1 有脚本有监控 | L1~L2 | 告警进群、面板齐全，但值班仍逐条人读 | 告警按"故障"而不是"规则"聚合（Alertmanager grouping 起步） |
| M2 有知识库 | 知识可检索 | runbook/复盘入库，新人能自助查 | 知识库接上检索问答（本模块 03 章） |
| M3 AI 辅助个人 | LLM 进个人工作流 | 值班用 T1 模板提问、AI 出假设人验证（本模块 02 章） | 把个人用法固化成团队规范与模板库 |
| M4 AI 进流程 | 只读 Agent 上线 | 值班 IM 里 @助手 拿诊断报告，变更走审批（本模块 04 章） | 用 MTTA/首轮假设命中率度量效果并迭代 |

两个常见误判：

- **跳级**：M1 都没站稳就想直接上 M4——告警本身还乱成一片，Agent 只会把噪声更流利地复述给你。表里的门槛列就是防跳级的。
- **倒挂**：监控覆盖不全（M1 欠账）却先建了知识库（M2）——知识库记的全是"我们没有数据"的抱怨。四层依次补，每层都给上层供数。

对照学习中心的模块地图：01~14 模块把你从 M0 送到 M1~M2，本模块负责 M2~M4 的方法论与工程实现。

## 实战演练：体验一次"上下文聚合"

目标：亲手复现第 2 节说的"LLM 最有用的那一件事"——把散落的事件聚成一段人能快速消化的陈述。分工刻意设计成：脚本做确定性聚合（可重复、可审计），LLM 做摘要与建议（自然语言、需验证）。

前提：kubeadm 练习集群正常，`kubectl` 可用。

```bash
# [master] 导出全集群最近事件为 JSON（事件的 lastTimestamp 可能为空，后面 jq 兜底）
kubectl get events -A --sort-by=.lastTimestamp -o json > /tmp/events.json
wc -l /tmp/events.json
```

预期输出类似（行数取决于集群活跃度）：

```
1800 /tmp/events.json
```

先做对照实验——纯手工读一遍：

```bash
# [master] 把事件压成"值班视角"表格（TSV：时间/命名空间/类型/对象/原因/消息）
jq -r '.items[] | [(.lastTimestamp // .eventTime // "-"), .involvedObject.namespace, .involvedObject.kind, .involvedObject.name, .reason, (.message // "-")] | @tsv' /tmp/events.json | tail -30
```

再看看哪类事件在刷屏：

```bash
# [master] 按原因+命名空间聚合计数，降序取前 10
jq -r '.items[] | [.reason, (.involvedObject.namespace // "-")] | @tsv' /tmp/events.json | sort | uniq -c | sort -rn | head -10
```

现在生成给 LLM 的完整上下文文件：

```bash
# [master] 生成"上下文聚合"prompt 文件
{
  echo "你是 Kubernetes 值班工程师的助手。下面是集群最近事件列表（TSV：时间/命名空间/类型/对象/原因/消息）。"
  echo "请输出三部分："
  echo "1) 不超过 3 句话的整体摘要；"
  echo "2) 按严重度排序的 Top3 问题，说明判断依据；"
  echo "3) 每个 Top3 问题给一条只读验证命令（kubectl get/describe/logs 范围内）。"
  echo "禁止给出任何变更类命令（delete/patch/scale 等）。条目里没有的信息不要编造。"
  echo "----"
  jq -r '.items[] | [(.lastTimestamp // .eventTime // "-"), .involvedObject.namespace, .involvedObject.kind, .involvedObject.name, .reason, (.message // "-")] | @tsv' /tmp/events.json | tail -50
} > /tmp/llm-context.txt
wc -l /tmp/llm-context.txt
```

把 `/tmp/llm-context.txt` 的内容整体粘贴给你可用的任意 LLM（网页版、CLI 或内网部署均可），对比它给你的 Top3 和你自己在第 2 步肉眼找出的重点。然后做两个动作：

1. **验证**：挑 LLM 给出的一条只读验证命令，在你的集群上实际执行，确认它的判断有据。
2. **挑错**：检查摘要里有没有它"脑补"的细节（比如你没喂节点信息它却说"worker1 压力大"）。找到一个幻觉实例，你就理解了第 3 节的"确定性"一行为什么那么写。

如果想做进阶版，把靶场的一个故障注进来再跑一遍（命令见第 2 章实战）：

```bash
# [master] 注入一个故障让事件流更"有故事"（用完记得 --restore）
sudo bash ~/learning-hub/scripts/faults/break-imagepull.sh
sleep 60 && kubectl get events -A --sort-by=.lastTimestamp -o json > /tmp/events.json
```

## 常见坑

| 症状 | 原因 | 解法 |
|---|---|---|
| LLM 摘要里出现你没喂过的细节 | 模型在"补全合理故事"，不是在检索事实 | 缩小 prompt 授权范围（"条目里没有的不要编造"），并逐条验证 |
| 团队不敢用 AI 辅助排障 | 怕出事没责任边界 | 先落地"只读辅助"：AI 只许给查询命令和摘要，变更命令一律人工重写 |
| 把告警原文整段丢给 LLM 效果很差 | 告警 JSON 里 80% 是无关字段 | 先用 jq/脚本裁剪（本节实战的做法），再交给模型 |
| 有人拿生产日志/IP/token 贴公网 LLM | 没有数据分级意识 | 敏感字段先脱敏（第 3 章第 3 节的规范）；内网环境优先用本地部署模型 |
| 期望 LLM 替代监控建设 | 概念混淆：LLM 消费数据，不生产数据 | 先补可观测覆盖（08/09/10 模块），再做 AI 应用 |

## 自测

1. 为什么说 L4（LLM/Agent）不是替代 L2（监控体系）而是"长在它上面"？如果 Prometheus 的 scrape 覆盖缺了某个组件，LLM 的根因分析会发生什么？

<details><summary>答案</summary>

LLM 的全部输入来自监控/日志/事件系统吐出的数据，它自己不采集任何东西。scrape 缺口意味着喂给模型的数据本身不完整，LLM 会在残缺数据上生成"看起来完整"的分析——比没有分析更危险，因为它带着自信的语气。所以 AIOps 落地的先后顺序必须是：先补数据覆盖，再上 AI 摘要。
</details>

2. "告警降噪"这件事在 L3（传统机器学习）时代就有，LLM 版本的降噪本质区别在哪里？

<details><summary>答案</summary>

传统方案是聚类/抑制规则，输出还是一堆告警的分组，值班仍要人读；LLM 版本输出的是自然语言摘要加时间线叙事，把"读"的成本降到接近零，且能跨数据源（告警+事件+变更记录）拼上下文。代价是引入了幻觉风险，摘要必须可回溯到原始告警。
</details>

3. 某同事用 LLM 生成了修复命令并直接在生产执行，出了事故。复盘时"我是按 AI 建议做的"这个理由在责任认定里站得住吗？

<details><summary>答案</summary>

站不住。LLM 没有决策权也没有责任能力，执行命令的人就是变更的执行者与责任人。合规做法是：AI 建议必须经过人工验证与审批（第 4 章的分级响应），且过程留痕。这也是为什么本模块反复强调"AI 建议必须验证后执行"是纪律而不是建议。
</details>

4. 第 4 节的 JD 拆解表里，为什么"告警治理、根因定位"对应的模块是 08-pca 和 05-cka，而不是任何 LLM 课程？

<details><summary>答案</summary>

因为做告警治理的前提是能判断"AI 的摘要/根因候选对不对"，这需要懂告警规则怎么写（PromQL/Alertmanager）和 K8s 故障模式（事件、状态、调度行为）。不懂底层的人做 LLM 运维应用，无法评测效果，只能当传声筒。
</details>

5. 如果让你给团队定一条"AI 参与值班"的最低红线，你会定什么？为什么只用一条？

<details><summary>答案</summary>

参考答案：AI 产出的任何变更类命令，必须由人验证并重新录入执行（或走审批流），不允许从聊天窗口复制粘贴直接上生产。只定一条是因为红线多了等于没有红线——这条覆盖了最大的爆炸半径（变更事故），而只读类操作的风险可以由 RBAC 兜底。
</details>
