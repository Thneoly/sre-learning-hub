# Lab 01 · 解答：电商三层 VPC 设计

## 思路总览

先做三个决定，再填表：

1. **网段**：机房占 `10.0.0.0/8`、办公占 `192.168.0.0/16`，唯一干净的大段是 `172.16.0.0/12`。取 `172.16.0.0/16` 作 VPC，第三字节按层分配：公网层 10/11、应用层 20/21、数据层 30/31（`-a`/`-b` 后缀对应 AZ）。命名、网段、AZ 三者对齐，看到 IP 就知道在哪层哪个 AZ——这是网络背景最直接的变现。
2. **三层 + 双 AZ = 6 个 vSwitch**：每层每 AZ 一个 `/24`（251 个可用地址），对"nginx×2、order-api×2、RDS 主备"的规模绰绰有余，且第三字节留白（12/13、22/23、32/33）作为每层的扩容段。
3. **安全组链式收敛**：sg-db 只收 sg-app，sg-app 只收 sg-web，sg-web 只收 LB 通信网段，SSH 只收 sg-bastion。利用"授权对象可以是安全组"实现角色间授权，不写任何 `0.0.0.0/0` 入方向（除跳板机的办公出口 IP）。

# 电商生产 VPC 设计

> 业务：主站 API + 下单链路，日均 50 万 PV，双 11 峰值约 10 倍
> 云与地域：阿里云 cn-hangzhou，双 AZ（cn-hangzhou-a / cn-hangzhou-i）

## 1. 拓扑图

```
                            Internet
                                |
                  +-------------+-------------+
                  |     ALB（公网七层 LB）     |
                  |  监听 443/HTTPS，双AZ接入 |
                  |   监听 80  -> 301 跳 443  |
                  +------+-------------+------+
                         |             |
              AZ cn-hangzhou-a   AZ cn-hangzhou-i
                         |             |
      +------------------+---+   +-----+------------------+
      | vSwitch web-a        |   | vSwitch web-b        |
      | 172.16.10.0/24       |   | 172.16.11.0/24       |
      | [web] ECS x2 + 跳板  |   | [web] ECS x2         |
      +-----------+----------+   +----------+-----------+
                  | :8080 仅收 sg-web流量      |
      +-----------+----------+   +----------+-----------+
      | vSwitch app-a        |   | vSwitch app-b        |
      | 172.16.20.0/24       |   | 172.16.21.0/24       |
      | [app] ECS x2         |   | [app] ECS x2         |
      +-----------+----------+   +----------+-----------+
                  | :3306 仅收 sg-app流量      |
      +-----------+----------+   +----------+-----------+
      | vSwitch db-a         |   | vSwitch db-b         |
      | 172.16.30.0/24       |   | 172.16.31.0/24       |
      | [db] RDS主/Redis主   |   | [db] RDS备/Redis备   |
      +----------------------+   +----------------------+
```

图例：[web] nginx + 跳板机；[app] order-api 无状态服务；[db] 托管数据库。流量自上而下逐层收敛，数据层不配 EIP、无公网路由。

## 2. 子网规划

网段选择理由：机房占用 10.0.0.0/8、办公与 VPN 占用 192.168.0.0/16，为避免后续专线/VPN 打通时路由冲突，VPC 取 172.16.0.0/16（属于 172.16.0.0/12）。第三字节按层分段，AZ 用后缀 -a/-i 区分。

| 名称 | 层 | 可用区 | CIDR | 用途 | 冲突检查 |
|------|----|--------|------|------|---------|
| VPC | — | — | 172.16.0.0/16 | 电商生产网 | 与机房、办公网段无冲突 |
| web-a | 公网层 | cn-hangzhou-a | 172.16.10.0/24 | nginx x2 + 跳板机 | 无冲突 |
| web-b | 公网层 | cn-hangzhou-i | 172.16.11.0/24 | nginx x2 | 无冲突 |
| app-a | 应用层 | cn-hangzhou-a | 172.16.20.0/24 | order-api x2 | 无冲突 |
| app-b | 应用层 | cn-hangzhou-i | 172.16.21.0/24 | order-api x2 | 无冲突 |
| db-a | 数据层 | cn-hangzhou-a | 172.16.30.0/24 | RDS 主 + Redis 主 | 无冲突 |
| db-b | 数据层 | cn-hangzhou-i | 172.16.31.0/24 | RDS 备 + Redis 备 | 无冲突 |

扩容预留：每层的下一个 /24（172.16.12.0/24、172.16.22.0/24、172.16.32.0/24）预留给未来新增 vSwitch；大促弹性优先横向加 ECS，不动网段。

## 3. 安全组矩阵

设计原则：入方向白名单、有状态不写回程；角色间用"授权对象=安全组"链接；除跳板机外不出现公网 CIDR 入方向。

| 安全组 | 方向 | 协议 | 端口 | 授权对象 | 说明 |
|--------|------|------|------|---------|------|
| sg-bastion | 入 | tcp | 22 | 203.0.113.7/32 | 跳板机唯一入口：办公出口 IP |
| sg-web | 入 | tcp | 80 | 100.64.0.0/10 | 仅收 LB 转发与健康检查流量（网段以官方文档为准） |
| sg-web | 入 | tcp | 22 | sg-bastion | 仅跳板机可 SSH 公网层 |
| sg-web | 出 | tcp | 443 | 0.0.0.0/0 | 调第三方支付/短信网关 |
| sg-app | 入 | tcp | 8080 | sg-web | 仅收公网层流量 |
| sg-app | 入 | tcp | 22 | sg-bastion | 仅跳板机可 SSH 应用层 |
| sg-app | 出 | tcp | 3306 | 172.16.30.0/23 | 仅访问 db-a/db-b（/23 覆盖两个 /24） |
| sg-db | 入 | tcp | 3306 | sg-app | 仅应用层可连库 |
| sg-db | 入 | tcp | 6379 | sg-app | 仅应用层可连 Redis |
| sg-db | 入 | icmp | -1/-1 | sg-app | 放行 ping 便于排障 |

## 4. SLB 拓扑

- 产品与接入：公网七层 ALB，双可用区接入（cn-hangzhou-a 主、cn-hangzhou-i 备），HTTPS 证书托管，公网带宽按流量计费
- 监听：443（HTTPS，开启 HTTP/2）转发至后端服务器组 vsg-web 的 80 端口；另配 80 监听做 301 重定向到 443，保证旧链接不断
- 后端服务器组 vsg-web：web-a 的 ECS x2 + web-b 的 ECS x2，后端端口 80，权重各 100，流量跨 AZ 均衡
- 健康检查：HTTP GET /healthz，正常返回 200 判健康；检查间隔 2 秒，健康阈值 3 次、不健康阈值 3 次，连续失败即摘除
- 大促弹性：应用层配置 ESS 弹性伸缩（CPU 平均 70% 触发扩容），新 ECS 自动加入 vsg-web；峰值回落后自动缩容
- 故障演练口径：单独停掉 web-a 两台 ECS，健康检查应在数秒内摘除，外部 curl 仍返回 200，验证双 AZ 冗余

## 5. 实施与验证

1. 创建 VPC 与 6 个 vSwitch：`aliyun vpc CreateVpc --RegionId cn-hangzhou --CidrBlock 172.16.0.0/16 --VpcName shop-prod`，再按表逐个 `CreateVswitch`；验收：`aliyun vpc DescribeVpcs` / `DescribeVswitches` 与上表一致
2. 创建 4 个安全组（bastion/web/app/db）并按矩阵逐条 `AuthorizeSecurityGroup`；验收：`DescribeSecurityGroupAttribute` 条数与矩阵一致
3. 在 4 个 web/app vSwitch 各启动 2 台按量 ECS（Ubuntu 22.04 镜像），用云助手安装 nginx 与 order-api；验收：跳板机 SSH 可达，web 层 curl app 层 8080 通
4. 创建 RDS 主备（db-a 主、db-b 备，仅内网）与 Redis；验收：从 app 层用 `mysql -h <内网地址> -P 3306 -u appuser -p` 能登录
5. 创建 ALB、443 监听与后端组 vsg-web 并启动；验收：`curl -I https://<ALB域名>/healthz` 返回 200
6. 双 AZ 演练：停止 web-a 的两台 ECS，确认健康检查摘除且流量全切 web-b；演练后按第 02 章收尾清单删除全部按量资源

## 设计决策讲解（为什么这么选）

| 决策 | 备选方案 | 为什么不选备选 |
|------|---------|---------------|
| VPC 用 172.16.0.0/16 | 10.x / 192.168.x | 与机房、办公网冲突，专线打通时路由无法收敛（第 01 章自测第 5 题的现实版） |
| 每层每 AZ 一个 /24 | 一个大 /16 平铺 | 层间隔离要靠子网边界（配 NACL 或路由控制），平铺后安全组成为唯一防线；且 /24 便于口头报 IP 定位故障层 |
| 数据层不配 EIP | 数据层留 EIP 便于运维 | "无公网出口"是硬约束；运维走跳板机 + 内网，安全上少一整面攻击面 |
| ALB 七层做 HTTPS 卸载 | NLB 四层 TLS 透传 | 卸载后后端走明文 HTTP，ECS 无需管理证书；七层还能做 301 跳转与路径路由 |
| 健康检查 3×2s | 默认更慢的阈值 | 大促 10 倍流量下摘除慢一秒就多砸一批超时；2s×3 在误摘与慢摘之间取平衡 |
| sg-app 出方向限 3306 到 /23 | 出方向默认全放 | 默认全放也能跑，但收紧出方向能挡住被攻陷后的横向移动（CKS 最小权限思想） |

注意 `172.16.30.0/23` 这个细节：它精确覆盖 db-a(172.16.30.0/24) 与 db-b(172.16.31.0/24) 两个子网，是对"授权对象可以是网段"的规范用法——比 `0.0.0.0/0` 收敛，比写两条 /24 简洁。
