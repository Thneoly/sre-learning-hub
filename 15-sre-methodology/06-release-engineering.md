# 06 · 发布工程与变更管理：把发版从豪赌变成例行公事

> 模块：15-sre-methodology ｜ 建议时长：4 小时 ｜ 关联认证：CKA-工作负载（rollout/rollback 是明列操作）/ —（方法论无考点，SRE 岗位面试高频）

## 学习目标

- 能解释为什么变更是头号故障源，以及渐进式交付如何把"一次大爆炸"切成"一串可控的小步"
- 能设计一份金丝雀发布方案：批次划分、每批判定指标、推进/暂停/回退判据
- 能用"影响面 × 可回滚性 × 可观测性"给变更定价，并据此制定分级评审标准与冻结窗口
- 能组织一次 rollback 演练并度量"回退恢复时间"，解释为什么没演练过的回滚等于没有回滚
- 能把错误预算当作货币，与产品方谈"发布速度 vs 可靠性"，而不是靠嗓门或资历

## 1. 变更是头号故障源

Google SRE Book 给过一个被反复引用的统计：**约 70% 的生产事故由变更引发**（第 3 章）。这与你的排障直觉一致——"昨天改了什么"永远是排障的前三个问题（第 3 章事件管理）。但结论不是"少发版"：不发版的系统同样在退化（CVE 累积、版本差拉大、被迫一次性大升级的利滚利）。**发布工程的正确目标：不是把变更压到最少，而是把单次变更的风险压到最小，从而允许高频发布**。变更风险不会消失，只会换形态：

| | 大爆炸式发布 | 渐进式发布 |
|---|---|---|
| 发现问题时刻 | 全量故障后 | 1% 流量的错误率异常时 |
| 影响用户数 | 全部 | 1%~5% |
| 回退成本 | 紧急回滚 + 可能的数据修复 | 关掉入口，旧版本从未下线 |
| 发布频率 | 被恐惧压制，越来越低 | 风险小才敢高频，越来越快 |

渐进式交付的本质是**用观测成本（每批多等 10 分钟）换爆炸半径（从 100% 缩到 1%）**——这是本章所有内容的主线。

## 2. 渐进式交付：蓝绿、灰度与金丝雀

### 2.1 三种形态对比

| | 蓝绿（Blue-Green） | 灰度（按人群/比例） | 金丝雀（Canary） |
|---|---|---|---|
| 切换单位 | 整套环境 | 用户分群（内部→VIP→1%→10%） | 流量比例逐批放大 |
| 资源/回退 | 2 倍资源；切回旧环境，秒级 | 视分组而定；关分组，秒级 | 只多 1~2 副本；缩掉金丝雀，秒~分钟 |
| 判定依据 | 冒烟通过即可切 | 分组行为/指标对比 | SLI 对比（02 章的输出） |
| 典型场景 | 中小规模、可双倍资源 | 需要按人群放量（地域、白名单） | 大流量在线服务的默认姿势 |

三者不互斥：一次发布可以"先金丝雀看指标，再按人群灰度，最后全量"——本质都是**控制新版本接触流量的速率**。

### 2.2 金丝雀批次设计（含判定盲区）

```
新版本流量占比
100% ┤                              ┌──────
 50% ┤                    ┌──25%────┘
  5% ┤          ┌─────────┘
  1% ┤  ┌───────┘
  0% ┼──┘
     └──┬────┬────────┬────────┬───────────→ 时间
      批次1  批次2    批次3     批次4(全量)
     观察10m 观察20m 观察30m
        │     │       │   判定：SLI 达标 → 推进；越界 → 暂停；失败 → 一键回退
```

批次设计的三个要素：

1. **观察窗口 ≥ 最慢 SLI 的收敛时间**：延迟类 SLI 用长窗口（如 10m rate）才稳，窗口太短会漏掉慢故障（连接池缓慢泄漏、缓存逐出抖动）。
2. **判定指标就用 02 章的 SLI**：新版本批次的 5xx 率、P99 延迟、业务成功率，与旧版本批次**同屏对比**，而不是与历史均值对比——同屏才能剔除全局因素（正好赶上大流量高峰）。
3. **回退判据预先写死**：例如"金丝雀批次 5xx 率 > 旧批次 3 倍且持续 2 个采样周期 → 回退"。当场讨论"这个异常要不要紧"时，用户正在替你付学费。

工具侧：GitOps 仓库的多环境晋升（test → staging → prod 的 overlays 结构）与"人工 MR 才进 prod"的晋升策略，在 [07-cd-gitops/03 §2~§3](../07-cd-gitops/03-delivery-platform.md) 已按工具链落地；Flagger / Argo Rollouts 可以把"批次推进 + 指标判定 + 自动回退"整段自动化（延伸阅读有链接）。本章先把手工流程走通——自动化的是流程，不是判断力。

最后一个常被忽略的判定盲区：**判定必须看 SLI，不能看 Pod Ready**。实战演练里会故意部署一个"应用端点全 500、但 /healthz 探针依旧 200"的坏版本——它照样 Ready、照样接流量，只有客户端指标能揭穿它。这就是 02 章"SLI 从用户视角出发"的发布场景版。

## 3. 冻结窗口与变更日历

### 3.1 冻结窗口的分级（经济学：冻结期故障代价被放大，所以付"延迟发版"的成本）

| 级别 | 触发条件 | 限制范围 | 豁免 |
|------|---------|---------|------|
| 常规冻结 | 周五下午、节假日前 | 非紧急变更不发 | 安全修复、P1/P2 故障修复 |
| 大促冻结 | 双 11、大促前 1~2 周 | 全部业务变更 | 大促专项变更（单独评审通道） |
| 重保冻结 | 重大活动、监管检查 | 含基础设施与配置 | 经 VP 级审批的清单内变更 |

冻结与错误预算（02 章）是一对工具：**预算告急 → 局部冻结；预算充裕 → 放开节奏**，都比一刀切聪明。

### 3.2 变更日历与唯一入口

- 所有进入生产的变更必须登记在**统一的变更日历/工单**里——"谁、什么时间、改什么、影响哪些服务、怎么回退"。散落在群里和口头上的变更无法审计，故障时也回答不了"昨天改了什么"。
- **冲突检查**：同一天对同一依赖（网关、数据库、公共库）的多处变更要错峰——两个各自无害的变更叠加出故障，是经典的复合事故。
- 豁免要留痕：紧急修复走绿色通道，事后补登记与复盘——豁免权不豁免记录。

## 4. 变更评审与风险定价

### 4.1 风险定价公式

对任一变更问三个问题，各打 1~3 分，乘起来就是风险分：

```text
变更风险 ≈ 影响面 × 可回滚性 × 可观测性
  影响面：核心链路？全量用户？还是有损可降级？
  可回滚性：能一键回退吗？回退会不会丢数据（schema 变更）？
  可观测性：回退判定指标是否已上线？多久能看出问题？
```

三项是**乘法**：任何一项趋近 0（比如不可回滚的 schema 变更），整体风险都趋于无穷——此时评审的重心不再是"要不要发"，而是"怎么把它拆成可回滚的小步"（4.4 节）。

### 4.2 变更分级与评审要求

| 级别 | 典型变更 | 评审 | 发布方式 | 通知 |
|------|---------|------|---------|------|
| P0 | 数据库 schema、网络架构、认证体系 | 架构评审 + 演练验证 + 双人执行 | 预演环境全流程 + 分批灰度 | 全员 + 干系方 |
| P1 | 核心服务功能性变更 | 代码评审 + 变更单评审 | 金丝雀 + 自动回退判据 | 相关团队 |
| P2 | 边缘服务、配置开关 | 代码评审 | 常规滚动发布 | 所在团队 |
| P3 | 文案、样式、内部工具 | 自助 | 直接发布 | — |

### 4.3 评审清单（每张变更单必答）

1. 这次变更想解决什么？不发的代价是什么？
2. 影响哪些服务与用户？怎么验证影响面判断是对的（依赖清单/调用链）？
3. 怎么回退？回退需要几分钟？回退后数据一致吗？
4. 出问题时**看哪个指标**、多长时间能看出异常？（答不出 = 没有可观测性 = 不许发）
5. 最坏情况下用户看到什么？有没有降级开关（feature flag 直接关掉新逻辑）？

其中 flag 与金丝雀是两条正交防线：金丝雀控"多少流量接触新代码"，flag 控"新代码里的逻辑开不开"。上线后关 flag 是秒级回退，比回滚镜像快一个量级——代价是代码里会积累需要定期清理的开关。

### 4.4 拆解不可回滚变更的标准手法

以最典型的数据库加字段为例，把一次 P0 拆成四次可回滚的 P1~P2：

```text
第 1 次：只加可空列（对旧代码不可见，回退 = 删列）        → 低风险
第 2 次：应用双写（新列与旧列同时写，读仍走旧列）          → 可观测、可关
第 3 次：灰度读切换（按人群/百分比从新列读，对比校验）     → 金丝雀判定
第 4 次：删旧列（稳定一个观察周期后再做，单独评审）        → 收尾
```

每一步之间隔着观察期，任何一步出问题都只回退那一步。"不可回滚的大变更"几乎总能这样拆；拆不动的，才是真正的 P0。

## 5. rollback：演练出来的能力，不是文档里的承诺

回退能力三要素，缺一不可：**产物可回退**（镜像按 digest 保留、配置在 Git 里有前一 revision、schema 双向兼容）；**路径可执行**（回退命令在 runbook 里，第 4 章，值班者在告警压力下不用查文档）；**能力被验证**（没跑过的回滚脚本第一次真实执行一定出问题——权限、镜像保留策略、缓存失效，总有一环在暗处烂掉）。

rollback 演练设计（与第 5 章混沌工程同一方法论，只是注入的故障换成"新版本有缺陷"）：

| 演练项 | 频率 | 通过标准 |
|--------|------|---------|
| 镜像回退（rollout undo / 上一 digest 重新部署） | 每月 | 从决定回退到 SLI 恢复 ≤ 5 分钟（含金丝雀摘除） |
| 配置回退（Git revert + 同步） | 每月 | revert 合并到生效 ≤ 10 分钟 |
| 数据回退（PITR 到变更前位点） | 每季度 | 恢复用时与数据损失符合 RTO/RPO 声明（第 7 章） |
| 降级开关（关 flag） | 随每个 flag 上线验证 | ≤ 1 分钟生效，且验证过"关掉后行为正确" |

度量口径要固定：**TTR（time to restore）从"决定回退"起算，到"SLI 回到 SLO 内"止**——审批、找镜像、等滚动完成全部计入。演练报告进复盘（第 4 章模板），超时项变成行动项。

## 6. 谈判桌：发布速度 vs 可靠性

产品方要"周五下午上大功能"，工程团队说"风险太高"——这类对话如果靠嗓门或资历裁决，说明缺少共同货币。**错误预算（02 章）就是那个货币**：

| 产品方说 | 工程方的预算语言 |
|---------|----------------|
| "这周必须上，不能再拖" | "当前预算剩余 40%。可以上，但按金丝雀流程走完全程需要 2 小时观察期；若中途烧穿预算，按 SLO 文档冻结到月底——这个代价你接受吗？" |
| "你们太保守了，别人一天发三次" | "别人一天发三次的前提是单批 1% 金丝雀 + 自动回退。给我们两个迭代把渐进交付建起来，之后一天发五次都行——速度是工程能力，不是胆量" |
| "先全量上了再说，出问题再改" | "全量故障一次按 30 分钟算，烧掉 70% 月度预算，接下来三周都要冻结。分四批灰度多花的 1 小时，是本月最便宜的一笔保险" |

三个谈判要点：**把风险翻译成预算数字**（不说"很危险"，说"这一把最多烧掉多少分钟错误预算、烧完之后冻结期多长"）；**区分"慢"与"稳"**（拒绝的是无观测的全量，不是速度本身，给出通往高频发布的工程路径）；**预算充裕时主动提速**（大量结余说明目标太松或投入过度，该由工程方主动提出放开节奏或收紧目标——货币要流通才有价值）。

## 实战演练：手工金丝雀 + 限时回退

环境：kubeadm 集群（自带清单，不依赖第 5 章环境）。全程约 40 分钟，目标：走完"基线 → 金丝雀 → 坏版本 → SLI 判定 → 回退"的完整循环并度量 TTR。

### Step 1 前置：快照 + 部署 stable 与流量发生器

前置动作：[本地Windows] VMware 先给 VM 打快照 `before-release-lab`（scripts/README.md 的快照策略）。

```yaml
# [master] release-lab.yaml —— stable(2 副本) + 共享 Service + 流量发生器
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
  labels: { app: web, track: stable }
spec:
  replicas: 2
  selector:
    matchLabels: { app: web }
  template:
    metadata:
      labels: { app: web, track: stable }
    spec:
      containers:
        - name: podinfo
          image: docker.io/stefanprodan/podinfo:6.7.6
          readinessProbe: { httpGet: { path: /healthz, port: 9898 }, periodSeconds: 5 }
          resources: { requests: { cpu: 10m, memory: 16Mi }, limits: { memory: 64Mi } }
---
apiVersion: v1
kind: Service
metadata:
  name: web
spec:
  selector: { app: web }        # stable 与后续 canary 共享同一入口
  ports: [{ name: http, port: 9898 }]
```

```bash
# [master] 应用 stable+Service，再起一个持续打流量的 Pod（同时充当测量探针）
kubectl apply -f release-lab.yaml
kubectl run loadgen --image=docker.io/busybox:1.36 -- sh -c 'while true; do wget -q -O /dev/null http://web:9898/; sleep 0.2; done'
kubectl get deploy web && kubectl get pod loadgen
```

### Step 2 基线：客户端口径的 SLI

```bash
# [master] 在 loadgen 内统计 300 次请求成败——这就是 02 章"请求式 SLI"的客户端实现
kubectl exec loadgen -- sh -c \
  'ok=0; bad=0; for i in $(seq 1 300); do wget -q -O /dev/null http://web:9898/ && ok=$((ok+1)) || bad=$((bad+1)); done; echo "ok=$ok bad=$bad"'
```

预期：`ok=300 bad=0`。记下这个测量脚本——它是整个演练的"SLI 探针"。

### Step 3 上金丝雀：1 副本承载 1/3 流量

```bash
# [master] 部署 canary（同镜像模拟"新版"；坏行为在 Step 4 由运行时注入）
kubectl apply -f - <<'EOF'
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web-canary
spec:
  replicas: 1
  selector:
    matchLabels: { app: web, track: canary }
  template:
    metadata:
      labels: { app: web, track: canary }
    spec:
      containers:
        - name: podinfo
          image: docker.io/stefanprodan/podinfo:6.7.6
          readinessProbe: { httpGet: { path: /healthz, port: 9898 }, periodSeconds: 5 }
          resources: { requests: { cpu: 10m, memory: 16Mi }, limits: { memory: 64Mi } }
EOF
kubectl get pods -l app=web -L track -w   # 看到 canary Running/Ready 后 Ctrl-C
```

重复 Step 2 的测量：仍应 `bad=0`（新副本本身是好的）。

### Step 4 制造"坏版本"：故障注入 + 观测

podinfo 自带运行时故障注入 API：开启后**应用端点全部返回 500，而 /healthz 依旧 200**——即"坏版本照样 Ready"，正是 2.2 节说的判定盲区。

```bash
# [master] 只对金丝雀 Pod 开启故障注入（podinfo 镜像内置 curl）
CANARY=$(kubectl get pod -l track=canary -o jsonpath='{.items[0].metadata.name}')
kubectl exec "$CANARY" -- curl -s -X POST localhost:9898/fault_injection/enable
kubectl get pods -l track=canary   # 注意：它仍然是 Running/Ready —— Ready ≠ 健康
```

再跑 Step 2 的测量。预期 `bad≈100`（300 次请求约有 1/3 落到金丝雀）。对照 02 章的公式：全站错误率 ≈ 33%，是 99.9% SLO 允许错误率的 330 倍——按第 5 节演练表的通过标准，此刻应立即回退。

### Step 5 回退并度量 TTR

```bash
# [master] 回退 = 摘除金丝雀（旧版本从未下线，这正是渐进式交付的回退红利）
date +%T; kubectl delete deploy/web-canary
kubectl get pods -l app=web -w    # canary Pod 消失、stable 仍在 → Ctrl-C
```

再跑一次 Step 2 测量确认 `bad=0`。从 `delete` 到测量恢复为 0 的总时长就是本次 TTR（含金丝雀摘除，应 < 1 分钟）。对照回退判据"预先写死"的要求：如果这个决定要等一次例会来拍板，TTR 就不是分钟级了。

### Step 6（进阶）镜像回退演练：rollout undo 计时

```bash
# [master] 给 stable 人为发一个坏版本（不存在的 tag），再计时回退
kubectl set image deploy/web podinfo=docker.io/stefanprodan/podinfo:6.7.x-broken
kubectl rollout status deploy/web --timeout=30s || true   # 预期超时：新 Pod ImagePullBackOff
date +%T; kubectl rollout undo deploy/web; kubectl rollout status deploy/web; date +%T
```

预期：`rollout undo` 后旧版本 Pod 恢复，服务不中断（滚动更新的 maxUnavailable 语义在保护你）。两个数字写进演练笔记：金丝雀摘除的 TTR vs 镜像回退的 TTR——前者秒级、后者分钟级，这就是"降级开关 > 金丝雀摘除 > 镜像回滚"的回退速度层级。清理：`kubectl delete -f release-lab.yaml` 与 `kubectl delete pod loadgen`（或还原 VMware 快照）。

## 常见坑

| 症状 | 原因 | 解法 |
|------|------|------|
| 金丝雀指标一切正常，全量后爆炸 | 判定指标看了 Ready/CPU，没看 SLI；或 1% 批次的样本量太小，比例型缺陷（如 0.5% 失败率）未达统计显著性 | 判定指标 = 02 章 SLI；小批次阶段延长观察窗或放大该批请求采样 |
| 回退时才发现旧镜像已被清理 | 镜像保留策略只留最新 N 个，"最新"全是坏版本 | 保留策略按"最近发布的 digest + 当前运行中"双维度；演练表加"上一版本镜像可拉取"检查 |
| rollout undo 后问题依旧 | 坏变更不止镜像：ConfigMap/CRD/schema 同步改了，undo 只回滚了 Deployment | 变更单要求列出全部伴生对象；回退演练必须覆盖配置与数据（5 节表） |
| 冻结期照样出变更事故 | 豁免通道无门槛、配置平台绕过变更日历、定时任务（CronJob）没人意识到也是变更 | 豁免事后必补单+复盘；变更平台收敛一切入口；把定时任务纳入变更清单 |
| 发布平台自动推进把坏版本铺满 | 自动化只做了"推进"，没做"判定失败即回退" | 自动化的完整闭环是 推进+判定+回退 三件事；只自动推进等于放大事故速度 |

## 自测

<details><summary>1. 为什么说风险定价三项（影响面×可回滚性×可观测性）用乘法而不是加法？</summary>

加法允许互补：影响面极大但可观测性满分，总分还能被拉平。乘法刻画真实约束——任何一项趋近于零，整体风险都趋于无穷：不可回滚意味着出问题后没有退路，影响面再小也可能是永久性损伤；不可观测意味着连"该不该退"都无法判断。乘法逼着评审把补短板当第一动作（先让变更可回滚、可观测，再谈影响面控制），而不是凑总分。
</details>

<details><summary>2. 金丝雀批次是 1%→5%→25%→100% 还是 1%→50%→100%？给出你的权衡框架。</summary>

权衡三个变量：单批爆炸半径（越小越安全）、统计显著性（每批样本够多才能检出比例型缺陷）、发布总时长（批次越多越慢）。大流量服务单批 1% 已有足够样本，可走 1/5/25/100；小流量服务 1% 一小时只有几十个请求，判定毫无意义，应放大首批比例或改用"内部账号→白名单→全量"的人群灰度。框架：先算"每批最小样本量能否在观察窗内支撑判定"，再定批次——而不是抄别人的百分比。
</details>

<details><summary>3. feature flag 与金丝雀都能"快速撤销"一个发布，它们分别撤销的是什么？为什么说要正交使用？</summary>

金丝雀撤销的是"新版本接触流量的比例"（缩掉新副本，旧版本还在跑）；flag 撤销的是"新代码中某段逻辑是否生效"（代码还在跑，行为切回旧路径）。正交的原因：一个新版本里往往有多个变更点，金丝雀只能整体退，flag 能精确关掉出问题的那一个，秒级生效且不用重新调度 Pod。组合用法：金丝雀控流量比例，批次内异常先关 flag，flag 覆盖不了的（新 schema、新依赖）才退整批。
</details>

<details><summary>4. 数据库"加一个非空字段并回填"为什么是 P0？如何把它拆成可回滚的小步？</summary>

直接加非空列要求瞬间完成默认值回填（大表锁表）、旧代码写入必失败、回退要删列丢数据——可回滚性趋近于零，乘法定价下风险无穷。拆法：①加可空列（旧代码无感）；②双写新旧列、读仍走旧列；③灰度读切换+对比校验；④回填任务分批限速跑；⑤观察一个周期后改非空+删旧列（单独评审）。每步可独立回退，P0 摊薄成五个 P1~P2。
</details>

<details><summary>5. 产品方质疑："你们又要冻结两周，大促前需求都发不了，损失谁负责？"请用预算语言重构这场对话。</summary>

把"损失谁负责"的对立换成共同货币：冻结不是纪律惩罚，是预算分配——大促期间单分钟故障的代价（GMV、赔付、舆论）被放大，同样的错误率烧掉多得多的"钱"。然后给选项而非单方面决定：a) 非核心变更走大促专项通道，变更单+灰度放行；b) 核心变更预算内允许，但占用的错误预算从大促保护期预扣，烧穿则严格冻结；c) 不可延迟的需求用 flag 上线默认关闭，大促后再放量。三个选项都把"风险多大、谁付、怎么付"摆上桌面——这正是第 6 节"货币要流通"的含义。
</details>

## 靶场联动：靶场是这些方法论的练习场

靶场（`scripts/faults/`）的每个 break 脚本本质上都是一次"没走变更流程的坏变更"。练习姿势：抽一个 break 脚本，先按 4.3 节清单给它补一张变更单（影响面怎么查、回退命令是什么、看哪个指标），再注入扮演"发布事故"，用第 3 章的时间线记录法测量自己的 TTR，最后按第 4 章模板写迷你 postmortem。走完几次，回退动作会从"翻文档"变成"肌肉记忆"——这正是 rollback 演练要练的东西。
