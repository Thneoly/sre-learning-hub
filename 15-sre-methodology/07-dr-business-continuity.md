# 07 · 灾备与业务连续性：RTO/RPO 与"备份 ≠ 可恢复"

> 模块：15-sre-methodology ｜ 建议时长：4 小时 ｜ 关联认证：CKA-集群架构（etcd backup/restore 是明列考点）/ —（方法论无考点，架构岗面试高频）

## 学习目标

- 能准确定义 RTO 与 RPO，说明各自由架构中的哪个环节决定，并主导一次"业务目标 vs 技术现实"的对账
- 能解释为什么"备份成功"不等于"可恢复"，并设计一套覆盖各数据层的 restore drill（恢复演练）体系
- 能对比冷备/热备/同城双活/异地灾备/多活的 RTO、RPO、成本与复杂度，为给定业务选层级
- 能把灾备与 SLO/错误预算（02 章）的关系讲清楚：前者管黑天鹅，后者管日常损耗
- 能写出一份业务连续性计划（BCP）骨架：决策链、通讯树、依赖清单与演练节奏

## 1. RTO 与 RPO：用两个数字定义灾备目标

### 1.1 时间轴上的两个缺口

```
                故障发生                 恢复完成
───────────────────┬────────────────────────┬──────────────→ 时间
        ◄──────────┴─────────►              │
            RTO（Recovery Time Objective）   │
            服务中断多久能恢复               │
                    │                        │
                    ◄────────────────────────┴───►
                        RPO（Recovery Point Objective）
                        数据损失多大：恢复点回到故障前多久
```

- **RTO（恢复时间目标）**：从服务不可用到恢复的时长上限。它考验**恢复路径**：预案、自动化、人。
- **RPO（恢复点目标）**：恢复后允许丢失的最近数据量（用时间表示）。它考验**数据复制/备份频率**：异步复制延迟 30s 就是 RPO≈30s；每日一次备份就是 RPO≤24h。

两个数字是**承诺**，不是愿望。承诺前必须能回答：凭什么能做到？（备份几分钟一次？切换脚本演练过吗？）

### 1.2 数字由谁决定

| 目标 | 决定因素 | 典型手段 |
|------|---------|---------|
| RPO = 0 | 同步复制（写双份成功才返回） | 同城同步复制、共享存储 |
| RPO = 秒~分 | 异步复制 | 半同步 MySQL、跨 Region 异步复制 |
| RPO = 小时 | 定时备份 | etcd snapshot、数据库全备+增备 |
| RTO = 分钟 | 自动切换 | 多活 + 健康检查自动摘除（SLO 体系管的事） |
| RTO = 小时 | 半自动 | 热备 + 人工决策切换 |
| RTO = 天 | 冷备 | 备份 + 采购机器 + 手工恢复 |

推论：**RPO 越小越花钱在"数据链路"，RTO 越小越花钱在"架构与演练"**。预算有限时先保 RPO（数据丢了补不回来），再压 RTO（宕久了还能修）。

### 1.3 对账：业务目标与技术现实的碰撞

RTO/RPO 的设定不是技术拍脑袋，是一张三方对账表（业务方出容忍度、财务出损失估算、工程出成本）：

```text
<!-- 对账表示例（每行一个业务系统，季度评审一次） -->
系统          业务要求        技术现状           差距动作
─────────────────────────────────────────────────────────
交易核心      RTO 15m / RPO 0   双活+同步复制       达标，持续演练
用户画像      RTO 4h  / RPO 1h  异步复制(延迟~10s)  达标
报表/数仓     RTO 3d  / RPO 24h 每日备份到 OSS      达标
新业务 X      RTO 30m / RPO 0   单机房+每日备份     不达标：
                                                RPO→上异步复制(2 周)
                                                RTO→先 4h 再压(2 月)
```

对账的价值在于把"差距"变成**有优先级的账**：RPO 从 24h 压到 10s 是两个数量级的投入，值不值，由业务损失估算来回答。灾备层级的选择见第 3 节。

### 1.4 与 SLO 的分工：日常损耗 vs 黑天鹅

SLO/错误预算（02 章）管理**常态故障**：单机宕机、慢查询、发布事故——发生频率足以用统计描述，预算可以定价。灾备管理**灾难**：整个机房/Region 失联、勒索软件加密全量数据——发生频率低到无法进入预算体系，但单次损失足以危及业务存续。两套体系共用同一套观测与事件管理设施（第 3 章），但目标、演练方式、决策链完全不同。

## 2. 备份 ≠ 可恢复：restore drill 是唯一证据

### 2.1 备份链路的四步与监控盲区

```text
产生 ──► 传输/存储 ──► 保留/清理 ──► 恢复
 [有监控]  [有告警]     [有策略]      [通常从没验证过]
（任务成功)（上传失败）  （误删/过期）  （真实恢复时才发现备份是坏的）
```

经典事故形态：备份任务每晚 02:00 都"成功"，两年后误删库要恢复时才发现——快照加密损坏、恢复脚本依赖的镜像源早下线、备份账号权限过期、"每日备份"实际只保留了 3 天。**备份是幻觉，恢复才是能力**。

### 2.2 restore drill 的设计

原则：**定期、真实、有通过标准**。每次演练验证四件事——找得到（目录/账号/密钥可访问）、读得出（校验和/元数据正常）、恢复得了（真的拉起服务）、恢复得对（数据校验通过）。

| 演练对象 | 频率 | 方式 | 通过标准（示例） |
|---------|------|------|-----------------|
| etcd 快照 | 每月 | 恢复到临时集群 | 集群启动且能 `get` 到关键对象 |
| 数据库 PITR | 每季度 | 恢复到隔离实例 | 恢复到指定位点，抽样行数/校验和一致 |
| 对象存储 | 每季度 | 跨账号/跨 Region 副本拉回 | 清单对账 + 随机对象可读 |
| 配置/IaC 仓库 | 每月 | 从 git+state 重建一套 staging | 与生产拓扑 diff 为空 |
| 整机房切换 | 每年 1~2 次 | GameDay 全链路 | 实测 RTO/RPO 落在承诺内 |

两个必答的设计问题：**恢复到哪**（生产内就地恢复 = 二次伤害风险，应恢复到隔离环境验证后再切流量）；**谁有权做**（演练账号的权限要和生产恢复时的真实路径一致——用演练专用的过高权限，灾难时照样卡在权限上）。

演练产物是三行结论：实测 RTO / 实测 RPO / 与承诺的差距。差距进第 4 章的复盘模板变行动项。这与第 5 章混沌工程是同一方法论——稳态假设换成"RTO/RPO 承诺成立"，注入的故障换成"生产数据面整体消失"。

### 2.3 数据层的具体抓手

- K8s 控制面：etcd snapshot（CKA 明列考点，完整实操在 [05-cka/04 · etcd 备份与恢复](../05-cka/04-etcd-backup-restore.md)——TLS 参数、恢复到新目录、四种验证手法）。
- 数据库：物理备份 + binlog 增量的 PITR 组合，决定 RPO 的其实是 binlog 保留策略（[mysql/02 · 备份恢复与主从复制](../13-middleware/mysql/02-backup-replication.md)）。
- 云上数据：快照、跨 Region/跨账号复制、恢复演练的云侧形态在 [16-cloud/05 · 云上容灾与备份](../16-cloud/05-cloud-dr-backup.md) 展开。

## 3. 容灾层级：从冷备到异地多活

### 3.1 层级菜单

| 层级 | RTO | RPO | 成本 | 复杂度 | 适用 |
|------|-----|-----|------|--------|------|
| 冷备 | 天级 | 24h+ | 低（只存备份） | 低 | 边缘系统、可重算数据 |
| 热备（standby） | 小时级 | 分钟级（异步复制） | 1.5~2 倍 | 中 | 大多数生产系统 |
| 同城双活 | 分钟级 | 0（同步复制） | 2 倍 | 中高 | 核心交易链路 |
| 异地灾备（两地三中心的"第三中心"） | 小时级 | 分钟级 | 高 | 高 | 抗 Region 级灾难 |
| 异地多活 | 分钟级 | 秒级 | 最高 | 极高 | 超大规模/合规要求 |

选型逻辑就是第 1.3 节的对账：先问业务要什么 RTO/RPO，再查这张表付对应的钱。**同城双活抗机房级故障，异地灾备抗城市/Region 级故障**——前者是性价比最高的容灾（AZ 间延迟 1~3ms，见 [16-cloud/01 §2](../16-cloud/01-cloud-fundamentals.md)），后者贵一个数量级但只保核心业务。

### 3.2 两地三中心：经典拓扑

```
            城市 A（生产）                     城市 B（异地灾备）
   中心1 ◄────1~3ms────► 中心2                中心3（冷/热备）
   ┌─────────┐  同步复制  ┌─────────┐          ┌──────────┐
   │ 全量服务 │◄═════════►│ 全量服务 │  异步复制 │ 备份+核心 │
   │ 双活承载 │  RPO=0    │ 双活承载 │ ────────►│ 子集 standby
   └─────────┘           └─────────┘  RPO=分钟级└──────────┘
        └──────────┬──────────┘
            全局负载均衡/DNS 按健康度分流
        城市A级故障 → 流量全切中心2（分钟级，双活红利）
        城市A级+中心2 同时失联 → 人工决策切换中心3（小时级）
```

三个工程要点：**流量入口**要能按健康度全局切换（GTM/智能 DNS），否则"双活"只是两套各自等死的系统；**数据分层**——核心库同步复制、普通库异步、可重算数据只做备份，全量同步的成本没人付得起；**切换决策**——双活故障自动切，异地切换必须人拍板（异步复制意味着切过去要丢数据，丢多少、值不值，机器答不了，见第 4 节决策链）。

### 3.3 脑裂：双活的暗面

双机房互相同步时若心跳线断而两边都活着，两边都可能认为"对方挂了我该接管"——数据两边各自写入，合并时冲突无法自动消解。防线：**仲裁机制**（第三方站点/quorum：etcd 的多数派就是这么设计的，[04-k8s-fundamentals/01](../04-k8s-fundamentals/01-why-kubernetes.md) 讲过为什么 3 节点比 2 节点安全）；**fencing**（接管前先确保旧主真的被隔离/下电，存储层 SCSI reservation、云上安全组一键掐断）；**写路径单点化**（多数双活实际是"双跑单写"：两边都有算力，写只走一侧，切写需要决策）。

## 4. 业务连续性计划（BCP）：系统之外的部分

灾难发生时先瘫的往往是组织而不是机器。BCP 至少回答四个问题：

1. **谁宣布进入灾难状态**：预先授权（如"核心服务全失联 30 分钟，值班 IC 可直接宣布切异地"），而不是层层请示——每级请示都在消耗 RTO。与第 3 章事件管理的 IC 角色衔接，灾难场景下 IC 的权限要更大、决策表要更短。
2. **通讯树怎么走**：对内（谁在 15 分钟内被呼叫、备用通讯渠道——办公 IM 本身可能就在故障域里）；对外（客户公告模板、客服话术、监管报备时限）。
3. **依赖清单**：上游（支付通道、短信、DNS 服务商）、下游（哪些业务依赖我）、共用设施（办公网、VPN、堡垒机）。**依赖的依赖**才是真盲区：机房断电时你的服务器没事，但运维通道全在同一个机房。
4. **人员冗余**：每个关键恢复步骤至少两人会做（runbook 的 owner + backup，第 4 章），恢复脚本不依赖某个人的笔记本。

BCP 的维护节奏：每次架构大改后更新依赖清单；每年一次全链路演练（3.1 表的最后一行）；演练后修订决策表——**没被演练过的 BCP 是科幻小说**。

## 实战演练：给练习集群做一次恢复能力审计

环境：kubeadm 单 master 集群 + 一台装 Docker 的 VM（mysql 演练可选）。全程约 45 分钟。目标：走完"备份 → 验证 → 纸面推演 → 对账"四步，产出一份迷你灾备审计报告。

### Step 1 etcd 快照：把 CKA 考点变成灾备动作

```bash
# [master] 建备份目录并执行快照（完整 TLS 参数解析见 05-cka/04 第 2 节）
sudo mkdir -p /opt/backup && cd /opt/backup
sudo ETCDCTL_API=3 etcdctl snapshot save snap.db \
  --endpoints=https://127.0.0.1:2379 \
  --cacert=/etc/kubernetes/pki/etcd/ca.crt \
  --cert=/etc/kubernetes/pki/etcd/server.crt \
  --key=/etc/kubernetes/pki/etcd/server.key
```

```bash
# [master] 验证"读得出"：元数据可读且 TOTAL KEYS 非零（status 只需要文件本身）
sudo ETCDCTL_API=3 etcdctl snapshot status snap.db -w table
```

预期：一张表，TOTAL KEYS 几千起，TOTAL SIZE 几十 MB。**把快照拷出本机**（`scp` 到 VM 或本地）——灾备第一原则：备份与生产同机 = 没有备份。

### Step 2 恢复推演：不真删集群，但把路径走到一半

完整的"恢复到新目录 → 改静态 Pod → 集群读回旧数据"流程在 [05-cka/04 第 3 节](../05-cka/04-etcd-backup-restore.md) 演过。这里做灾备视角的推演，回答三个问题并写进审计报告：

```text
Q1 恢复的依赖链：etcdctl 在哪台机器？PKI 证书从哪来？kubeadm 版本？
   （生产答案应该是：恢复 runbook 里写明，且恢复镜像/证书有异地副本）
Q2 恢复之后应用层怎么办？etcd 恢复=控制面回来，业务 Pod/数据还要：
   PVC 里的数据、数据库、ConfigMap 之外的配置（这些 etcd 快照救不了）
Q3 实测过吗？上次演练日期？谁会做？backup owner 是谁？
```

第 2 问是本步的关键认知：**etcd 快照只覆盖"声明"不覆盖"数据"**——灾备是分层的（控制面/无状态负载/有状态数据/配置），每层要有自己的恢复手段与演练。

### Step 3 有状态层：MySQL 的 RPO 账

（可选，集群内有 MySQL 实验环境时）按 [mysql/02 第 1 节](../13-middleware/mysql/02-backup-replication.md) 做一次全备 + 记录 binlog 位点，回答：当前配置下误删一张表，最多丢多少数据？（RPO = 备份间隔？还是有 binlog 就能到秒级？——PITR 的位点机制决定了只要 binlog 齐全，RPO 可以压到"最后一笔事务"）

### Step 4 对账表：给学习中心环境填一张

```text
<!-- 审计报告（mini 版），完成后存 ~/learning-hub/docs/dr-audit-<日期>.md -->
对象          实测 RPO         实测 RTO          承诺    差距动作
k8s 控制面    依赖快照频率      Step2 推演路径     ？      定 cron 每日快照
业务数据      无备份/有 PVC     —                ？      评估 Velero
mysql(可选)   Step3 结论       未演练            ？      下季度 PITR 演练
```

两个收尾动作：把 etcd 快照加上 cron（每日一次、异地拷贝、保留 7 份——写进 cron 前先想清楚保留策略）；把"承诺"列留白拿去和"业务方"（这里是你自己扮演）对账——空白就是差距，差距就该有动作与期限。

清理：保留 `/opt/backup/snap.db`（下一课可用），删除拷出的临时副本。

## 常见坑

| 症状 | 原因 | 解法 |
|------|------|------|
| 灾难时备份恢复失败 | 备份只验证了"任务成功"，从未做过恢复演练 | 2.2 节 drill 体系：找得到/读得出/恢复得了/恢复得对 四连验证 |
| RPO 承诺秒级，实际丢了 20 分钟 | "异步复制"与"备份"混为一谈：RPO 由复制链路决定，不由备份频率决定 | 对账表区分复制（秒级 RPO）与备份（小时级 RPO+防误删）两条线 |
| 切换到灾备站后核心功能全挂 | 只演练了数据库切换，依赖的缓存/配置/密钥/网络端点没跟着切 | 依赖清单+全链路 GameDay；切换是"业务"不是"组件" |
| 异地机房设备常年未启用，切换时全坏 | 冷备不定期通电验证，硬件/镜像/证书悄悄过期 | 冷备也要月度巡检：机器可开机、镜像可拉、证书未过期 |
| 双活一机房失联，两边同时升主 | 心跳断联 + 无仲裁，脑裂双写 | 仲裁第三方/quorum + fencing，接管前先隔离对端 |
| 备份被勒索软件连同生产一起加密 | 备份与生产同账号同网段，权限一路通 | 备份跨账号+只写不可改（对象存储版本化/WORM），恢复演练覆盖"备份账号被攻陷"场景 |

## 自测

<details><summary>1. 为什么说"RPO 由数据链路决定，RTO 由恢复路径决定"？各举一个只影响其中一项的改造。</summary>

RPO 度量"数据丢多少"，由数据从生产落到副本的**时延与方式**决定：把每日备份改成半同步复制，RPO 从 24h 压到秒级，但如果切换要人工决策，RTO 不变。RTO 度量"多久恢复"，由**预案、自动化与演练**决定：把人工切换脚本化并演练达标，RTO 从 4h 压到 15m，但如果数据仍是每日备份，RPO 还是 24h。两条线独立投入——这正是对账表把它们拆成两列的原因。
</details>

<details><summary>2. 业务方要求"RPO=0"，你该问什么、说什么？</summary>

先问"丢一单的损失 vs 零丢失架构的差价"：RPO=0 意味着同步复制——写请求必须双机房（或双存储）落盘才返回，同城 1~3ms 延迟能接受，跨 Region 则延迟和可用性代价巨大（对端网络抖动直接拖慢本地写入）。再说明替代方案：秒级 RPO 的异步复制 + 对账补偿任务，对绝大多数业务"丢最后一秒"的期望损失远小于同步复制的长期成本。真要 RPO=0，给出边界：仅核心交易表走同步，其余分层处理。
</details>

<details><summary>3. 为什么异地切换必须人工决策而同城双活可以自动切？</summary>

同城双活是同步复制（RPO=0），自动切换不丢数据，误切的代价只是短暂抖动——自动化收益大于风险。异地是异步复制，切换意味着**主动放弃未复制完的数据**：丢多少（复制延迟）、值不值（业务损失估算）、要不要先尝试其他恢复路径（比如原地抢救主站），这些是业务权衡不是技术判断，机器没有授权也没有信息做这个决定。所以异地切换的自动化只做到"把决策所需数据（延迟、损失量、剩余选项）在一分钟内摆到人面前"。
</details>

<details><summary>4. etcd 快照恢复后集群"回来了"，灾备就完成了吗？还缺哪些层？</summary>

etcd 快照只恢复了**控制面声明**（Deployment/Service 等 API 对象）。还缺：①数据层——PVC 里的文件、数据库的数据，快照救不了；②集群外状态——负载均衡配置、DNS 记录、证书/密钥的轮转状态、节点上的本地配置；③接入层——客户端怎样找到新集群。分层的恢复手段与演练（控制面/无状态/有状态/配置）才是完整灾备；"集群对象都在"只是第一层过关。
</details>

<details><summary>5. 你的备份策略是"每日全备 + 保留 7 天"，误操作在事发第 8 天才发现。这个设计暴露了什么问题？怎么改？</summary>

保留期短于故障发现窗口，备份形同虚设：误删类"慢故障"的发现周期常以周计（报表对不上、归档被清）。改法分层：近线保留 7~30 天满足快速恢复，**归档层保留 90 天~1 年**（对象存储归档存储成本低一个量级）；关键数据用版本化/WORM 防覆盖；把"最远可恢复点"写进对账表当 RPO 的另一半——RPO 不只问"丢多少"，还问"能回到多久以前"。
</details>

## 靶场联动：靶场是这些方法论的练习场

本模块七章闭环：第 2 章定目标、第 3 章管日常故障、第 4 章沉淀知识、第 5 章主动注入、第 6 章管住变更、本章兜住灾难。靶场（`scripts/faults/`）里的故障都是"单组件级"，正好用来练分层恢复的判断：抽一个 break 脚本注入后，先问"这在灾备分层里属于哪一层？我的恢复手段是什么、演练过吗？"——把每次排障都当作一次微型的恢复演练，第 4 章的 runbook 就是这么积累出来的。更接近本章主题的玩法：挑一天，故意把 `/opt/backup/snap.db` 的恢复流程从头走一遍并计时，你会得到自己集群的实测 RTO——一个大多数团队从没测量过的数字。
