# 复盘不是追责会：把「谁的错」换成「系统为什么允许」

「这次故障到底是谁改的？」

复盘会上第一句话如果是这个，这份 postmortem 大概率还没动笔就死了。因为从这一刻起，在场每个人的输出目标，都从「还原真相」切换成了「自证清白」。

## 一、追责开始的那一刻，真相开始退场

先说机制，再谈文化。人有合理的自保本能：一旦预感被追责，信息输出会立刻收敛——「当时我以为」「我不确定是不是我改的」「日志我记得不太清了」。而根因恰恰藏在被隐藏的细节里，细节一收敛，复盘就退化成一场所有人配合演出的会。

所以**复盘的首要目标是改进系统，不是追责**。这不是道德姿态，是信息成本问题：你想要的数据锁在别人的恐惧里，就得先让人确信交出来是安全的。

Blameless 有两条默认假设，值得公开写进你的复盘制度，每次开会由主持人开场宣读：

1. 每个当事人都基于当时可得的信息，做了在其职责范围内合理的选择。换成你坐那把椅子，带着同样的监控水平和同样的交付压力，大概率做同样的事。
2. 要问「系统为什么允许这个错误造成故障」，而不是「谁犯了错」。人总会犯错，可靠系统在设计上就假定这一点。

SRE Book 第 15 章 Postmortem Culture 讲的就是这件事：无责的氛围，换的是当事人愿意交出那些对预防复发至关重要的细节。这条判据可以反着用——你们团队复盘会上出现过几次「其实我当时还发现了一个异常，但没敢说」？零次不代表没有，只代表不安全。

## 二、瑞士奶酪：故障是所有防御层的孔排成了一条线

系统性归因不是不给结论，而是给对层次的结论。业界常用的解释框架是瑞士奶酪模型【第三方转引，James Reason，1990】：每层防御都像一片有孔的奶酪，单片上的孔无害，事故是所有层的孔恰好排成一条直线。

拿一个构造典型案例拆开看。某天 14:05，某命名空间服务流量 100% 失败，SLI 跌到 0，持续 40 分钟。直接原因：有人把 Service 的 selector 值敲错，Endpoints 变空，流量无后端可转发。

「谁敲错的」——这只是奶酪上最后一片的孔。往前看，这条线是怎么排成的：

- 孔一：变更走人工 kubectl，没有流水线校验 selector 必须命中现存 label，敲错直接生效
- 孔二：Endpoints 空值没有专门告警，要等用户路径的 SLI 烧穿才知道，探测多花了 7 分钟
- 孔三：演练环境与生产共用同一套 YAML 手改习惯，同类错法早有前科

培训那个人、批评那个人，只堵最后一片奶酪的孔。孔一和孔二还开着，下一个人来排线，照样穿透。**把根因按在个人头上，是最省事也最先失效的改法。**

## 三、合格 postmortem 的骨架：七段，直接抄

模板直接抄。存放于 git 仓库 `docs/postmortems/`，一事件一文件：

```markdown
# Postmortem · INC-1024 Service 无后端导致访问失败

- 日期：2026-08-20 ｜ 撰写人：值班 SRE ｜ 状态：草稿/评审中/已结项
- 级别：SEV2 ｜ 持续：40 分钟（14:05–14:47）｜ 影响：fault-ep 命名空间 100% 流量

## 影响与 SLI 结算
- 用户影响：约 30% 门户请求失败
- SLO 结算：当日错误预算消耗 11.2%（阈值 1%/日），触发发版双人评审

## 时间线（只记事实与时间戳）
| 时间 | 事件 | 来源 |
|------|------|------|
| 13:58 | 变更：fault-web-svc 的 selector 被误改（事后从审计日志确认） | audit log |
| 14:05 | SLI 跌至 0，快火燃烧率告警 Firing | Prometheus |
| 14:07 | primary ack，定级 SEV2，IC 认领 | 值班频道 |
| 14:21 | 定位：svc selector 与 pod label 不匹配（describe 对比） | 排障记录 |
| 14:32 | 修复：selector 改回 app: fault-web | 变更记录 |
| 14:45 | SLI 回 100%，观察 2 分钟无复发，关闭 | Grafana |

## 根因（root cause）
Service selector 值被打错，Endpoints 为空，流量无后端可转发；
变更未经 CI 校验直接 kubectl apply。

## 促发因素（contributing factors，通常 2~4 条）
1. svc 变更走人工 kubectl，无流水线校验 selector 合法性
2. Endpoints 空值无专门告警，探测靠用户路径的 SLI（MTTD 7 分钟）
3. 演练环境与生产共用同一套 YAML 手改习惯

## 做得好的（把运气也写进来）
- 燃烧率告警 2 分钟内 page，无人工发现延迟
- IC/OL 分工保持，时间线完整
- 运气：故障落在午后低峰，未叠加晚高峰流量

## 做得差的
- 定位耗时 14 分钟，其中 9 分钟在看 Pod 自身（先怀疑应用后怀疑接线）
- 变更无回滚预案，靠现场推理修复

## 行动项（进 issue tracker，此处只引用编号 A1–A3）
```

三处写法纪律。

第一，**时间线只写何时发生了什么**，不写为什么、不写评价。评价混进时间线，下一个人就没法拿它对表复盘。

第二，「做得好的」小节要把运气显式写进来：这次没扩大，是因为变更恰好发生在低峰，还是因为二线恰好在线？near-miss 的价值就在这里——故障的学费已经预付，只是没发货。在模板里单列幸运因素这一行，是骨架之上的从业者加法【从业者判断】。

第三，时间线要能分解出可对比的指标：MTTD 是探测体系的成绩，MTTA 是值班体系的成绩，定位加修复是 runbook 与自动化的成绩。每次复盘把三段耗时记进表格，季度横比——这是可靠性工程有没有进步的最诚实答案。

## 四、根因的陷阱：写到「人为失误」就停，等于没写

最常见的翻车：根因栏写着「人为失误，操作时粗心」。**「人为失误」不是根因，是起点。**人失误是常数，你改不掉常数，只能改系统对常数的容忍度。

追问只有一句，连着问：系统为什么允许？为什么变更能绕过校验？为什么探测要 7 分钟？为什么没有回滚预案？每问一层，行动项就从「培训」往「工程」挪一层。

随手一个自查，在存复盘的仓库里跑：

```bash
grep -rn -e "人为失误" -e "粗心" -e "疏忽" docs/postmortems/
# 预期输出为空；命中的行落在根因/结论段，说明那份文档的根因分析停在第一层（仅行文提及该词不算）
```

定位根因时用证据说话的那条命令，也值得贴在时间线旁边当范例：

```bash
kubectl -n <namespace> describe svc <svc-name> | grep -A2 Selector
kubectl -n <namespace> get pods --show-labels
# 预期：selector 的 k=v 能在 Pod 的 labels 里原样找到；找不到即接线问题
```

一句话判死刑：**根因栏出现「人为失误」，行动项栏十有八九是培训类许愿。**

## 五、行动项：没有 owner 和期限的不叫行动项，叫许愿

合格行动项的四条硬标准，SMART 的运维版：

1. 单一 owner：一个人名，不是「我们组」
2. 有期限：具体到日期，「尽快」等于没有
3. 可验证：完成后能用命令、看板或流程证明
4. 分层投放：P0 立即做（本周），P1 本季度，P2 进 backlog 定期重审

伪行动项一眼识别，对照着改：

| 伪 | 真 |
|----|----|
| 加强监控 | 增加 Endpoints 空告警，owner 张三，8/27 前，验证表达式返回 0 条活跃 |
| 提高大家意识 | 9 月 onboarding 培训加入 svc 变更案例 15 分钟，课件链接入库 |
| 增加人手 | 拆成具体的自动化项后再谈人力 |

投放还要按防御层次分摊，避免全堆在预防：Prevent 问怎么让诱因不再发生（变更进 CI，流水线校验 selector），Detect 问再发生怎么更快发现（Endpoints 空告警），Mitigate 问发现后怎么少伤人（runbook 把修复压到 3 分钟、一键回滚）。只做预防的清单，一旦漏防就全裸奔。

跟踪机制三件，缺一不可：行动项进 issue tracker 打 postmortem label，复盘文档只引用编号；每季度一次清点会，过期未完成的当场重排期或明示放弃并写理由；结项判据是验证命令的输出，不是 owner 说「做完了」。

## 六、无指责不等于无后果：边界画在流程上

blameless ≠ accountability-free。这条边界要提前画清楚，否则复盘文化会被两边搞坏：一边是拿 blameless 当免罪金牌的当事人，一边是以「无责」为名彻底放弃管理的上级。

失职的线画在「是否遵守了流程」，不在「是否犯了技术错误」。技术错误永远 blameless——敲错 selector 属于这一类；故意违章不在豁免范围——跳过审批直接 apply 属于另一类。

后者怎么处理？分两层。技术层照常 blameless：把「流程可被绕过」作为系统缺陷写进促发因素，行动项指向让绕过变难或变显眼，比如准入控制、审计告警。纪律层不进复盘文档：是否违规、如何处理是管理动作，走单独渠道。混在复盘里有两个坏结果——当事人防御性沉默，以及团队从此把复盘会等同于问责会。

还有一个操作细节：管理层看报告，不进会场。高层旁听施压，是复盘会变追责大会的第一诱因【从业者判断】。

**blameless 豁免诚实的错误，不豁免故意的违章**；但违章的审判，也不该占用改进系统的复盘。

## 七、不是每次故障都值得复盘：阈值是防疲劳的

**全写等于不写。**复盘是重体力活，小事全写，三个月后团队看到模板就生理性厌恶，这是比不复盘更隐蔽的反噬【从业者判断】。定阈值，满足其一才触发：

| 触发条件 | 时限 |
|---------------------|------|
| 用户可见的 SEV1/SEV2 事件 | 72 小时内开会，5 个工作日内出报告 |
| 错误预算单日烧掉 ≥ 10% | 同上 |
| page 响应超时、升级链断裂（流程事故） | 同上 |
| near-miss：靠运气没变成故障 | 鼓励自愿复盘，同样 blameless |
| 例行变更失败但有惊无险 | 低成本轻量复盘，模板可裁剪 |

注意最后两行。near-miss 是性价比最高的复盘素材：根因链已经完整暴露，只是最后没击中用户。一个团队复盘会的数量里，near-miss 占比高是好信号；只在真实故障后复盘的团队，等于只从学费全款支付的课程学习。

轻量复盘的裁剪法：30 分钟会，模板只留时间线、根因、行动项三节，不强制记录员。判断标准不是「有没有用户受影响」，而是「同样的链路下次还会不会出现」——会，且击中用户，就是 SEV1。

## 结尾：这周就能做的三件事

1. 把第三节的模板搬进你的仓库，从建目录开始，一条命令：

```bash
mkdir -p docs/postmortems
```

2. 跑一遍第四节的 grep 自查，数数你们的复盘文档有几份停在「人为失误」。
3. 挑最近一次故障或 near-miss，按四条硬标准写 3 条行动项，进 tracker 打 postmortem label，再设一个 7 天后的清点提醒。

留一个提问：你们团队最近一次复盘的根因栏写的是什么？评论区贴出来——我赌一半以上是「人为失误」或它的同义词，不服来晒。
