# 往集群加一台机器的午夜惊魂：分片再平衡怎么不停机做完

> （构造典型案例，细节已脱敏虚构）23:52，Redis Cluster 第 6 个节点 cluster meet 入网。00:04，P99 从 6ms 爬到 240ms；00:19，源节点网卡打满；00:31，值班放行了滚动发布，消费组 rebalance 又补一刀。凌晨 1:47 全部回滚——加机器为了救集群，差点杀死集群。

凶手不是新机器，是再平衡：数据从旧归属搬去新归属，占网络磁盘 CPU，还要让客户端在"一半在这、一半在那"的中间态里继续读写。

上一篇《一致性哈希那么好，为什么 Redis 和 Kafka 都不用》（12）讲为什么；这篇讲怎么做——怎么把一次扩容安全做完。难的就三问：搬多快？搬的期间谁服务？搬错了怎么办？

## 一、搬多快：先算三本账，算不平就改期

三本账这个提法，选型篇（12）结尾露过一面；这里拆开逐项算。

| 账本 | 算什么 | 锚点 |
| --- | --- | --- |
| 迁移流量 | 搬移数据量走一遍网络与磁盘 | 搬 1TB 在 1Gbps 网卡上纯跑就要 2 小时起步，叠上业务流量再翻倍 |
| 源端压力 | MIGRATE 会同步阻塞源节点的单线程 | 大批量小 key 能把源节点卡出超时 |
| 客户端感知 | 重定向、消费组整组停顿、路由抖动 | 窗口期超时率要有基线 |

迁移量怎么估：5 节点扩到 6 个，就是 16384/6 ≈ 2731 个槽、约 1/6 的数据，200GB 集群约搬 33GB。但迁移流量和业务流量走同一条网卡，实际要按纯迁移时长 ×2 估。窗口盖不住就分多晚迁，前提是确认中间态可暂停。

比总时长更容易翻车的是源端：MIGRATE 同步阻塞源节点单线程，一大批小 key 下去整个节点跟着卡。所以铁律是小批慢迁：每批几十个 key，批间盯延迟与超时率，随时能停。

**迁移时长不是纯搬运时长，是叠着业务流量走同一条网卡的时长。**

## 二、搬的期间谁服务：中间态路由是生死线

搬槽不是原子操作。Redis 的做法：迁移期间槽的正式归属仍在源节点——源上有这个 key 就直接服务；查无此 key 才回 ASK 重定向，客户端带着 ASKING 去目标执行，仅此一条，本地槽表不动。归属正式切换后，才由 MOVED 让客户端永久更新槽表。

两种重定向一字之差、语义相反，完整对照表和「为什么 ASK 绝不能当 MOVED 记住」选型篇（12）拆过，这里不重抄——只留结论：谁在迁移中提前把槽表指向目标，未迁的 key 查无此 key、目标又把请求指回源，就是打乒乓球式的死循环。

**中间态只信正式归属，一次性重定向只为兜底**——这是 Redis 迁槽敢暂停、敢分多晚的底气。

各家有各的中间态：Mongo 的 balancer 后台搬 chunk，路由抖动是客户端的直接感知；Kafka 搬分区要过副本追平与 Leader 切换【从业者判断】；消费组 rebalance 期间的整组停顿，是另一类"谁服务"的空窗。

不吃中间态的苦还有一条路：双写重建切流——新旧集群并行写、后台对账、按比例切读切写【从业者判断】，用"双写一致性"换掉"迁移路由"，代价是双倍写入与切流回滚，超大数据量或换分片键时才划算。

## 三、搬错了怎么办：刹车和回滚是设计出来的

Redis 迁槽天然可暂停：ASK 兜着中间态，今晚停手业务照常，明晚接着迁；回滚是显式动作，SETSLOT 把槽归还源节点。但记住反面——`cluster-require-full-coverage=yes`（默认）下任何槽没有归属，整个集群拒绝写。**迁一半弃疗，比不迁更危险。**

Kafka 把刹车做进流程：Cruise Control 生成提案，人工 approve 后才真正动数据——先看搬哪些、估多少字节再动手。

Mongo 的闸门是 balancer 窗口：不停 balancer，只圈一个允许搬迁的时段。

```javascript
// [mongos] 只许 balancer 凌晨搬【从业者判断】
db.getSiblingDB("config").settings.updateOne({ _id: "balancer" },
  { $set: { activeWindow: { start: "02:00", stop: "05:00" } } },
  { upsert: true })   // 窗口外不搬迁
```

检验一套方案成不成熟，只看一条：**被叫停之后，回滚动作本身不产生新迁移。**

## 四、固定槽、动态区间、静态分区：迁移语义三连

| | 一致性哈希 | Redis 16384 槽 | Mongo 动态区间 | Kafka 分区 |
| --- | --- | --- | --- | --- |
| 迁移单位 | 环上相邻段（隐式） | 槽（显式，2KB 位图） | chunk（随写入自动分裂） | 分区（显式静态元数据） |
| 刹车在哪 | 没有 | ASK 兜底+SETSLOT 回滚 | balancer 窗口 | 提案→人工 approve |
| 扩容语义 | 相邻段自动迁移 | 手工迁约 1/N 的槽 | 自动匀 chunk | 老分区纹丝不动 |
| 热点干预 | 不可（哈希决定） | hash tag 定向 | refine 分片键 | 建分区时规划 |

Mongo 一列按其分片章节口径，字段以官方文档为准。三条语义各买各的：Redis 买"可控"——槽是显式元数据，成段迁移、可暂停、可回滚；Mongo 买"免运维"——chunk 自动分裂、balancer 自动搬，代价是搬什么你说了不算。

Kafka 买"确定性"——分区映射创建时写死，扩容后老分区不动，官方不自动迁移的理由就是带宽与 IO 不可控。

所以 Kafka 扩容后盯着新 broker 的磁盘看三天毫无增长，别急着提单——上表「老分区纹丝不动」那一格，说的就是它。顺带拆一对常被混用的词：消费组 rebalance 是分区在消费者之间重分（秒级、自动），分区再分配是副本在 broker 之间搬家（搬数据、手动、分钟到小时级）——两码事，混着说方案就写歪了。

规律：**自动化省下的每一步，都得在别处补一个闸门**——Mongo 补窗口，Kafka 补 approve，Redis 干脆把迁移整个留给运维。

## 五、再平衡风暴：三个正常变更叠成一场事故

风暴的配方：扩容+滚动发布+消费组 rebalance 挤进同一窗口。它是分布式五类经典故障之一——没有单一凶手，凶手是"同一时间窗口"。

Kafka 侧的正反馈最典型：处理慢 → max.poll.interval.ms 超时被踢出组 → rebalance 整组停顿 → 停顿拖垮所有人的处理进度 → 更多人被踢。雪球就这么滚。

限速阀清单，动手前逐条对：

- 消费组用 CooperativeStickyAssignor（KIP-429 增量协作），不停全组
- 会话超时与 max.poll.interval.ms 按真实时长放宽
- 发布与迁移错峰；group.instance.id 缺失时每次发布都可能全组重分配【从业者判断】
- Redis 侧同一条铁律：小批量+批间隔，限速阀是 sleep

排障顺序定型：先看日志分型——心跳失败类日志（如 Attempt to heartbeat failed）多指向会话/网络问题或 rebalance 正在进行，max.poll.interval 超时则是单批太慢，两类方向不同【从业者判断】；再对齐时间线，看 rebalance 是否与发布、扩容吻合。

**风暴的根因不是参数，是三个正常变更排进了同一个窗口。**

## 六、搬不动的和搬不匀的：jumbo chunk 与热点

键均匀和流量均匀是两回事：同一个大 V 的 key 与一个僵尸号的 key 各占一槽，QPS 能差四个数量级——加节点匀的是键，流量它管不着。选型篇速查表里「加了 2 个 Redis 节点，倾斜没改善」那一行，根子就在这里。

处置两条路：先定位热点 key（--hotkeys 或监控采样），要么 hash tag 定向隔离，要么业务层打散（加盐、预聚合）。

Mongo 还有一类"搬不动"：一个 chunk 内所有文档共享同一分片键取值（低基数键），拆也拆不开，超出大小上限后被标记为 jumbo，balancer 搬不动，数据与负载一起倾斜。

正解是 refineCollectionShardKey 给键增补高基数后缀列（4.4+，只能加列不能改列）；个别版本还要清 jumbo 标记才重新参与调度【从业者判断，以官方文档为准】。根因永远是选键时的低基数——refine 是补救，不是设计。

```javascript
// [mongos] jumbo 正解：补高基数后缀列
db.adminCommand({ refineCollectionShardKey: "app.orders",
  key: { user_id: 1, order_id: 1 } })
// { ok: 1 }——chunk 从此可拆可搬
```

**哈希替你匀键，没人替你匀流量；搬不动的，最后都得人来裁决。**

## 七、操作剧本：一晚搬完，还是分多晚迁

动手前过 pre-flight，任何一条不满足就改期：

```text
□ 容量账：迁移量≈数据量/N，估纯迁移时长×2
□ 窗口账：低峰盖不住 → 分多晚迁，确认中间态可暂停
□ 副本账：目标盘余量 > 迁移量×1.5，源/目标无告警
□ 中间态账：Redis 拒写风险；Kafka 先看提案
□ 干扰账：无滚动发布、无扩缩容、无备份大任务
□ 回滚账：回滚动作写下来，且不产生新迁移
□ 观测账：延迟、超时率、rebalance 次数有人盯
```

Redis 渐进式迁槽的标准动作（槽 1649 从源节点搬去新节点 F）：

```bash
SH=10.0.0.1; SP=6379; DH=10.0.0.6; DP=6379; SLOT=1649
SRCID=$(redis-cli -h $SH -p $SP cluster myid)
DSTID=$(redis-cli -h $DH -p $DP cluster myid)

redis-cli -h $SH -p $SP cluster setslot $SLOT migrating $DSTID
redis-cli -h $DH -p $DP cluster setslot $SLOT importing $SRCID

while :; do    # 批间停 1 秒：sleep 就是限速阀
  KEYS=$(redis-cli -h $SH -p $SP cluster getkeysinslot $SLOT 100)
  [ -z "$KEYS" ] && break
  redis-cli -h $SH -p $SP migrate $DH $DP "" 0 5000 keys $KEYS   # OK
  sleep 1
done
# 任意时刻 Ctrl-C 都安全（ASK 兜底）

redis-cli -h $DH -p $DP cluster setslot $SLOT node $DSTID   # OK：目标认领
redis-cli -h $SH -p $SP cluster setslot $SLOT node $DSTID   # OK：MOVED 接管
redis-cli --cluster check $SH:$SP   # [OK] All 16384 slots covered.
```

Kafka 同一场扩容走提案审批：KafkaRebalance 的 YAML 与 approve 注解，选型篇（12）演示过，这里不重抄。增量只有两问——ProposalReady 之后，提案要搬多少字节、落在哪些盘，人核过再 approve，此后才真正动数据；裸集群的等价工具是 kafka-reassign-partitions.sh。审批这一步就是 Kafka 的刹车，别图快省掉。

一次性搬完还是分多晚，判断依据只有一条：窗口能不能盖住"纯迁移 ×2"【从业者判断】。盖得住就一晚做完人盯全程；盖不住就分多晚，每晚收敛一部分槽，第二天仍是完整集群。**渐进式的本质不是慢，是每个中途状态都是完整集群。**

## 八、30 秒自检

| 问题 | 一句话答案 |
| --- | --- |
| 三难是什么 | 搬多快（三本账）、谁服务（中间态路由）、错了怎么办（刹车回滚） |
| Redis 迁移中读路由 | 源优先：源上有就服务，查无才 ASK 去目标，槽表不动 |
| ASK 为什么不能记 | key 一半在源一半在目标，记了就是重定向死循环 |
| 迁一半弃疗的下场 | 槽无归属全集群拒写——要么迁完要么 SETSLOT 归还 |
| 风暴怎么来 | 扩容+滚动发布+消费组 rebalance 挤进同一窗口 |
| jumbo chunk | 键基数不够拆不动，refineCollectionShardKey 补列 |

**三难答不出可以补课；答"加机器自动匀"的，先收回变更权限。**

## 写在最后

这篇只想留下一句：**不停机靠的不是搬得快，是中间态有人兜底、刹车踩得死。**三难对应三个动作：三本账定搬多快，ASK 定谁服务，SETSLOT 归还与人工 approve 定怎么收场。选型篇讲为什么 Redis 宁可管 16384 个槽，这一篇就是那些槽搬家那天的实操——两篇连读，选型与操作闭环。

## 现在就能做的事

- 对一遍手头集群的三个开关：Redis 的 `cluster-require-full-coverage` 当前值、Mongo balancer 有没有 activeWindow、Kafka 有没有待 approve 的再平衡提案
- 用「数据量 ÷ N × 2」算一次最近的扩容计划，拿结果和低峰窗口比大小——盖不住，今天就改成多晚分批
- 把本月排期里的扩容、滚动发布、消费组变更拉出来看一遍，挤在同一晚的先拆开

评论区报两个数：最近一次扩容你迁了多少数据、实际跑了几个小时；有没有中途叫停过——叫停那一刻，中间态是拿什么兜住的？
