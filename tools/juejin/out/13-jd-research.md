# Linux+脚本才是运维的分水岭：一份 84.2k 星题库和 9 个高星仓库的交叉验证

入行第三年，多数运维停在入门档；调研显示薪资断层明显，同一批人里跨过这道断层的那部分，差别不在 K8s。

我把 23 组招聘平台的搜索词和 9 个高星 GitHub 仓库逐条过了一遍，答案有点反直觉：真正拉开差距的，是路线图里排最前、面试题量前三但常被轻视的 Linux 和脚本。

更意外的是，在那个 84.2k 星的面试题库里，Terraform 的题量超过了容器（Containers）类目。下面把两份调研的硬数据摊开讲。

## 这份"真相"是怎么来的

先交代方法论，免得说我编故事。第一份数据来自平台侧：几家主流招聘平台（含海外侧的 LinkedIn），加上字节、腾讯、阿里云等大厂官网职位页，23 组关键词搜索，外加一次 JD（岗位描述）聚合页的全文抓取，调研时间窗覆盖 2025 到 2026 年。

样本覆盖互联网、云厂商、金融和事业单位，其中 8 份完整岗位描述做了全文逐条拆解——23 组搜索词负责看"哪些词高频出现"，完整岗位描述负责看"要求具体怎么写"，两层口径互补。频次分级用"高/中/低"定性口径，不编精确百分比，这一点先说清楚。

第二份来自社区侧：V2EX、知乎等社区的高赞讨论，加上 9 个 GitHub 高星仓库的逐文件考察，包括 84.2k 星的 devops-exercises、20.3k 星的 DevOps 路线图、9.1k 星的 SRE 面试指南。

两份调研分别来自平台侧和社区侧两个独立的来源维度——一边是岗位描述数据，一边是社区讨论和开源仓库——结论却高度一致。这种交叉印证，比任何单一"大 V 经验帖"都扎实。

顺带交代行情背景：某头部招聘平台 2025Q4 数据显示，运维需求同比涨了两成以上，但 2025 年各城市 SRE/DevOps 行情较 2024 年回落 2%-12%，而 AI Infra SRE、大模型平台运维逆势走高。

涨的是结构，不是原来的岗位。

## 真相一：Linux 和脚本，排得最前却最常被轻视的一层

先看题库硬数据。bregman-arie/devops-exercises（84.2k 星）的题量分布是逐文件数出来的：AWS 444 题、Kubernetes 341 题、Linux 298 题——Linux 排第三，仅次于云和 K8s。

注意这是国际版题库，云厂商类目换成阿里云、腾讯云另算，但 Linux 是全语言通用的类目，不存在地域偏差。你绕不开它，任何路线图的第一层都有它。

再看路线图。milanm（20.3k 星）、mxssl（9.1k 星）、roadmap.sh 三家独立路线图，在"把 Linux 排在容器和 K8s 之前"这一点上无一例外，这是三家唯一完全一致的前置项。主顺序也大体同构：基础 → 容器/K8s → IaC/CI-CD → 可观测 → 云 → SRE 方法论（milanm 和 mxssl 完全吻合，roadmap.sh 把 CI/CD 和 IaC 提得更靠前）。脚本的位置有分歧：milanm 明确把"Linux 与脚本"合成基础层放在容器之前，mxssl 和 roadmap.sh 则把编程语言排到了后段。社区把这条缝补齐了：知乎的主流观点就一句——"会写脚本是运维的分水岭"；V2EX 高赞帖的原文更直白——"不涉及 coding 是没前途的"。路线图排的是知识顺序，社区筛的是能力顺序，两回事。

平台侧的岗位要求也在印证这个方向。把普通运维和 SRE 两类岗位的描述逐条对齐后，重合的部分是 Linux、容器、监控、网络；SRE 侧多出来的那一栏，是"用 Go/Python 开发运维工具"。分级要求写得更清楚：初级要求 Shell，中级要求 Python 做自动化，高级要求 Go 做平台和 Operator 开发。**工具人人都会装，代码才是替代不掉的部分。**

分工上社区也有共识：Shell 做系统级任务，Python 扛复杂逻辑，Go 留给平台和 Operator 开发。三者不必齐头并进，Shell 和 Python 是底线，Go 可以等方向定了再学。

举个最直接的例子。判断一个人过没过这道坎，就看他能不能不看资料写出这样的巡检脚本：

```bash
#!/usr/bin/env bash
# 巡检：磁盘使用率 >= 80% 就告警，并定位大目录
THRESHOLD=80
df -P | awk 'NR>1 {gsub("%","",$5); print $5, $NF}' | while read -r usage mount; do
  if [ "${usage:-0}" -ge "$THRESHOLD" ]; then
    echo "[WARN] ${mount} 已用 ${usage}%"
    du -xh --max-depth=2 "${mount}" 2>/dev/null | sort -rh | head -5
  fi
done
```

这段代码没有任何高深的东西，但能顺手写出来的人，和只会开面板看监控的人，**在面试官眼里是两个物种**。

面试里对脚本的考察也很实际：社区回忆版的面经里，场景排查题集中在磁盘满、CPU 高、服务不通这类真实故障上。背题库应付不了，只有真的写过才答得上。

## 真相二：Terraform 的题量超过了容器，IaC 被严重低估

这是整次调研里最反直觉的一条。同一个 84.2k 星题库里，**Terraform 175 题，Containers 只有 143 题**。很多人的心智地图里"云原生 = Docker + K8s"，但在这份国际版的备考题库里，IaC 的分量已经不低于容器——题量反映的是国际面试准备场景的热度，不直接等于国内考察频率，这个口径先说清楚，下面有国内侧的对账。

题量前列的类目长这样（节选自全库 2624 题 / 35+ 类目，逐文件实测）：

| 类目 | 题量 |
|---|---|
| AWS | 444 |
| Kubernetes | 341 |
| Linux | 298 |
| Terraform | 175 |
| Containers | 143 |
| Network（主 README 补充题） | 72 |
| Argo（GitOps） | 51 |
| CI/CD | 42 |
| Git | 39 |
| Shell | 31 |
| Kafka | 5 |

表里还有个更极端的对比：Argo（GitOps）51 题，Kafka 只有 5 题，差出一个数量级。另外 Shell 单独占 31 题——正好接上真相一那条分水岭论点。这个分布和你以为的"热点"，可能完全不在一个频道上。

CI/CD 和 Git 的题量（42、39）对应到平台侧：国内主流表述还是 Jenkins 和 GitLab CI，而 ArgoCD、GitOps 是明确写在上升趋势里的词。部署这一侧的工具链，题库和岗位描述对得上。

V2EX 上有句流传很广的话："Terraform 才是云原生的正确打开方式。"这句话要分市场对账：海外岗位里 Terraform 已是高频要求；国内侧，平台调研的技能频次表把 IaC 列在第 9 位，频级"中频（海外高频）"，备注是"Ansible 国内主流，Terraform 海外高频、国内上升"——也就是说，国内存量以 Ansible 为主，Terraform 在上升但还不是主流。入门从 Ansible 切入更贴近国内现岗，Terraform 决定你能对接多少海外实践。

平台侧还有个信号值得注意：银行、设备商、国企的"运维"岗，岗位描述措辞已经系统性写入云原生、CI/CD 和 IaC。转型压力不是互联网独有，它已经下沉到传统行业。

IaC 上手其实不吓人，核心就是"用代码描述基础设施"。比如用 Terraform 在阿里云开一台机器（规格和镜像 ID 以官方文档为准）：

```hcl
resource "alicloud_security_group" "default" {
  name = "sre-lab-sg"
}

resource "alicloud_instance" "web" {
  instance_name   = "sre-lab-web"
  instance_type   = "ecs.e-c1m1.large"   # 规格以官方文档为准
  image_id        = "ubuntu_22_04_x64"   # 镜像 ID 以控制台查询为准
  security_groups = [alicloud_security_group.default.id]
}
```

重点是思想转变：手工点控制台，变成改代码、走 code review、可回滚。这个思维一旦建立，GitLab CI、ArgoCD 都是同一套逻辑的延伸。

## 真相三：CKA 是敲门砖，不是护城河

调研里有个扎心的反面案例：V2EX 上有人拿着 CKA+CCNA，投递仍屡屡受挫。社区对此的共识很冷静——证书能帮你过简历筛选，但过不了实操面试。

两份数据在这一点上完全一致：岗位描述里 CKA/CKS、RHCE、云厂商认证都是高频加分项，但配套要求普遍是实操经验更受看重。面试官真正想看的，是你排查过什么故障、搭过什么体系。

顺带提醒：CKA 的考试环境、K8s 版本和题型每年都在调整，备考前以 CNCF 官方页面为准，别依赖二手攻略。

认证的优先级也可以给个参考：方向偏国内云就考阿里云 ACP/ACE，偏海外或外企就 AWS 认证加 CKA，RHCE 适合 RedHat 生态重的传统企业。按目标岗位选，别全都要。

那真正的护城河是什么？平台调研的总结很精辟：中级到高级的断点不是"会更多工具"，而是三条跃迁——从使用工具到开发工具；从处理故障到设计稳定性体系；从执行操作到制定规范并跨团队推动。每一条都在考代码和方法论，没有一条在考证书。

各级别的画像也能佐证：初级做监控值守、巡检和按文档部署；中级独立负责业务系统、做性能优化和自动化工具；高级做容量规划、高可用设计和体系建设。跃迁的每一步都在远离"纯手工"。

所以合理的策略是：CKA 用最短周期拿下当敲门砖，然后把省下来的时间全部投到项目和代码上。"证书 + 可演示的实操项目"这个组合叙事，比任何单一证书都值钱。

## 网络背景不是包袱，是存量优势

这一节专门写给网络工程师。社区回忆版的面经里，网络方向是转型者被问频率最高的一类：三次握手、TIME_WAIT 排查、TLS 全过程、LB 算法、网卡收包到协议栈的路径。

但注意一个关键细节：这些题全部以 Linux 内核视角出题。考的不是你背不背得出报文格式，而是你能不能用 tcpdump、ss 这些工具在真实机器上把问题摁住。

题库侧同样支持这个判断：主 README 的补充题里，Network 一个类目 72 题，是所有单类里最多的。你的存量知识，是别人要专门补课才能拿到的部分，别浪费。

V2EX 一位在职 SRE 的忠告很到位："好好花时间在 Go/K8s/Linux 上，切忌啥都搞。"网络知识是你的送分题，但要把能力"内核化"，而不是继续深钻设备方向。

转型路径也已经被验证：Linux → 虚拟化 → 公有云 → Docker/K8s → DevOps 工具链 → SRE。网络工程师在 VPC、LB、SDN 上有天然优势，这条路你已经走了一半。

```bash
# 把网络知识"内核化"的最小练习：
# 抓一次完整的 TCP 握手，亲眼看 SYN / SYN+ACK / ACK
sudo tcpdump -i eth0 -n 'tcp[tcpflags] & (tcp-syn|tcp-ack) != 0' and port 443

# 看当前机器的 TIME_WAIT 概况，面试高频
ss -s | grep -i timewait
```

再往前看一步，海外岗位里已经出现 eBPF 可观测方向的专职岗，Cilium 这类云原生网络方案正是网络背景最顺的延伸。可以不当主线，但值得知道天花板在哪。

## 学习顺序有共识，但也要听一个反方声音

前面的顺序骨架（基础 → 容器/K8s → IaC/CI-CD → …）来自几家路线图的交叉验证，roadmap.sh 在 CI/CD 和 IaC 的位置上略有出入，但当骨架用没问题。有个 2.5k 星的反方仓库值得听一听。

DevOpsHiveHQ 的 dynamic-devops-roadmap 直接批评线性路线图"无法帮你拿到第一份工作"，主张 MVP 迭代式：每轮横跨所有领域，做一遍"写码 → 构建 → 部署 → 监控 → 故障"的小闭环。

我的建议是两者结合：知识按线性补，但每学完一个阶段就跑一遍贯穿闭环。比如学完 Terraform，就把之前手工搭的环境重写成 IaC；学完监控，就给自己部署的应用加上告警。

这个闭环本身，就是面试时最好的项目素材。

顺带一提，社区里 3k 星的 SadServers 专门做"症状 → 限时排查 → 验证"的故障练习，甚至有公司拿它当面试工具。可见"能动手排查"这件事，本身就有市场定价。

## SRE 的护城河是方法论，不是工具清单

调研里还有个容易忽略的结构性事实：awesome-sre 这个仓库里，一半类目不是工具，是流程和文化——SLO/SLI、错误预算、On-call、Postmortem、Runbook、Toil 治理。

入门材料不用纠结，Google SRE 那两本书就是社区公认的教材，上面这些类目基本都能在书里找到对应章节，比零散刷文章效率高得多。

平台侧也在呼应：腾讯和 AI 基础设施方向的岗位，已经把 SRE 方法论明文写入要求，且占比在上升。

一句话总结：SRE 不等于"会 K8s 的运维"。**工具决定你能不能干活，方法论决定你能不能设计让别人好好干活的体系。**这才是"软件工程师 + 运维专家"的完整含义。

## 还没内卷的组合：传统运维 + 编程 + LLM 应用

最后一条发现偏前瞻，值得单独一节说。平台调研里，AIOps/大模型相关要求还是低频项，但标注是"快速升温"，而且集中在三类岗位：专职 AIOps 工程师、AI 基础设施 SRE（万卡 GPU 集群稳定性，薪资溢价最高）、科研单位的 MLOps。GitHub 侧同样有动静，multi-agent-aiops 这类做企业级多 Agent 智能运维（监控告警、根因分析、故障自愈、变更审批）的项目在 2026 年保持活跃。

两份调研在这里给出同一个判断：**"传统运维技能 + 编程 + LLM 应用"，是当前还没内卷的组合公式**，属于差异化机会窗口。它现在还不是普遍要求，不值得当主线，但值得留一小部分精力提前卡位。

落地门槛很低：用大模型辅助写 runbook、做告警根因的初步归类，把它当提效工具嵌进现有流程，就足以形成简历上的差异点。

## 给你的可执行清单

如果只打算记住几条，我建议是这六条：

1. **今天就自查脚本分水岭**：不看资料，手写一个批量巡检或告警脚本。写不出来，就把每天 30 分钟投给 Shell 和 Python，这是当前优先级最高的事。
2. **给 K8s 学习降一点权重，匀给 IaC**：Terraform 或 Ansible 二选一深入上手，另一个做到能读能改。题库与岗位描述的双侧信号都指向 IaC 值得加投——国内 Ansible 主流、Terraform 上升，按你的目标市场选。
3. **把网络优势内核化**：每周用 tcpdump、ss、strace 做一次真实机器上的排查练习，把设备视角的知识翻译成 Linux 视角。
4. **证书策略明确化**：CKA 用最短周期拿下当敲门砖，考试细节以官方文档为准；剩余时间全部投到"可演示的项目"上。
5. **构建自己的闭环项目**：一台机器、一段代码、一套 IaC、一条流水线、一块监控面板，再定期给自己注入故障做复盘。这个故事讲出来，比任何证书都有说服力。
6. **留一成精力做差异化布局**："传统运维 + 编程 + LLM 应用"这个组合还没内卷。从用大模型辅助写 runbook、做告警根因归类开始，把它嵌进现有流程，就是简历上的差异点。

配套材料我持续整理在 [sre-learning-hub](https://github.com/Thneoly/sre-learning-hub)：靶场环境、分阶段清单，以及上面提到的闭环项目模板，配合本文的调研结论一起用效果更好。如果你也在从传统运维或网络方向转型，欢迎来提 issue 交流。

这篇如果帮你省了试错时间，点个收藏，转给同组正在转型的人。清单第一条，今晚就能做。
