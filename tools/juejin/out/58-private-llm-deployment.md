# 一张 24G 卡能跑多大的模型？先把这本显存账算清

「我这张 24G 的卡，跑 7B 模型绰绰有余吧？」——多数人第一次私有化部署 LLM，都从这句自信开场，以 vLLM 启动即 CUDA OOM 收尾。

原因只有一个：**显存账只算了权重，漏了 KV cache 和运行开销**。值班篇（34）结尾给过一页显存速查，这张表背后的账怎么算、算完怎么拍板，是这篇的正题：24G 卡到底能跑什么、Ollama 和 vLLM 怎么分工、量化要付什么代价，以及最诚实的那一问——到底该不该自部署。

## 一、显存三件套：权重是房租，KV cache 是水电费

粗算公式（误差够用，目的是排除"明显跑不动"的选项）：

```text
显存占用 ≈ 参数量 × 每参数字节数   ← 权重，只跟模型和精度有关
           + KV cache              ← 随上下文长度与并发数线性增长
           + 10%~20% 运行开销       ← 激活值 / CUDA 上下文，经验值
```

权重部分一张表搞定（B = 10 亿参数）：

| 精度 | 每参数字节 | 7B | 14B | 32B |
|---|---|---|---|---|
| FP16 / BF16 | 2 | 约 14 GB | 约 28 GB | 约 64 GB |
| INT8 | 1 | 约 7 GB | 约 14 GB | 约 32 GB |
| INT4 | 0.5 | 约 4~5 GB | 约 8~9 GB | 约 17~20 GB |

INT4 实际占用略高于"参数量 × 0.5 字节"：量化元数据和少量不量化的层有额外开销，所以给区间。

真正的变量是 KV cache，粗算式：

```text
KV cache ≈ 2(K和V) × 层数 × KV头数 × 头维度 × 每元素字节数 × 序列长度 × 并发数

以 Qwen2.5-7B 为例（28 层、4 个 KV 头、头维度 128、FP16；具体以模型卡为准）：
  每 token     ≈ 2 × 28 × 4 × 128 × 2 ≈ 56 KB
  4k 上下文    ≈ 0.22 GB / 请求
  32k 上下文   ≈ 1.8 GB / 请求
  10 并发 × 8k ≈ 4.5 GB —— 并发上来后，这部分能反超权重
```

（Qwen2.5 用 GQA 把 KV 头压到 4 个，就是为了让这份开销可控。）

一句话立住：**权重是固定房租，KV cache 是水电费，人越多账单越吓人**。很多"OOM 玄学"，不过是水电费没算。

## 二、实算一张 24G 卡：能跑什么，不能跑什么

把公式代入 24GB 这一档（3090 / 4090 / A10）：

```text
方案 A：7B FP16
  权重 14GB + 10 并发 × 8k 上下文 4.5GB + 10%~20% 开销
  ≈ 20~22GB —— 刚好接住，这就是"24G 卡默认配 7B"的由来

方案 B：14B INT4 + 16k 上下文
  权重 8~9GB（含量化开销）
  + KV cache 约 3GB（14B 配置：48 层、8 个 KV 头，约 192KB/token）
  ≈ 12GB，加开销仍在 24GB 内 —— 可行，但余量不多
```

方案 B 的启示更值钱：瓶颈在固定占 8~9GB 的权重。KV cache 可以靠限上下文、限并发压下去，权重压不掉。

各档位速查：

| 参数量 | 显存（INT4 / FP16） | 定位 |
|---|---|---|
| 0.5B~3B | 约 1~2GB / 1~6GB | 摘要、格式转换；CPU 可跑 |
| 7B~9B | 约 4~6GB / 14~18GB | 值班助手主力：排障、RAG 问答、工具调用 |
| 14B~32B | 约 8~20GB / 28~64GB | 复杂根因推理、长 runbook 理解；要好的 GPU |
| 72B+ | 40GB+ / 144GB+ | 多卡多机，运维场景性价比急剧下降 |

硬件对号入座：无独显或 8GB 以下，Ollama 加 INT4 或降到 1.5B（1.5B 在 CPU 上十几秒级响应，慢但可用）；16GB 用 INT8；24GB 跑 7B FP16 加富余上下文；48GB 以上再谈 14B~32B。启动前先 `nvidia-smi` 看卡上有没有别的进程——OOM 的另一半原因不是算错账，是卡不干净。

**7B 是单机的分水岭**：它是"单张 24GB 卡全精度跑完还有 KV cache 富余"的最大档，也是工具调用开始靠得住的最小档【从业者判断】。再往上一档，你就进入了每一步都要精打细算的区间。

## 三、Ollama 与 vLLM：不是二选一，是先后关系

有人叫 Ollama"单机玩具"，这不公平。它的定位是个人与小团队的最快路径：GGUF 量化格式、CPU/GPU 自适应、单命令管理模型，代价是并发吞吐一般。

vLLM 则是为并发流量造的：PagedAttention 管显存分页、continuous batching 管持续凑批，高并发吞吐做到开源推理栈第一梯队，团队 GPU 机器和 K8s GPU 节点多半落在它头上，代价是要求 NVIDIA GPU、部署更重。

```bash
# [任意节点] 路线一 Ollama：拉模型 + 冒烟（7B 默认 Q4 量化，约 4.7GB 下载）
ollama pull qwen2.5:7b
ollama run qwen2.5:7b "用一句话解释 CrashLoopBackOff"

# [有 NVIDIA GPU 的节点] 路线二 vLLM：装好直接起（建议独立 venv）
pip install vllm
vllm serve Qwen/Qwen2.5-7B-Instruct \
  --host 127.0.0.1 --port 8000 \
  --served-model-name qwen2.5-7b-instruct \
  --enable-auto-tool-choice --tool-call-parser hermes
```

命令末尾两个参数开启 Qwen 系工具调用解析，Agent 的 tool_calls 依赖它。权重首次拉取约 15GB，国内网络可配镜像加速——参数名与镜像配置都以官方文档为准。Ollama 那边默认只监听 127.0.0.1:11434，API key 任意非空即可——个人用正好，暴露到内网就是裸奔。

| 维度 | Ollama | vLLM |
|---|---|---|
| 上手成本 | 一条命令 | venv + GPU 驱动 + 参数调优 |
| 并发吞吐 | 单请求友好，并发一般 | continuous batching，高并发首选 |
| 硬件 | CPU 可跑 | NVIDIA GPU |
| 典型位置 | 个人桌面、跳板机 | 团队 GPU 服务器、K8s GPU 节点 |

我的建议是当流水线而不是站队：**先用 Ollama 走通全流程，用量起来再迁 vLLM**——迁移成本见第六节，低到没有理由提前纠结。

## 四、量化的代价矩阵：省下的显存，拿什么换

量化不是免费午餐，是一笔交换：显存和速度，换能力。

| 档位 | 7B 显存 | 速度 | 质量代价 |
|---|---|---|---|
| FP16 / BF16 | 约 14GB | 基准 | 基准 |
| INT8 | 约 7GB | 与 FP16 相近【从业者判断】 | 多数任务几乎无感【从业者判断】 |
| INT4（GPTQ / AWQ / GGUF q4） | 约 4~5GB | 通常更快，访存压力更小【从业者判断】 | 日常问答可接受；指令遵循与工具调用可靠度下降【从业者判断】 |

矩阵里最要命的是最后一行。INT4 省一半显存，但"工具调用可靠度下降"对 Agent 是慢性毒药——单轮对话看不出来，多轮工具循环里一次格式错误就可能让整条链路断掉。而且这类退化不报错，往往只是让你的 Agent 偶尔"发呆"。

所以纪律只有一条：换模型、换精度、换引擎，任何模型侧变更都必须先跑评测集再上线。质量损失的具体幅度因模型和任务而异，别信任何人的转述（包括本文），**用你自己的评测集说话**。

## 五、并发与 batch：容量边界不在权重，在 KV cache

回到水电费。KV cache 总量 = 每 token 占用 × 序列长度 × 并发数，三项都随负载线性增长。单请求 4k 上下文才 0.22GB，10 个并发 × 8k 就是 4.5GB——高并发长上下文场景，KV cache 会反超权重，成为第一显存大户。

这正是 vLLM 存在的理由。PagedAttention 把 KV cache 按页分配、减少碎片；continuous batching 让新请求持续填满 GPU，不用等一批全结束——**同样一块显存，服务更多并发**。这层优化不是 Ollama 的主打，"并发一般"不是实现糙，是产品定位就不在那。

容量边界的实操：先按公式算出"权重 + 目标并发 × 目标上下文"的总账，超了就三选一——降精度（压权重）、限上下文、限并发（后两项压 KV cache）。反过来，端点跑着时显存持续逼近上限，该拧的旋钮还是这三个。

## 六、OpenAI 兼容 API：换后端不改代码

两条路线最终落到同一套接口上，这不是偶然——chat/completions 已是事实标准，Ollama、vLLM、llama.cpp、各类商业服务几乎全兼容。核心就两个端点：GET /v1/models 列模型，POST /v1/chat/completions 对话加工具调用。

这层兼容换来的工程性质是切换成本趋近于零：换模型、换引擎、从本地迁到内网 GPU 集群，代码只动三个环境变量——LLM_BASE_URL、LLM_MODEL、LLM_API_KEY。OpenAI SDK、LangChain、各类 Agent 框架无需改造直连本地端点；同一份评测集还能跑在不同端点上横向对照。

```bash
# [任意节点] 从 Ollama 迁到 vLLM 的全部工作量：改两个值
export LLM_BASE_URL=http://127.0.0.1:8000/v1   # 原来是 http://127.0.0.1:11434/v1
export LLM_MODEL=qwen2.5-7b-instruct            # 原来是 qwen2.5:7b
# 注意 BASE_URL 必须带 /v1，少了它是最常见的 404 来源

# [任意节点] 验收两连
curl -s http://127.0.0.1:8000/v1/models | jq -r '.data[].id'
# 预期输出: qwen2.5-7b-instruct
ss -tlnp | grep -E '8000|11434'
# 预期: 127.0.0.1:8000（Ollama 为 127.0.0.1:11434），不应出现 0.0.0.0
```

但兼容的边界要认得清：**接口全通，不代表能力没缩水**。7B 换成 1.5B，models 与 chat 照样应答，tool_calls 却可能时灵时不灵；各引擎对参数与工具调用细节的支持也参差。换完必跑评测集——第四节那条纪律在这里第二次出现，后面还会出现。

## 七、为什么要私有化，以及最诚实的反方

四个理由，按分量排：

数据不出域。排障 prompt 里有内网拓扑与配置，知识库里有基础设施细节，公网 API 意味着这些数据离开你的边界——在很多行业这不是选择题。

可用性自主。对外承诺的 SLA 不能拴在别家的限流与停服上；内网端点稳不稳，主动权在自己手里。

可复现。云端的模型版本会悄悄挪动、行为跟着漂移，而评测基线要求同一版本长期钉死。

成本可控。Agent 排一次障动辄十几轮工具调用，按 token 计费是一笔流水账；自部署是一次性买断的固定成本。

然后是反方，必须诚实地说：**对多数团队，调 API 几乎总是更便宜【从业者判断】**。API 不用买卡、不用运维、模型常新；自部署的真实成本等于硬件加电费加一个兼职 SRE 的精力。显存账算得再清，也算不出"有人愿意养它"这一项。

判断条件清单，命中三条以上再谈自建【从业者判断】：

- 合规或客户合同白纸黑字要求数据不出域
- 用量恒定且大：全团队天天用的值班助手、批量跑的评测任务
- 需要版本冻结做评测基线，云模型静默升级已实际干扰过你
- 值班链路不能依赖公网 API 的可用性
- 团队里有人认领 GPU 运维：驱动、OOM、模型升级，往后都是你的活

一条都不命中？Ollama 在自己机器上玩玩就够了，别为想象中的需求买卡。

最后收个尾：私有化解决了"数据不出域"，但端点自己成了新的敏感资产——没有认证、没有限流、收到什么 prompt 就处理什么。收口三件事：个人用把监听钉死在回环地址；团队共享就在前面加一层带认证的网关，或启用引擎自带的 --api-key；服务日志会把请求原文落盘，轮转与脱敏都得跟上。**边界是缩小了，不是消失了。**

## 结尾：这周就能做的三件事

1. 用第一节的公式算你手头那张卡：权重 + 目标并发 × 目标上下文 + 10%~20% 开销，把"明显跑不动"的选项先排掉。
2. Ollama 十分钟起步：拉一个 7B，跑通 /v1/models 和一次对话，体感一下本地模型的速度与质量。
3. 给团队定一个默认模型，攒下 5 条评测用例——下次谁想换模型、换精度，先过评测再说话。

留一个问题：你们团队如果真要私有化，压倒性的理由是数据、可用性还是成本？算过自建对 API 这本账的，评论区晒一下结论——每个团队的答案都不一样，值得互相抄。
