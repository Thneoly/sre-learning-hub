# 断网也能协同编辑：CRDT 怎么让副本自己长成一样

两个人在两地编辑同一份文档，中间光缆断了一小时。断网期间各写了几十段，重连之后文档自动长成同一个版本：没有冲突对话框，没有手工合并，甚至没有一条告警。

Google Docs 那一代做不到——它的 OT 方案要中央服务器串行仲裁，断网就不能编辑。Yjs、Automerge 这一代敢做这个承诺，靠的不是更快的网络，是把数据结构本身设计成"怎么合并都不打架"：CRDT。

这篇讲清：共识为什么注定给不了这个能力；三条数学性质怎么让合并零协调；计数器到寄存器的构造；LWW 的时钟坑与因果序救场；账单与选型边界。

## 1. 先看强一致的代价：每次写都在等别人

单主复制（Redis/MySQL 主从）：只允许一个写入口，分歧"以主为准"消除。分区时必须选边，旧主没来得及复制的写，愈合后直接丢。

共识（etcd/Raft）：过半提交，彻底没有分歧。代价明码标价——**每次写过半 fsync、少数派分区停写**，单 leader 还是吞吐与延迟的串行点。

无主多写（Dynamo 系）：N 个副本都收写，向量钟能检测出并发——然后呢？要么应用层写合并逻辑（购物车可以，账户不行），要么 LWW 丢一边。

一句大实话【从业者判断】：quorum 写等来的不是最快的人，是过半里最慢的那个。

另一条路叫收敛：不保证所有副本按同一顺序看到写，但保证**收到同一批更新的副本必然处于同一状态**——术语叫强最终一致。一致性谱系那篇讲过：最终一致承诺的是收敛，但合同里藏着一句"分歧必须能被裁掉"。CRDT 是这份合同最彻底的工程实现：**把冲突裁决做进数据结构，变成数学保证**。

一句话立骨架：共识用**"少数派闭嘴"换唯一真相**，CRDT 用**"自动合并"换掉整个裁决环节**。

## 2. 三条律：交换、结合、幂等

CRDT 的同步只靠一个 merge 操作，它必须满足三条律（本地读写照常，跨副本才走 merge）：

交换律 a ⊔ b = b ⊔ a，谁先谁后结果一样；结合律，三份状态先合哪两份、分组无关；幂等律 a ⊔ a = a，同一份状态重复合并无副作用。

乱序、重复、断续是网络常态——三条律全部吸收。幂等还白赚保险：重发同一份状态毫无副作用，重试随便做。

三律之外还有一根支柱：**状态只增不减**——挡住"回退覆盖"，慢副本不能把别人涨上去的状态拉回来。

反直觉的推论：**删除不能真删，只能加墓碑**。去掉元素是"状态变小"，破坏单调性；墓碑把删除翻译成"追加一条死了的记录"，状态还在涨——第 7 节的账单一半来自它。

三个副本各自计数，任意顺序合并：

```text
 R1=(5,0,0)   R2=(0,3,0)   R3=(0,0,7)     每格 = 各副本自记的计数
      └──────────┼──────────┘
 (R1⊔R2)⊔R3 = R1⊔(R2⊔R3) = (5,3,7)
              ← 顺序无关 = 收敛保证
```

**交换律等于主动放弃对顺序的仲裁权**。反过来读就是 CRDT 的天花板：锁、选主、不超卖这类"必须判先后"的事，它天生干不了。

口诀带走：数据能不能表达成"只累积、不回退"，合并能不能写成取 max、并集、相加这类交换运算——能，就是 CRDT 候选；要覆盖旧值、按业务取舍，另想办法。

## 3. 构造：从计数器到寄存器

G-Counter（只增计数器）：每个副本一格，自己只写自己那格；合并逐格取 max，值 = 各格相加。类比景点多入口客流统计：每个入口一本计数册，对账谁的多听谁的——分区期间各记各的，愈合后一次不丢。

PN-Counter（正负计数器）：两个 G-Counter，P 记加账、N 记减账，值 = P − N。"减法"其实是往 N 册里加——单调性没破，代价是两倍空间。

LWW-Register（最后写入者胜）：状态是（时间戳, 节点 ID, 值），时间戳大者胜，同戳比节点 ID。类比排班表贴墙上：谁最后改的听谁的。

一个只用标准库的短脚本：

```python
# 存为 crdt_demo.py，任何有 python3 的机器都能跑
class GCounter:
    def __init__(self, node): self.node, self.v = node, {}
    def incr(self, n=1): self.v[self.node] = self.v.get(self.node, 0) + n
    def value(self): return sum(self.v.values())
    def merge(self, o):
        out = GCounter(None)
        for k in sorted(set(self.v) | set(o.v)):   # 排序只为输出稳定，合并与顺序无关
            out.v[k] = max(self.v.get(k, 0), o.v.get(k, 0))
        return out

# 1) 分区期间三个副本各写各的，任意顺序合并都收敛
r1, r2, r3 = GCounter("R1"), GCounter("R2"), GCounter("R3")
r1.incr(5); r2.incr(3); r3.incr(7); r2.incr(1)
a = r1.merge(r2).merge(r3)      # 合并顺序一
b = r3.merge(r1).merge(r2)      # 合并顺序二
print("顺序一:", a.v, a.value(), "| 顺序二:", b.v, b.value(), "| 相等:", a.v == b.v)

# 2) PN-Counter：减法 = 往 N 账本里加
p1, n1, p2 = GCounter("R1"), GCounter("R1"), GCounter("R2")
p1.incr(150); n1.incr(30); p2.incr(20)    # R1 存 150 取 30，分区对侧再存 20
print("PN 余额 =", p1.merge(p2).value() - n1.value())

# 3) LWW-Register：钟慢 90 秒，真实写得更晚却被覆盖
def lww(x, y): return x if (x[0], x[1]) > (y[0], y[1]) else y
w_a = (1000, "A", "库存=10")    # A 在墙钟 1000 写
w_b = (910,  "B", "库存=9")     # B 的钟慢 90 秒：真实时刻 1000 才写
print("LWW 结果:", lww(w_a, w_b)[2])
```

```bash
python3 crdt_demo.py
# 顺序一: {'R1': 5, 'R2': 4, 'R3': 7} 16 | 顺序二: {'R1': 5, 'R2': 4, 'R3': 7} 16 | 相等: True
# PN 余额 = 140
# LWW 结果: 库存=10    ← B 真实写得更晚，钟慢 → 被静默丢弃，无任何报错
```

验证两刀：把合并顺序一改成 `r3.merge(r2).merge(r1)`，结果纹丝不动；把 w_b 时间戳改成 1100，LWW 翻转为"库存=9"——时间戳成了唯一裁判。

这节最重要的结论：**除 LWW 外的常用基础 CRDT 都是无损合并，LWW 是唯一有损裁决**。"用了 CRDT 就不丢数据"是面试常见口误——计数器丢不了，寄存器丢的是时间戳小的那次写。

## 4. LWW 的坑：把时钟当裁判

Cassandra 就是 LWW 的天下：同 key 并发写，时间戳大的赢，输方静默丢弃，连"发生过冲突"都不告诉你。删除也一样——delete 是写墓碑，比数据新就遮住它，默认 10 天（gc_grace_seconds）后才真正清除。

坑的根源：**写时间戳通常由客户端按本机墙钟生成**。一台钟慢 5 分钟的应用服务器，它"现在"的写带着 5 分钟前的时间戳，会被别人 4 分钟前发出的写覆盖——没有报错，数据就是不翼而飞。这类工单查遍集群无异常——集群侧本来就一切正常。

Redis Enterprise 的 CRDB（Active-Active 多活）同一条病根：Counter 类型两地各加、相加无损；String 类型 LWW、有损——官方明确要求各实例严格 NTP 同步（商业版能力，开源 Redis 无等价物，评审别混）。

运维对策四条：

1. 集群与客户端统一 NTP，对 offset 斜率与失联告警——时钟纪律是数据正确性问题，不是监控洁癖；
2. 需要显式控制顺序的写，用 `USING TIMESTAMP` 手工指定，不赌钟；
3. 计数场景别用 LWW 字段做 read-modify-write 的 +=，并发必然丢更新——换 counter 表或单写者；
4. 理解墓碑：大量短 TTL 写会造出海量墓碑，是读放大与修复风暴的经典来源。

一句话对比：**G-Counter 的合并不依赖时间，LWW 把时钟当裁判**——裁判会迟到，这就是静默丢写的全部原因。

## 5. 因果序救场：分清"先后"与"并发"

LWW 的病根是墙钟分不清两件事：真实先后，和真并发。向量钟就是来干这个的——给每个版本记上"我见过谁"，两个版本一比：

可比的（有因果关系），安全留新；不可比的（并发），全部保留。这就是 MV-register：并发版本做成 siblings 列表全留着，读出多值，应用层圈一个。Dynamo 论文的原路线，购物车合并是原例。

对照一致性谱系那篇：因果一致的合同是"有因果关系的操作所有人看到的顺序一致，并发写可以各有所见"——MV-register 正是这份合同的数据结构版。向量钟检测并发，寄存器保留并发，裁决交还应用：检测从来不等于裁决。

CRDT 自己也有一条因果暗线：操作型（CmRDT）传操作本身，传输前提是**可靠因果广播**——按因果序不重不漏到达，丢一条就永久少一次 effect。状态型（CvRDT）传状态，对传输层零要求：可丢可重可乱序，gossip 反熵就能当载体。

一句面试答法：**状态型把复杂度记在状态体积的账上，操作型记在传输层的账上**。

## 6. 协同编辑：给每个字符发身份证

多人编辑一份文档是最极端的多主场景：每个浏览器标签页都是独立写入口，离线还能继续写。

OT（Google Docs 一脉）：客户端把"在第 12 个字符后插入 X"发给**中央服务器串行变换**。服务器是唯一真相与顺序仲裁者——本质是软共识、单点串行化，断网即不能编辑，中央服务的伸缩就是天花板。

序列 CRDT（Yjs/Automerge 一代）：文档是一个字符序列 CRDT，**每个字符分配全局唯一 ID**，插入位置算法（Yjs 用 YATA 一类）保证任意顺序应用编辑，最终字符序完全一致。

定序思路不玄【从业者判断】：并发插入同一位置时，谁排前面由字符 ID 与位置规则决定，不由消息到达先后决定——还是交换律，应用顺序不影响最终序。

于是服务器从仲裁者退化成接力棒：只负责转发与存档，不仲裁、不需要共识，甚至可以 P2P。这是 CRDT 给协同编辑最大的架构红利【从业者判断】，也是"本地优先"应用的卖点。

删除呢？还是墓碑。每个字符的 ID 与墓碑都是永久元数据，长文档只增不减持续膨胀——Yjs/Automerge 有压缩与 GC 机制，效果随版本迭代，以官方文档为准。

## 7. 账单与边界：什么时候不该用

换来分区两侧都能写、无仲裁合并、没有 failover；付三张账单：

**元数据膨胀**——墓碑与字符 ID 只增不减，存储与 GC 压力的主要来源。**静默丢写**——LWW 系类型并发只留一个赢家。**收敛不等于对**——购物车合并出两件商品是惊喜，账户合并出两倍余额是事故。

还有个精彩的语义坑，OR-Set 复活判例：删除只能埋掉"当时观察到"的 tag；分区对面并发地再添加同一元素（带新 tag），删除埋不到它——合并后元素复活。add-wins 是语义不是 bug，对策是元素用唯一 ID，让复活的成为可区分的新成员。

什么时候不该用，一张表说清：

| 需求 | 选谁 | 为什么 |
|---|---|---|
| 写完立刻读到（读己之写） | 共识 | CRDT 异步收敛，不承诺新鲜 |
| 全局唯一（锁、选主、扣款、不超卖） | 共识 | 唯一性本质是全序仲裁，交换律给不了 |
| 多地域低延迟写、断网可写 | CRDT | 跨地域 quorum 往返延迟不可行 |
| 计数、点赞、协作内容 | CRDT | 合并语义自然，无损或可解释 |

两条边界，值一次方案评审。**CRDT 与共识不是二选一，是按数据分片的组合**：配置与成员关系（要唯一）走共识，业务计数与协作内容（要可写）走 CRDT——Nacos 的 Distro/Raft 双协议正是这个模式的产品化。以及：CRDT 只保证它管辖的数据结构收敛——协同文档收敛了，落库 MySQL 那一秒还是要单写者。

## 8. 现在就能做的事

跑第 3 节的脚本，换三种合并顺序各跑一遍，"任意顺序收敛"从结论变成体感；再把 w_b 的时间戳改成 1100，看 LWW 翻转——你的 NTP 质量决定它每天裁得对不对。
