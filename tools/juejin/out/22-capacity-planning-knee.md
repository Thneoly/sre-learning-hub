# “扛住了 1000 并发”，然后呢？

老板在会上问：“大促流量翻倍，现在的集群接得住吗？”

你翻开上季度的压测报告，结论栏写着：“支持 1000 并发，通过。”然后你发现这句话回答不了任何问题——1000 并发是多少 RPS？瓶颈在哪？流量翻倍后最先死的是什么？

更扎心的是，“扛住了 N 并发”在工程上接近废话：**“没挂”只说明负载没到瓶颈，而你没记录瓶颈在哪，等于测试白做**。压测真正值钱的产出只有两个数——**拐点出现在多少 RPS，当时第一个饱和的资源是什么**。容量规划的全部后续，都是从这两个数字出发的外推。

这篇把链路走完：压出拐点、定水位、外推副本数、复验外推，最后给一份能过评审的报告骨架。

## 一、拐点：吞吐-延迟曲线上最值钱的那一段

正经压测的产出不是一句话，而是一张**吞吐-延迟曲线**：

```text
 吞吐 / 延迟
   │                          吞吐 ──●───●───╮ ← 平台期：某资源打满，RPS 加不动了
   │                 ●────●──●            ╰─● ╰● ← 过载区：队列堆积，吞吐反降
   │           ●───●       p99 ─────────●●●  ← 拐点后指数式抬升
   │       ●──╯      p99 ──●──●
   │  ●╋── p50 ──●─●──●──●──●──●──●─────────  ← 线性区：延迟平稳
   └───┼──┼────┼────┼────┼────┼────┼────→ 负载（RPS）
     线性区    拐点(knee)    平台期      过载区
```

| 区域 | 特征 | 此时要回答的问题 |
|---|---|---|
| 线性区 | RPS 涨、p99 基本不动 | 日常余量；容量规划只用这段的斜率 |
| 拐点 | p99 快速抬升、吞吐增速放缓 | **瓶颈是什么资源？** 压测最值钱的一段 |
| 平台/过载区 | 吞吐封顶甚至反降、错误率上升 | 限流该不该接、超时会不会级联 |

为什么盯 p99 不盯平均？设 100 个请求，99 个 10ms、1 个 1010ms，平均 20ms 看着健康，p99=1010ms 才是真相。更狠的是扇出放大：页面聚合 50 次调用，单次 1% 概率慢，页面撞上至少一次慢调用的概率约 39.5%（`1-0.99^50`）——链路越长，尾部越要命。

读曲线的纪律：**p99 从哪一级负载开始跳档，拐点就在哪一级**。用 k6 的 ramping-arrival-rate 做阶梯加压（100→200→400→800 RPS），每级至少数千个请求、持续 1 分钟以上——200 个样本算出的 p99 是噪声。

## 二、先排掉一颗雷：闭环压测会抹平拐点

很多人压不出拐点，不是系统没有拐点，是负载模型把拐点藏起来了。

压测分两种流量模型。**闭环**钉死“同时在系统里的请求数”：系统一变慢，虚拟用户就自动放慢发请求的节奏，饱和被负载发生器自己消化——延迟永远“体面”。**开环**钉死“每秒到达多少请求”：系统消化不了就排队，队列延迟直接进 p99，饱和点无处可藏。

机理一句话：Little 定律 L=λW。闭环钉死 L，系统变慢时到达率 λ 自动回落；开环钉死 λ，延迟涨多少全由系统自己扛着排队。

一个很典型的对比：同一服务，`constant-vus=100` 测得 p99=50ms，换 `constant-arrival-rate=2000/s` 测得 p99=800ms。哪个可信？**差 16 倍本身就是发现**：2000 RPS 已经逼近或越过拐点——下一步是找瓶颈资源，不是争论哪个数字“对”。

顺带埋掉另一个误区：**并发数不是稳定的负载刻度**。按 Little 定律，RPS ≈ 并发数 ÷ 平均响应时间——100 VU、响应 200ms 时约 500 RPS，恶化到 1s 后只剩 100 RPS。报告一律以 RPS 为横轴。模型怎么选：用户会话型看闭环，秒杀、推送这类“请求照涌”的形态必须开环。

## 三、USE 方法：利用率没红，用户已经在付 p99 的账

拐点找到了，日常水位怎么盯？“看 CPU 利用率”不够。USE 方法（Brendan Gregg）对每类资源问三问：利用率 U（忙不忙）、饱和度 S（排队多久）、错误 E（坏没坏）。

为什么利用率不够？排队等待时间不随利用率线性增长：≤50% 几乎不用等，80% 开始离开地板，90% 之后每加一个百分点都在跳。用户感知的是排队延迟，不是利用率——等利用率“变红”再动手，用户已经在付 p99 的账。

**第一节的 p99 拐点，本质是饱和度指标在系统外的投影**：p99 跳档的那级负载，回头看资源快照，必有一个 S 列指标先抬头。最典型的指纹：容器 CPU 用量只有 limit 的 60%，p99 却按 100ms 周期性尖刺。查 cgroup 节流计数：

```bash
POD=$(kubectl get pods -l app=<app> -o jsonpath='{.items[0].metadata.name}')  # <app> 换成你的 selector
kubectl exec "$POD" -- grep -E 'nr_periods|nr_throttled|throttled_usec' /sys/fs/cgroup/cpu.stat
# nr_throttled 增长 ← CPU“不高”却已饱和的实锤：CFS 配额在 100ms 周期内提前用完即挂起
# 注意 cgroup v2 该文件前几行是 usage/user/system 用量，节流字段在后面，别用 head 截断；
# cgroup v1 路径不同，是 /sys/fs/cgroup/cpu/cpu.stat，以官方文档为准
```

据此把水位切三档（通用起点，按自家压测数据校准）：

| 档位 | 含义 | 动作 |
|---|---|---|
| 绿 <60% | 日常水位 | 无动作，季度复核 |
| 黄 60%~75% | 计划线 | 立项扩容或优化，每周看趋势斜率 |
| 红 >75% | 行动线 | 72 小时内扩容或降级预案待命 |

到了 K8s，“CPU 利用率”还得再拆——同一个数字至少有三个分母、四本账，混用是容量报告最常见的错误：

| 账本 | 算式 | 回答什么 |
|---|---|---|
| 调度账 | Σrequests / allocatable | 还能塞多少 Pod（>100% 是超卖，设计如此） |
| HPA 账 | usage / requests | 弹性刻度（HPA 内部算的就是它） |
| 拥挤账 | usage / limits | 真实挤压；逼近 100% 即节流/OOM 前夜 |
| 节点账 | Σusage / allocatable | 要不要买机器（唯一能外推机器数） |

判读纪律：先看拥挤账定“谁在疼”，再看调度账定“还能塞多少”，最后用节点账定“要不要买机器”。describe/top 这类命令采不到拥挤账（它要拿每个 Pod 的实时 usage 对照各自的 limits），得单独补采：

```bash
kubectl describe node $(kubectl get nodes -o jsonpath='{.items[0].metadata.name}') \
  | sed -n '/Allocated resources/,/Events:/p'   # 调度账 + 超卖上限账（Σlimits/allocatable，不在四本账表内）
kubectl top nodes    # 节点账的分子
kubectl get hpa -A   # HPA 账（TARGETS 列就是 usage/requests）
kubectl top pod -A --containers   # 拥挤账的分子（每容器实时 usage，对照下一行的 limits）
kubectl get pods -A -o custom-columns=NS:.metadata.namespace,NAME:.metadata.name,CPU_LIMIT:.spec.containers[*].resources.limits.cpu
# 有 Prometheus 的话，拥挤账直接用 container_cpu_usage_seconds_total ÷ kube_pod_container_resource_limits 更省事
```

顺带一条硬规则：CPU 超卖顶多争抢，内存没有“超卖后限流”这回事——超卖的内存真用满就是 OOM 驱逐，所以内存超卖度要给得比 CPU 更保守。

## 四、三步外推：把拐点变成副本数

三步外推法：

1. **单副本安全容量** = 拐点 RPS × 水位系数（0.6~0.75）。留的不是余量，是突发、缓存冷启动、单副本故障后重排这些必然发生的事。
2. **目标负载** = 峰值 RPS × 增长系数。峰值取实测（网关 P95 流量），不取拍脑袋的“设计值”。
3. **副本数 N** = ceil(目标负载 ÷ 单副本安全容量) + 1。**+1 就是 N-1 原则**：峰值时刻挂掉任何一个副本，剩余副本仍在安全水位内。

纸面算例（示意值）：

```text
拐点 400 RPS（CPU 饱和），水位系数 0.7
安全容量 = 400 × 0.7 = 280 RPS/副本
目标负载 = 峰值 950 × 增长 1.3 = 1235 RPS
N = ceil(1235 ÷ 280) + 1 = 5 + 1 = 6 副本
N-1 校验：剩 5 副本 × 280 = 1400 ≥ 1235，通过
```

再把三个系数各改一档重算（0.6/0.8、增长 1.1/1.5），体会结论对系数的敏感度——**报告里要展示敏感性，而不是只给一个数**。

但外推有一条必须写进报告的边界：线性外推假设“副本翻倍、拐点翻倍”，这只在瓶颈是**无共享资源**（本副本 CPU、内存）时成立。瓶颈若是共享的——DB 连接池、下游配额、中心缓存带宽——副本翻倍拐点不动，甚至因争抢加剧更糟。

所以外推之后必须**加倍复压验证**：

```bash
kubectl scale deploy/web --replicas=12   # 原为 6，翻倍，等 rollout 完成
BASE_URL=http://<目标> k6 run --out web-dashboard mixload.js   # 同一脚本复压，<目标> 换成压测入口
```

**拐点偏差超过 20%，就是撞上了共享瓶颈**——继续加副本无效，要么拆瓶颈（读写分离、连接池复用、配额扩容），要么改架构。这份对比数据就是报告第 3 节“外推边界”的证据。

N-1 别只停在算式里，用一次真实的单副本下线验证延迟仍在 SLO 内：

```bash
# 负载压到目标负载（全量，如算例的 1235 RPS）并稳住后，删一个副本，观察 p99 与错误率
# 注意：别只压一半负载——6 副本摊 617 RPS 才约 103 RPS/副本，删一个也远低于 280 的安全水位，
# 测试必然“通过”，但证明不了峰值时刻 N-1 成立
kubectl delete pod $(kubectl get pods -l app=web -o jsonpath='{.items[0].metadata.name}')
```

在该负载下 p99 不跳档、零错误，N-1 假设才成立；跳档了，回头加副本或提水位系数。这就是一次最小化的稳态假设验证——混沌工程的方法，拿容量问题当靶子。

## 五、一份能交给老板的报告长什么样

链路走完，落成可评审的文档。骨架六节：

```markdown
# <服务名> 容量评估报告 YYYY-MM
1. 结论先行：安全容量 X RPS，可支撑至 YYYY-MM（按周增速外推）；
   建议动作（扩容至 N 副本 / 优化瓶颈 / 无动作）+ 责任人 + 期限
2. 输入：压测日期与脚本版本、拐点 RPS、饱和资源、生产峰值 RPS（网关 P95）、错误预算状态
3. 外推过程：水位系数、增长系数、N-1 算式；外推边界与共享瓶颈排查结论
4. 水位快照：四本账 + 中间件基线，各附一行判读
5. 风险与依赖：共享瓶颈、单副本故障演练结果、预算约束
6. 复核安排：重跑压测的条件（流量涨 20% / 大版本发布 / 架构变更）
```

中间件各用各的尺子：Redis 看内存水位（<80%）与 evicted_keys，MySQL 看连接水位（<80%）与缓冲池命中；每张表五行以内，行末标绿/黄/红。

评审专盯三个最容易写虚的地方：

**“外推边界”写“无”等于没查**——共享瓶颈要给排查证据，就是第四节的复压数据。

**第 1 节别只给一个数**——系数敏感性摆出来，给决策者看置信区间，而不是伪精确。

**第 6 节为什么写“条件”不写“每季度”**——容量漂移的驱动因素是事件（大版本发布、新依赖、流量结构变化），不是日历；重跑条件挂进发布检查单，让复压被风险事件触发，日历只做兜底。

还有一句定性值得写进开头：**容量不足从来不是性能问题，是可用性问题**——过载的延迟与失败直接烧错误预算。可用性目标越高，水位系数和 N-1 余量就该越保守。

## 六、预埋一个反方：有 HPA 自动扩容，还要容量规划干嘛？

一定有人反驳：“配了 HPA，流量来了自己扩，规划是多余的。”

HPA 是响应式扩容，滞后是一条链：指标窗口聚合 → HPA 计算周期 → 新 Pod 调度和拉镜像 → 应用预热（JIT、连接池、本地缓存）。**每一环加起来 3~10 分钟**，而早高峰流量爬坡可能只要 5 分钟——水位冲过红线后扩容才到，p99 已经抖过了。

正确的关系是分工：流量可预测的部分用日历解决（定时预扩），**不可预测的才交给 HPA 兜底**。容量报告给出“黄线何时到”的趋势斜率，预扩在那之前把动作做完；两者都不该由告警触发——告警响时，用户已经在付延迟的账。

另一个反问是“压测环境跟生产不一样，压了也白压”。值得半个让步：环境差距确实存在，但拐点方法论的产出是“瓶颈在哪、量级、改动前后的相对变化”，加倍复压比的正是同一环境的前后差异；要绝对精确就上全链路压测，那是另一档投入，不是否定规划的理由。【从业者判断】

## 七、现在就能做的三件事

1. **30 秒，采水位**：跑第三节那几条 kubectl 命令（含拥挤账那条，别漏），对每个数字回答 USE 三问——U 高的是哪个？S 证据在哪？写成一页快照，标上日期。
2. **2 分钟，揪一个藏起来的饱和**：挑一个 p99 有尖刺的 Pod，看 `cpu.stat` 的 `nr_throttled` 是否增长——利用率视角看不见的饱和，一条命令现形。
3. **本周，把旧压测报告改写成拐点报告**：翻出原始数据，找到 p99 跳档的那级 RPS 和当时的资源快照，按第五节骨架重写前三节。旧报告若只有一句“扛住 N 并发”——恭喜，你已经知道下个季度该干什么了。

容量规划不是玄学，是“拐点 → 水位 → 外推 → 复验”四步代数。拍脑袋给机器数的时代，该翻篇了。
