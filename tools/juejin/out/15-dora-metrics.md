# DORA 四指标：部署越频繁，故障反而越少

"你们团队 DevOps 做得怎么样？"

"还行吧，K8s 上了，GitLab CI 也配了，发布比以前快多了。"

如果你也只能答到这一层，先给你一个数：精英团队和低效团队修同一个故障，时间差 2604 倍——第八节给你四步（五条 git 命令），30 秒跑完、5 分钟读出你的基线，看看你站在哪一端。

## 一、转型之后，最怕的是"感觉良好"

做过传统运维的人，对下面这个场景都不陌生：开发的目标是多交付，运维的目标是别出事，两边的考核方向完全相反。出故障后第一句话永远是"你们到底改了什么"，开发的回答永远是"在我机器上是好的"。

这堵墙的产物，是季度末 200 个变更一次性抛过来，是发布日通宵守着一屏日志，是出事之后先找人背锅再看系统。后来我们开始转型：学容器、学 K8s、搭 CI/CD，工具换了一轮。

但工具换完，新问题来了：老板问"交付为什么还是慢"，开发问"稳定性到底有没有变好"，你怎么回答？靠体感？体感会被最近两次事故主导，也会被最近两次顺利发布主导，两头都不靠谱。

DevOps 领域给这个问题准备了一个客观答案：DORA 四指标。它是《Accelerate》一书背后的研究产出，也是国内外 SRE 岗位面试的高频考点——工具谁都能学，能不能量化自己的交付，才见功力。

## 二、四个数字的来历：三万人的数据，不是拍脑袋

先交代出处。DORA 是 DevOps Research and Assessment 的缩写，由 Nicole Forsgren 等研究者发起，后来团队被 Google 收编。四指标的体系化表述出自 2018 年出版的《Accelerate》（Nicole Forsgren、Jez Humble、Gene Kim 合著）。

研究的数据底盘要分层说：《Accelerate》浓缩了 2014–2017 年四年的研究、约两万三千份问卷；DORA 年度报告此后持续验证，本文第五节引用的 2019 年报告，口径是累计六年、超过 31000 名从业者。做法不是专家闭门列 KPI，而是用统计方法（聚类分析）把组织分档——年度报告分成精英、高效、中效、低效四档，《Accelerate》书里是高、中、低三档——再反推：是哪些实践把组织推向了精英档。

研究还专门控制了行业、公司规模、从业年限这些干扰变量。结论很硬：不管你是万人厂还是五人小团队，做对了实践的团队，数字就是更好。这一点对国内团队尤其重要——"我们规模特殊""我们行业特殊"在这份数据面前站不住。

更有说服力的是，研究把交付绩效和业务结果挂了钩：高绩效组织在盈利能力、市场份额这些组织级目标上同样显著占优。这让四指标跳出了"技术团队自嗨"，成了能写进经营语言的一页纸。

结论里最反直觉的一条：**快和稳是正相关，不是取舍关系**。部署越频繁的团队，恢复故障反而越快、失败率反而越低。因为批量越小，单次变更风险越低，出了问题也越好定位——变更集合就一个 commit。

这条结论直接推翻了"多发布等于多风险"的传统运维直觉，也是小批量发布、持续交付这一整套实践的数据地基。

## 三、为什么偏偏是这四个数字

候选指标其实有几十个，最后留下这四个，筛选标准大致三条。

第一，它们都是结果指标，不是过程指标。衡量的是交付的结果（多快、多稳），而不是"你们用了什么工具""有没有每日站会"。装了 Jenkins 不等于任何事，数字只认结果。

第二，它们都能从既有事件里算出来：部署记录、commit 时间戳、故障单。不需要团队为度量专门填一张表——凡是需要人手工填报的指标，最后都会变成填表艺术。

第三，两快两稳，结构上防作弊。只优化速度不看稳定，或反过来，都会在另外两个指标上露馅。这个组合本身就是一套互相校验的设计。

顺带一个加分点：这四个指标能映射回《The Phoenix Project》的三步工作法——部署频率和前置时间量的是"流动"，MTTR 和失败率量的是"反馈"。理念层的框架和度量层的数字，在这里对上了。

## 四、四个指标逐个拆：运维人都有体感

### 1. 部署频率：多久往生产发一次

定义很直白：多久向生产环境部署一次，方向是越高越好。它衡量的是"发布的日常程度"——发布是像喝水一样随时能做的事，还是像放烟花一样一个月搞一次的大事。

传统运维对这个指标体感最深：发布等于变更窗口，等于晚上十点后，等于三个人在场盯着。频率被流程和恐惧锁死，而不是被技术锁死。

### 2. 变更前置时间：commit 到跑在生产上要多久

注意不是"需求到上线"，而是从代码 commit 到它真正跑在生产上的耗时，越短越好。

这个指标最能暴露流程浪费。一个 2 行的 nginx 配置改动，执行只要 30 秒，但走完工单、评审、窗口审批要 3 天——时间几乎全部耗在排队上。前置时间长的团队，瓶颈几乎从不在工具，在等待。

### 3. 平均恢复时间（MTTR）：坏了多久能修好

社区通行口径是"从发现一个影响用户的故障，到把它修复"的耗时，越短越好——计时起点取发现，不是发生。对运维背景的读者，这是最亲切的一个——它就是你们一直在追的"故障处理时长"，DORA 只是把它和交付指标放进了同一张报表。

实践里常再拆成两段：发现时间（告警灵不灵）和恢复时间（回滚、预案熟不熟）。注意这是运维侧的扩展口径，"从发生到发现"那一段并不在这个指标的计时范围里——做基线时先声明口径，别拿它直接对比官方阈值。发现慢是观测问题，恢复慢是演练和自动化问题，诊断时必须分开看。

> 小知识：DORA 后来的报告把它改叫 Time to Restore Services（服务恢复时间），口径以官方文档为准。面试里两个名字都要听得懂，说的是同一个东西。

### 4. 变更失败率：多少部署会闯祸

引发故障、回滚或需要补救的部署，占总部署数的比例，越低越好。它是四个里把"快"和"稳"直接挂钩的那根线：提速提得对不对，看它。

## 五、精英和低效团队，差的是数量级

以 2019 年 DORA 报告口径为例：

| 指标 | 精英团队 | 低效团队 | 差距 |
|---|---|---|---|
| 部署频率 | 按需，一天多次 | 一月到半年一次 | 208 倍 |
| 变更前置时间 | 小于 1 天 | 1~6 个月 | 106 倍 |
| 平均恢复时间 | 小于 1 小时 | 1 周到 1 个月 | 2604 倍 |
| 变更失败率 | 0~15% | 46%~60% | 约为低效团队的 1/7 |

注：阈值逐年有微调，近年还引入了可靠性维度，引用时以官方文档 dora.dev 的最新报告为准。2604 倍这个数字出自 2019 年 DORA 报告原文，官方未披露具体推导方法。

208 倍的部署频率差距什么概念？精英团队一天发的次数，低效团队要发上七个来月。2604 倍的恢复时间差距，本质是"告警加回滚自动化"和"翻日志加人肉定位"的差距。失败率这行换个体感：精英团队每 7 次发布才出 1 次事，低效团队两次发布就要出一次。

还有一点容易被忽略：精英团队靠的不是英雄，是实践组合。trunk-based 开发、自动化测试、持续交付、可观测性——这些实践在研究里全部与高绩效强相关。换句话说，差距是可以靠工程手段追的。

两个提醒。第一，别把这些数字背成永恒标准，历年口径有调整，以官方为准。第二，比绝对值更重要的是趋势——你们的部署频率从月提到周，比"离精英线还差多少"更有讨论价值。

## 六、两条铁律：联看，且不考核个人

第一，四指标**必须联看**。一天发 50 次、失败率 40%，不是精英，是灾难。只报部署频率不报失败率的团队，多半在选择性地汇报。

第二，度量用来改进，**不用来考核个人**。一旦进绩效，行为立刻变形：拆无意义的小提交刷频率、隐瞒小故障拉低失败率——古德哈特定律的标准翻车现场。指标只进团队回顾会，跟自己的基线比，不跟人比。

## 七、指标是探照灯，别拿它当指挥棒

拿到基线之后干什么？四个指标各对应一组明确的杠杆，对号入座：

- 部署频率低：批量发布、变更窗口卡死 → 上 CD 自动化，拆小批量
- 前置时间长：画价值流，找最大的那段等待 → 审批左移成 MR 评审加自动门禁，而不是给审批加人
- MTTR 长：先分清发现慢还是恢复慢 → 发现慢补观测和告警，恢复慢补回滚演练与 Runbook
- 失败率高：看出事的变更有没有共同类型 → 缺哪层测试补哪层

每做一个改动，回到指标上看数字动没动。这就是"实验、度量、改进"的闭环，也是四指标存在的最终目的——指标是探照灯，不是指挥棒：探照灯帮你照出下一步该拆哪堵墙，指挥棒只会逼着团队为数字表演。

## 八、实战：用 git log 30 秒跑出你的基线

理论说完，上手。前提假设：你们的发布对应打 tag 或合主干。在一个有发布历史的仓库里，Git Bash 直接跑。

第一步，看部署频率的原料——近 90 天每天的提交数：

```bash
cd /path/to/your/repo   # 进入任意一个你有发布历史的仓库

git log --since="90 days ago" --date=short --format="%ad" | sort | uniq -c
```

输出是一张直方图，左边的数字是当天提交条数。注意：提交频率只是部署频率的代理值——只有"发布即合主干"的团队两者才接近，否则会高估。哪怕只当节奏参考，也比体感准。

如果直方图每月只有一个尖峰，你们的节奏就是月度批量，问题在流程，不在代码。

第二步，看发布事件序列——所有 tag 按创建时间排：

```bash
git for-each-ref refs/tags --sort=creatordate \
  --format="%(refname:short) %(creatordate:short)"
```

如果这张列表是空的，恭喜，你发现了第一个问题：发布没有可追溯的事件序列，四指标连原料都没有。

第三步，算单个版本的前置时间下限。取最近一个 tag（假设叫 v1.8.3）：

```bash
# commit 发生时间
git show -s --format="%ai" "$(git rev-parse v1.8.3)"

# tag 创建（即发布）时间
git for-each-ref refs/tags/v1.8.3 --format="%(creatordate:iso)"
```

两个时间戳的差，就是这个版本前置时间的下限——真实值只会更长，因为 tag 之后还有部署动作。对最近 3 个 tag 各算一次，取中位数，比平均值抗干扰。

一个前提：这套算法要求注解 tag（用 git tag -a 打的）。轻量 tag（git tag v1.8.3 这种）没有独立时间戳，%(creatordate) 会回落为所指向 commit 的提交日期——第二步的排序和这一步的差值都会失真，差值趋近于零不代表你快，只说明 tag 打法不对。

第四步，粗估变更失败率。如果你们的失败发布通常伴随 revert 提交：

```bash
git log --since="90 days ago" -i --grep="revert" --oneline | wc -l
```

revert 数除以近 90 天的 tag 数，就是个粗略失败率。MTTR 是四指标里唯一 git 算不出来的，老老实实翻故障单——如果连故障单都没有，这本身就是最大的发现。

30 秒的命令，5 分钟的解读，你会得到：一张交付节奏图、一列发布事件、一个前置时间中位数、一个粗估失败率。这就是基线，之后所有改进都拿它对照。

一个诚实的警告：样本太小时（比如一个季度只有三五次发布），单个数字没有统计意义。看趋势、看分布，别为 1% 的波动专门开一次会——那也是度量变形的一种。

## 九、给转型路上的你：四指标是"共同语言"

第一，它是你和开发对话的通用语言。以前你只能说"发太频繁会出事"，现在可以说"我们失败率 50%，已经踩进低效区间，先补测试门禁再谈提速"——同样一句话，后者能上会。

第二，它是 DevOps 和 SRE 的接口。DevOps 优化交付流程，SRE 优化运行时可用性，错误预算是两者的桥：预算烧光就减速发布。四指标里的 MTTR 和失败率，正是 SRE 值班体系要接住的部分。

第三，它是能写进季度汇报的一页纸。四个数加一条趋势线，就是"交付效能"最硬的经营语言——比"本季完成发布 12 次"更能让管理层看清你们是在变好还是原地打转。

## 结尾：这周就能做的三件事

1. 找一个你手头有权限的仓库，把第八节那四步（五条 git 命令）跑一遍，结果记成一页基线，标上日期。
2. 花 30 分钟画一次价值流：最近一次上线从写完代码到用户用上，每一步的等待时长和处理时长。找出占比最大的那段等待——它大概率不需要新工具，只需要砍流程。
3. 以三个月为周期，只挑一个指标改进（推荐部署频率，从月到周），期间 MTTR 和失败率不许变差——这就是"快稳联看"的实践版。

下次再有人问"你们 DevOps 做得怎么样"，别再答"还行"——甩出这四个数，和上季度的自己比。

最后重复一遍：度量是探照灯，不是指挥棒。指标只进回顾会，不进绩效表。
