# 为 1% 的查询付 100% 的索引费：ELK vs Loki 的成本账

A 团队的 ELK 集群 30 天保留 12 TB，老板问：日志凭什么花这么多钱？B 团队听了劝迁到 Loki，存储成本砍掉一个数量级，三周后 push 开始整批返回 429——日志在丢，面板上却一片安静。

两个团队都不是工具不行，是同一笔账没算明白：**ELK 在写入时预付全款，Loki 把钱挪到了查询时**。钱没有消失，只是换了支付时点——选型就是选你在哪个时点付、付给谁。

这篇只算账：索引怎么膨胀、分片副本怎么放大、标签打错怎么撞限、LogQL 查不动什么，最后给一棵决策树。

## 一、根本差异：你在为谁的查询付索引费

ES 的快是有实体的：每个 text 字段写入时先分词，每个词项（term）进倒排索引，posting list 记着"哪些文档含这个词"。搜 error 是查表，毫秒级。

代价是索引体积：**倒排索引常见是原始日志的 1~3 倍**，取决于分词与字段量。你搜得快，是因为每条日志的每个词都已经提前交过索引税了。

Loki 从反面设计：只索引 label set——一组标签键值对决定一条流（stream）的身份；正文原样压缩成 chunk（默认约 1.5 MB 一块）扔进对象存储，JSON 日志常见压缩 10~20 倍，索引体积只有数据量的零头。

查询路径的分歧就在这里：

```text
ES：    error AND service:payment
        └→ 查倒排表直接得到文档 id → 快，钱在写入时付过了

Loki：  {app="payment"} |= "error"
        └→ 标签查索引锁定流 → 拉回 chunk 解压 → 逐行扫描
           标签越准扫得越少，没有标签就退化为暴力全扫
```

回到标题那个问题：你的日志查询里，有多少是不带标签边界的即兴全文搜索？现实是，运维日志的排查几乎总带着边界来——哪个集群、哪个 namespace、哪个应用、哪段时间。**为 1% 的即兴查询给 100% 的日志建全量倒排**，就是 ELK 成本失控的结构性来源。

## 二、ES 的成本账：倒排、副本、不分层各放大一轮

把日增 200 GB 场景的账原样摆出来：

```text
原始日志        200 GB/天
单分片目标      10~50 GB（日志场景偏上限，取 40 GB）
主分片数        200 ÷ 40 ≈ 5 个
副本 1 份       200 × 2 = 400 GB/天磁盘
保留 30 天      12 TB
```

这 400 GB/天里，倒排索引常常占掉一半以上——第一节那 1~3 倍不是虚的。你在用最贵的 SSD 存"查询的预备答案"。

分片还有条铁律：文档落哪个分片由 `shard = hash(routing) % 主分片数` 决定，**主分片数建后不可改，改了旧文档全部失联**；副本数可随时调，容量估错的正解是 rollover 出新索引加别名切换。

副本管读扩展与容灾，不管写扩展——写要主分片加全部副本都成功才返回，副本越多写越慢。

heap 则是另一笔线性账。【从业者判断】ES 是 JVM，堆通常给到机器内存一半、压在 32 GB 上下，堆大小决定你能同时养多少分片、并发查询和 merge——账单里 CPU、内存和磁盘一样线性涨。

不信可以自己量：

```bash
# 看每个索引的真实磁盘占用（pri.store.size 为主分片体积）
curl -s "http://localhost:9200/_cat/indices/logs-*?v&h=index,docs.count,pri.store.size,store.size"
# 预期：store.size ≈ pri.store.size × (1 + 副本数)
```

**ES 的账单是三层乘法**：倒排放大一份、副本放大一份、不分层的热存储再放大一份。

## 三、Loki 的标签纪律：高基数在日志侧不是贵，是不可用

前面指标篇（37）拆过：一个 user_id label 能把 Prometheus 打爆。日志侧同源但更狠——指标侧高基数的下场是 OOM，是"贵"；Loki 侧高基数的下场是**拒绝写入，日志整批丢**。

连锁反应三步：user_id 进 label，每个活跃用户开一条独立流，流数从 O(服务数) 变成 O(用户数)；ingester 为每条流维护内存 chunk 状态，TSDB 索引跟着膨胀；流变碎变小，chunk 还没攒满就 flush，对象存储上海量小对象，写放大恶化。

最后撞上 max_global_streams_per_user 或每流速率限制，push 返回 429/400，丢的是整批。

更隐蔽的变体是流抖动（stream churn）：deployment generation、发布哈希这类"每次发版全体换一轮血"的值放进标签——每个值本身低基数，但取值频繁轮换，旧流冷却、新流诞生，flush 与索引压力同样失控。

promtail/Alloy 的 K8s 发现元数据里默认就带着 Pod 的全部 label——【从业者判断】把 pod_template_hash 透传进 Loki 标签，就是**这类事故的标准姿势**。

名单直接背：

```text
可以进 label（有界、能收窄扫描范围）：
  cluster、env、region、namespace、app/job、container、node_name、level

绝不进 label（无界，或界随流量增长）：
  user_id、session_id、request_id、trace_id、order_id、
  ip、email、带 query 参数的完整 url、分钟级时间粒度
```

判定口诀一句话：**取值集合随流量线性增长的字段，一律留在正文**，查询时用 `| json` 运行时提取。运行时提取的是临时字段，不占索引不占标签——这就是便宜的前提。

```bash
# 看自己离悬崖多远：当前生效的流数与速率限制
curl -s http://localhost:3100/config | grep -A3 'max_global_streams\|per_stream_rate_limit' | head -8
# 预期：能看到 per_stream_rate_limit: 3MB 一类的默认值（随版本以 /config 实际输出为准）
```

## 四、LogQL 能查什么，查不动什么

标签纪律守住了，LogQL 的表达力完全够用。它能做的两类事：

```text
# 1. 日志查询：标签选流 + 行过滤 + 运行时提取
{namespace="default", app=~"logger|api"} |= "error"
{namespace="default"} |~ "time(d )?out"          # RE2 正则
{namespace="default"} | json | __error__="" | duration_ms > 400

# 2. 度量查询：把日志行折叠成指标，与 PromQL 同构
sum by (level) (count_over_time({app="logger"} | json [5m]))
quantile_over_time(0.99, {app="logger"} | json | unwrap duration_ms [5m])
```

用 curl 直接试（这就是 Grafana Explore 在后台发的请求）：

```bash
curl -sG "http://localhost:3100/loki/api/v1/query_range" \
  --data-urlencode 'query={job="app"} | json | level="error"' \
  --data-urlencode 'since=1h' --data-urlencode 'limit=5' \
  | jq -r '.data.result[].values[] | .[1]' | head -5
# 预期：返回若干含 "level":"error" 的原始日志行
```

查不动的是另一面。裸 `{}` 不合法，流选择器必须至少一个标签匹配；只有宽标签的全库全文搜索（只带一个 env 就想捞一个关键词）会退化为对海量 chunk 的暴力扫描——拉回来、解压、逐行正则。ES 拿倒排查表毫秒级做完的事，Loki 拿 CPU 和时间硬扛。

由此推出一条工程纪律：**ruler 告警规则里的 LogQL 必须便宜**——用标签收窄、加行过滤器，别在告警规则里跑大范围 `| json` 扫描，否则 ruler 会成为 Loki 自己最大的查询客户。

**LogQL 的能力边界就是标签的收敛能力**：标签准，Loki 又便宜又快；标签宽，它比 ES 还慢。

## 五、冷热分层与对象存储：两种成本模型

ES 自己也知道热存储扛不住，正解是 ILM 生命周期：

```text
hot    SSD、副本 1、接受写入与高频查询
warm   只读、force merge 成单 segment、副本降 0、换 HDD
cold   searchable snapshot 挂对象存储
delete 到期物理删除
```

每一层降一档价格，整体成本能降数倍。但注意方向：**ES 是靠分层把自己一步步变得像对象存储**。

Loki 生在终点：chunk 与索引的第一站就是对象存储（S3/MinIO/本地盘），每 GB 成本最低；最近的数据常驻 ingester 内存，那是为低延迟可见，不是为分层。代价是对象存储成为一等公民依赖——存储故障等于读写全断，运维重心在存储本身。

但分层和对象存储都救不了"写得太多"。日志侧最狠的成本杠杆在写入端：**行数本身就是 cardinality**。debug 级日志全量保留，等于为"将来可能看一眼"支付 100% 的存储与索引。

分级采样（debug 采样留 1%、error 全量）、丢健康检查日志、按 team 路由不同保留期——不是所有日志都值同样的钱。这一刀下去，比换任何存储后端都省。

## 六、落地形态：谁全量、谁热点

混合是当下的主流答案：海量低价值日志进 Loki（长保留、低成本），少量高价值审计/业务日志进 ES（强检索、短列表），在采集端用 OTel Collector 或 Fluent Bit 路由分流。

反过来——ES 扛全量、Loki 查热点——【从业者判断】基本不成立：让最贵的存储扛最大的量，让最需要低延迟的查询走扫描路径，两边都用在了自己最弱的一面。

两个补件：ES 前面加 Kafka 削峰（保留 12~24h），把存储故障从"丢数据风险"降级为"延迟入库"；Loki 侧记着 compactor 的 retention 必须显式开启，不然"自动过期"只是幻觉。

**混合只有一个正确方向：便宜的存全量，贵的查热点。**

## 七、选型决策树

```text
开始
 ├─ 查询模式是"任意关键词全文捞"？（安全审计、合规取证、给用户的搜索框）
 │   └─ 是 → ELK，且只把这几类日志给它
 ├─ 需要跨字段复杂聚合 / join / 运营报表，日志是分析对象本身？
 │   └─ 是 → ELK
 ├─ 基础设施/K8s 运维日志，查询总带 namespace/app/时间窗边界？
 │   └─ 是 → Loki（默认答案）
 ├─ 两类查询形态都真实存在、量都不小？
 │   └─ 混合：Loki 全量长保留 + ES 热点短保留，采集端分流
 └─ 量小（几十 GB/天内）且没有专职运维？【从业者判断】
     └─ 单 Loki；没有 JVM 和分片调优，一个组件加对象存储就能跑
```

决策顺序有讲究：先问查询形态，再问量级与团队，最后才轮到混合——命中混合的资格是"两类查询都真实存在"，不是"选不出来"。

## 八、反方观点：很多团队两个都要，是浪费

混合被滥用了。两套后端意味着存储双份、采集链路双份、权限与保留策略双份，新人还得同时学 KQL 和 LogQL——每一样都是长期税。

默认答案是"新项目选 Loki"——大多数团队的正确答案就是单 Loki。单 ES 就够的场景反而更少：日志本身就是检索产品（业务搜索框、安全平台），或已有成熟 ES 运维能力且量不大。

两个都要的正当理由只有两个：真有一小撮日志需要全文索引与合规取证；真有跨字段复杂聚合的分析需求。其余的"都上"，本质是选型不敢担责——**混合是"两类查询都存在"的答案，不是"我不知道选哪个"的答案**。

## 现在就能做的三件事

第一，量你的索引膨胀率：拿 `_cat/indices` 的 pri.store.size 除以当天原始日志量，超过 2 就该重读第一节了。

第二，查你离 Loki 流数上限多远：`/config` 看限制值，再看监控里活跃流数的增速——每次发布后跳一级台阶，就是有人在往标签里塞高变动值。

第三，把你最高频的 10 条日志查询拉出来数一数：几条带着 namespace/app/时间窗边界？10 条里 9 条带边界，你的全文索引就是在替那 1 条查询交税。
