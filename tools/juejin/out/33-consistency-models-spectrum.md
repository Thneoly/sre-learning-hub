# 线性一致和串行化不是一回事：一致性模型当合同看，四级谱系一次讲清

先看一段面试里天天上演的对话：

"你们系统什么一致性？"——"强一致，我们用 etcd。"
"那 Kafka 呢？"——"也算强一致吧，我们开了 acks=all。"

第一句只对了一半：etcd 默认读确实是线性一致，但一条参数就能把它降一档。第二句全错：**acks=all 买到的是持久性，不是读语义**。更根本的是，"整个系统什么一致性"这个问法本身就是陷阱——**落位是按操作粒度的**，同一个系统读一套、写一套。

这篇把一致性模型当合同讲清：四级谱系各自承诺什么；它和隔离级别（串行化）为什么是两个正交维度；CAP 的 C 到底指哪一个；etcd/Kafka/Redis 各落在哪格；最后给面试答法。

## 1. 一致性模型是合同：系统保证你观察不到什么

副本一多，"读到的值新不新"就没有唯一答案——同一个集群，读主库和读从库是两回事，不同客户端同一秒读也可能不同。

**一致性模型是系统与客户端的合同：保证你不会观察到哪些现象**。合同越强，代价越大。

运维的日常就两件事：把每张合同贴到正确的组件上；在有人投诉"数据不对"时判断，这是违约，还是你签的就是这种合同。"读到了旧数据"的工单，九成不是故障——是你签的合同本来就允许旧值【从业者判断】。

## 2. 四级阶梯：每往下一档，放开一类"允许读到的旧值"

先立一个锚：一致性不是"强弱"的形容词，是一份份具体到"读到什么算违约"的合同。

| 模型 | 一句话合同 | 读到什么才算违反 |
|---|---|---|
| 线性一致 | 操作看起来在"调用与应答之间的某一瞬间"原子生效，且尊重真实时间先后 | 写已应答成功后，任何客户端从任何副本读仍返回旧值（且无新写覆盖）——"写完读不到"即违约 |
| 顺序一致 | 存在全体认同的操作全序，不违背各客户端程序序；不尊重真实时间 | 找不到一个同时满足所有客户端程序序的全序。注意："实时上后开始的读看不到先完成的写"不违约 |
| 因果一致 | 有因果关系的操作所有人看到的顺序一致；并发写可以各有所见 | 读到比已知因果更旧的值：A 写完 x 告诉 B"我写完了"，B 去读却读不到 |
| 最终一致 | 停止写入后，经过有限时间所有副本收敛到同一值 | 读到旧值不算违约。违约是停写后永不收敛，或冲突修不平要人工裁决 |

线性一致和顺序一致的全部差别，只有一条：**实时序**。

```text
线性一致（必须尊重实时序）:
  C1 ──PUT x=1──► 应答 OK ──┐
                            │ 实时上，C2 的读在 C1 的写完成之后才开始
  C2 ───────────────GET x ──┴─► 必须返回 1

顺序一致（只认程序序，可无视实时序）:
  C1 ──PUT x=1──► 应答 OK     全序 = [C2 的 GET, C1 的 PUT] 是合法排列
  C2 ───────────────GET x ────► 允许返回旧值 0
```

线性一致的要求：写已应答、读在真实时间上晚于它开始，就必须读到新值。顺序一致只认"全体认同一个全序、不违背各客户端自己的程序序"——把 C2 的读排到 C1 的写前面是合法排列，返回旧值不违约。

最终一致是被误解最深的一级。它从不承诺"不读到旧值"，它承诺的是收敛：停写之后，有限时间内所有副本到达同一个值。拿"我读到了旧值"去指责最终一致系统，是把合同里写明的条款当事故——旧值是正常履约。

四级是包含式的：线性一致 ⊃ 顺序一致 ⊃ 因果一致 ⊃ 最终一致，上线自动满足下线的合同。每往下一档，就多放开一类"允许读到的旧值"；每往上一档，都要拿东西买：延迟（quorum 往返）、可用性（分区期间停写）、元数据（因果上下文，比如 MongoDB 因果一致会话要消息捎带会话令牌）。

所以别问"强一致好不好"，问"这一格的价格，这笔业务付不付得起"。

## 3. 线性一致和串行化：两根轴，正交

最常见的混淆，是把一致性模型和事务隔离级别当成同一根轴上的强弱。它们管的是两件不同的事：

- **一致性模型管"读操作能看到哪些写"**——对象是副本间的顺序
- **隔离级别管"多个事务交错执行时的现象"**——对象是并发事务

串行化是隔离级别的最强档：并发事务执行的结果，等价于某种一次一个事务的串行执行【从业者判断】。线性一致是一致性模型的最强档：单个操作尊重实时序。两个"最强档"可以同时要——既要单操作实时序、又要事务全序，即严格串行化【从业者判断】——但谁也不包含谁，它们根本不在一个维度上。

验证两个维度独立，不用搭系统，看 MySQL 就够：RC/RR 靠 MVCC 的 Read View 在单机上挡住不可重复读（RC 每条语句建视图、RR 首条快照读建视图），但这与主从复制后"读从库拿到旧值"是两个维度。

隔离级别哪怕开到 SERIALIZABLE，从库照样可能落后 30 秒——隔离级别治不了副本间的旧值，一致性模型也管不了事务交错。

还有个术语陷阱：etcd 的 `--consistency=s` 官方叫"串行读"，落位在顺序一致这一档，和数据库的串行化隔离没有关系。面试把这两个"串行"混用，是硬伤。

### CAP 的 C，是哪一个 C

**CAP 的 C 就是线性一致这一档**；ACID 的 C 是业务约束不被破坏。CAP 的 C、ACID 的 C、隔离级别的串行化——三个缩写、三个维度，混用一个就露怯。

分区发生时在 C 和 A 之间怎么选，两家的现场表现就是答案：

- 3 节点的 ZK 挂掉 2 台，直接停写——凑不齐过半提交，宁可不可用也要保住已提交数据；etcd 同款：3 成员挂 2，写被拒，但已提交数据大概率仍在，恢复任一成员即可救回
- Kafka 的 `unclean.leader.election.enable` 允许落后副本上位，用丢已提交数据换可用——往 A 侧倒的开关；etcd 没有等价物，Raft 的任期直接否决旧主复活

Kleppmann 专门写过一篇《Please Stop Calling Databases CP or AP》，反对给整个数据库贴 CP/AP 标签【第三方转引，Kleppmann 博客，2015】。理由和下一节一致：落位按操作、按参数，一个标签装不下一个系统。

## 4. etcd / Kafka / Redis：竖着看一家横跨全部档位

| 档位 | etcd | Kafka | Redis |
|---|---|---|---|
| 线性一致 | 默认读：ReadIndex 先与多数派确认 | 不提供；acks=all 买的是持久性 | 仅主库近似成立；failover 瞬间不保 |
| 顺序一致 | `--consistency=s`：读本成员 KV | 单分区 FIFO；跨分区无全局序 | 读主库成立；读从库即掉出本档 |
| 因果一致 | 不单设档位：线性读自动覆盖 | 同 key 恒进同分区；跨 key 跨分区无 | 钉住同一主库期间成立；主从切换即可能违反 |
| 最终一致 | 串行读打到落后成员的实际体验 | 消费 lag 与 ISR 收缩全程可观测 | 默认档：异步复制，offset 差即"最终"的实测长度 |

竖着看：**同一家系统横跨全部档位，档位由"读路径 + 参数"当场决定**。所以"etcd 什么一致性"永远要追问一句："哪个操作、什么参数？"——这句话能接住面试官的所有追问。

etcd 默认读为什么也要过多数派：ReadIndex 要先确认"我还是当前任期的 leader"，否则可能把已卸任旧主上的旧值当最新值返回——问题不是读得慢，是朝代已经换了。

代价是每读多一轮往返，`--consistency=s` 省的就是这一轮，价格是可能读到旧值。有 K8s 集群可以亲手给这个差价计时：

```bash
# 在 K8s master 节点上跑：50 次线性读 vs 50 次串行读
kubectl -n kube-system exec etcd-"$(hostname)" -- bash -c '
  export ETCDCTL_API=3
  C="--cacert=/etc/kubernetes/pki/etcd/ca.crt --cert=/etc/kubernetes/pki/etcd/server.crt \
     --key=/etc/kubernetes/pki/etcd/server.key --endpoints=https://127.0.0.1:2379"
  etcdctl $C put /sre-lab/consistency v1 >/dev/null
  echo "--- 50 次线性读(默认, ReadIndex 多一轮多数派确认):"
  time (i=0; while [ $i -lt 50 ]; do etcdctl $C get /sre-lab/consistency --consistency=l >/dev/null; i=$((i+1)); done)
  echo "--- 50 次串行读(读本成员 KV, 无多数派确认):"
  time (i=0; while [ $i -lt 50 ]; do etcdctl $C get /sre-lab/consistency --consistency=s >/dev/null; i=$((i+1)); done)
  etcdctl $C del /sre-lab/consistency >/dev/null
'
# 预期：串行读的 real 更短。单成员集群差距小（ReadIndex 只需问自己）；
# 3 成员集群上，差价才是"每读省一次多数派往返"的全价
```

Kafka 为什么停在顺序一致：单分区只有一个 leader，读写都走它，分区内 FIFO，"全体认同一个全序"有了；但它不承诺跨分区实时序，也没有"写应答后任何读必见"的全局仲裁。

HW 补的是可见性边界：消费者只能读 ISR 集体确认过的位置，防止读到"随 leader 切换被截断而消失"的消息——这是把脏读挡在合同外，跟线性一致是两件事。

再看深一层：`acks=all + min.insync.replicas=2` 是运维手工拼出来的"准 quorum"，副本间没有共识协议，leader 由外部 controller/KRaft 指定——所以才容得下 unclean leader election 这种主动破坏已提交语义的开关。

Redis 为什么停在最终一致：主从异步复制，failover 会丢旧主最后一段写入。主库上单线程执行序即实时序，读主库"近似线性"；读从库立刻掉到最终一致；哨兵切换瞬间还可能"时间倒流"——新主比旧主落后，第二次读比第一次还旧。

`WAIT 1 3000` 也改不了档位：它改善的是这一条写的持久性/RPO，与一致性档位正交，不是线性读。

横着看：同一档位三家机理完全不同——多数派确认、单 leader 全序、单线程执行序——排查手段也不同：etcd 查 Raft 与 ReadIndex，Kafka 查 ISR 与 lag，Redis 查主从 offset 差。

最后一条通用规律，值一次选型评审：**强一致都不是白来的**。etcd 每次写要多数派 fsync，ZK 每次写要过半 ACK——这正是两家不适合当业务存储、只放元数据的根源。

## 5. 会话保证：业务投诉的重灾区

比"全体观察者"更贴近业务的，是同一个客户端自己视角的合同——因果一致性的实用子集：

| 保证 | 内容 | 违反时的业务表现 |
|---|---|---|
| 读己之写 | 我写完的值，我立刻能读到 | "改完头像，一刷新还是旧的" |
| 单调读 | 重复读同一数据，不会越读越旧 | 刷新一次，内容"倒回去"了 |
| 单调写 | 我的多次写不被乱序观察到 | 消息顺序颠倒 |

三条都有便宜的拿法：Redis 要读己之写，写后读都打主库；ZK 要读己之写，读前先 `sync()`；Kafka 单消费者按 offset 前进，天然单调读——lag 是收敛距离，不是违约。

最容易被打破的场景也各有其主：单调读死于 Redis 客户端从一个从库切到更落后的从库或新主；单调写的标准解是 Kafka 同 key 恒进同一分区。

有人会反问：全打主库不就全保住了？——从库存在的理由就是扛读压，全打主库等于放弃水平扩展；务实的折中是只把写后短窗口内的关键读钉在主库【从业者判断】。

一句话：**多数业务投诉要的不是线性一致，是读己之写**——这是价格最便宜的"够用档"。

## 6. "最终一致的最终是多久"：把玄学变成指标

"最终"由三个变量决定：服务端反熵/复制追赶周期、故障切换的接管窗口、客户端缓存 TTL。总窗口约等于三者之和，且只有停写之后才单调收敛到零。三个变量都有对应的监控数：MySQL 的 `Seconds_Behind_Source`（注意它只测重放）、Redis 主从 offset 差、Kafka 的 follower lag、DNS 的 TTL。

两条工程结论，各值一次事故复盘：

- **收敛窗口 ≈ 故障时的丢失窗口**。从库落后 30 秒，主库坏掉就丢 30 秒——最终一致的"旧"，在故障瞬间变成 RPO
- **客户端缓存把窗口二次放大**。DNS 的 TTL、SDK 的槽表缓存、Informer 的本地缓存，都在"副本已收敛"之后还在发旧值——排查时两层都要算

有 docker 就能实测"最终"到底多长：

```bash
# 起一主一从
docker network create cons-lab-net 2>/dev/null
docker run -d --name cons-master --network cons-lab-net redis:7.2
docker run -d --name cons-replica --network cons-lab-net redis:7.2 --replicaof cons-master 6379
sleep 3
docker exec cons-replica redis-cli INFO replication | grep -E "^role|master_link_status"
# 预期：role:slave / master_link_status:up

# 突发写入 5 万个 key，立刻看两端的 offset 差（当下收敛距离）
printf 'SET bk:%d v\r\n' $(seq 1 50000) | docker exec -i cons-master redis-cli --pipe | tail -1
docker exec cons-master redis-cli INFO replication | grep -E "master_repl_offset|slave0="
docker exec cons-replica redis-cli INFO replication | grep slave_repl_offset
# 预期：主从 offset 存在差值；几秒后重跑上面两条，差值归零——这就是"最终"的实测长度

# WAIT：把这一次写的"最终"变成可等待的确认
docker exec cons-master sh -c 'redis-cli SET sync:test v; redis-cli WAIT 1 3000'
# 预期：OK 之后 (integer) 1（确认的副本数）；从库断开则返回 0，写不阻塞但退回最终一致

# 用完清理
docker rm -f cons-master cons-replica && docker network rm cons-lab-net
```

## 7. 面试怎么答：三句话不露怯

被问"线性一致和串行化什么区别"，一句话背下来：线性一致是一致性模型的最强档，对单个操作承诺实时序；串行化是隔离级别的最强档，对并发事务承诺交错结果等价于串行执行。**两根轴，正交。**

被问"CAP 的 C"：线性一致。别答 ACID 的 C，也别答"数据不丢"。

被问"你们系统什么一致性"，别答"强一致"，按操作粒度答："etcd 默认线性读，`--consistency=s` 降到顺序一致；Kafka 单分区顺序一致，acks=all 买的是持久性；Redis 主从最终一致，读主库近似线性。"答到这个粒度，追问到哪层都接得住。

被问"最终一致的最终是多久"：**最终一致不是不保证一致，是不保证何时一致**；上界由反熵周期、写压和客户端缓存 TTL 决定，三个数都可以监控和调优。真正不可接受的场景（扣款、扣库存）不是换更强的模型，而是把关键操作改成对账加幂等重试。
