# 没人恢复过的备份不算备份：RTO/RPO 与一次像样的恢复演练

备份任务跑了两年，每晚 02:00 都是绿色的"成功"。直到误删库那天要恢复，才发现快照早就损坏、恢复脚本依赖的镜像源已下线、备份账号权限过期——而所谓每日备份，实际只保留了 3 天。

日志全绿，数据没了。

这是灾备领域反复上演的标准剧本，病根只有一句：**没人恢复过的备份不算备份**。这篇文章讲四件事：RTO/RPO 怎么定才不是拍脑袋、备份验证悖论与恢复演练怎么设计、同城双活和异地灾备的成本账怎么算，最后给 etcd 和 MySQL 两条实测过的恢复路径，命令照抄能跑。

## 一、RTO 与 RPO：两个数字，两条花钱的线

```text
    最后一次有效数据 ──── 故障发生 ──── 恢复完成
           │◄────  RPO  ────►│◄────  RTO  ────►│
            丢多少数据         中断多久
```

- **RTO**（Recovery Time Objective）：服务中断多久能恢复的上限。考验**恢复路径**——预案、自动化、人。
- **RPO**（Recovery Point Objective）：恢复后允许丢掉的最近数据量。考验**数据链路**——异步复制延迟 30s，RPO 就是约 30s；每日一次备份，RPO 上限就是 24h。

这两个数字由架构里的哪个环节决定，一张表说清：

| 目标 | 决定因素 | 典型手段 |
|---|---|---|
| RPO = 0 | 同步复制，写双份成功才返回 | 同城同步复制、共享存储 |
| RPO = 秒~分 | 异步复制 | 半同步 MySQL、跨 Region 异步 |
| RPO = 小时 | 定时备份 | etcd snapshot、数据库全备+增备 |
| RTO = 分钟 | 自动切换 | 双活 + 健康检查自动摘除 |
| RTO = 小时 | 半自动 | 热备 + 人工决策切换 |
| RTO = 天 | 冷备 | 备份 + 采购机器 + 手工恢复 |

看清这张表的形状：**RPO 越小，钱花在数据链路上；RTO 越小，钱花在架构与演练上**。两条线完全独立。

举个例子，这是对账时最常踩的误区：把每日备份改成半同步复制，RPO 从 24h 压到秒级，但切换若靠人工决策，RTO 纹丝不动。反过来，把人工切换脚本化并演练达标，RTO 从 4h 压到 15 分钟，RPO 还是 24h。所以预算有限时先保 RPO——数据丢了补不回来，宕久了还能修。

最后一条纪律：这两个数字是**承诺，不是愿望**。承诺前必须能回答"凭什么"：备份几分钟一次？切换脚本演练过吗？答不上来的数字写进方案，就是给老板挖坑。

## 二、对账：把差距变成有优先级的账

RTO/RPO 不该由技术在会议室里拍出来，它是一张三方对账表：**业务方出容忍度，财务出损失估算，工程出成本**。每行一个系统，季度评审一次：

```text
系统        业务要求           技术现状              差距动作
交易核心    RTO 15m / RPO 0    双活 + 同步复制        达标，持续演练
用户画像    RTO 4h  / RPO 1h   异步复制(延迟~10s)     达标
报表数仓    RTO 3d  / RPO 24h  每日备份到对象存储      达标
新业务 X    RTO 30m / RPO 0    单机房 + 每日备份      不达标：先上异步复制压
                                                     RPO(约2周)；RTO先承诺
                                                     4h 再压(约2月)
```

对账的价值是把差距变成**有优先级的账**：RPO 从 24h 压到 10s 是两个数量级的投入，值不值，由业务损失估算回答，不由技术热情回答。

三个容易漏的口径。第一，RPO 还有另一半——**能回到多久以前**。每日全备保留 7 天，误操作在第 8 天才发现（误删类"慢故障"的发现周期常以周计），备份就形同虚设。改法：近线保留 7~30 天，归档层保 90 天到 1 年，把"最远可恢复点"也写进对账表。

第二，别把灾备目标和 SLO 混为一谈。SLO 和错误预算管**常态故障**——单机宕机、慢查询、发布事故，频率高到能统计定价；灾备管**黑天鹅**——机房失联、勒索软件加密全量数据，频率低到进不了预算体系，但单次足以危及业务存续。两套体系共用观测设施，目标、演练方式、决策链完全不同。

第三，最常见的翻车：承诺 RPO 秒级，出事实际丢了 20 分钟——因为把"异步复制"和"备份"混为一谈了。**RPO 由复制链路决定，不由备份频率决定**，对账表里这两条线必须分开写。

## 三、备份验证悖论：链路四步，最后一步没人管

备份链路四步：**产生 → 传输/存储 → 保留/清理 → 恢复**。前三步分别被任务监控、上传告警、保留策略兜着，唯独最后一步——灾难时你唯一要执行的那步——通常从没验证过。

所以有那句行话：**备份是幻觉，恢复才是能力**。没人恢复过的备份不算备份，它只是一堆"看起来可读"的文件。

验证恢复能力不是一条命令的事，是四连问：

1. **找得到**：目录、账号、密钥此刻可访问吗？
2. **读得出**：校验和、元数据正常吗？
3. **恢复得了**：真的能把服务拉起来吗？
4. **恢复得对**：恢复出来的数据经得起校验吗？

预埋一个反驳，评论区一定会有："我们验证过，每天对备份跑 `snapshot status`，TOTAL KEYS 正常。"这只做到了四连的第二条——文件读得出。它证明不了你能在一个新集群里把这份数据拉起来，更证明不了恢复出来的数据是对的。从"读得出"到"恢复得了"，中间隔着的正是一次像样的演练。

## 四、恢复演练四要素：环境、时间预算、度量、复盘

**环境——恢复到哪。**在生产就地恢复等于二次伤害：原集群正病着，再往它身上恢复一次。正确姿势是恢复到隔离环境，验证通过再切流量。权限是隐形炸弹：演练账号的权限必须和生产恢复的真实路径一致，平时拿高权限演练，灾难时照样卡在权限上——这种演练只生产假安全感。

**时间预算——定期，写进日历。**演练不是兴致来了做一次，是节奏：

| 演练对象 | 频率 | 方式 | 通过标准 |
|---|---|---|---|
| etcd 快照 | 每月 | 恢复到临时集群 | 集群启动且能 get 到关键对象 |
| 数据库 PITR | 每季度 | 恢复到隔离实例 | 恢复到指定位点，抽样校验一致 |
| 对象存储 | 每季度 | 跨账号/跨区副本拉回 | 清单对账 + 随机对象可读 |
| 配置/IaC 仓库 | 每月 | 从 git+state 重建 staging | 与生产拓扑 diff 为空 |
| 整机房切换 | 每年 1~2 次 | GameDay 全链路 | 实测 RTO/RPO 落在承诺内 |

**度量——三行结论。**每次演练的产出就三行：实测 RTO、实测 RPO、与承诺的差距。实测 RTO 是大多数团队从没测量过的数字，第一次测，做好被吓一跳的准备【从业者判断】。

**复盘——差距变行动项。**差距进复盘，带着 owner 和期限关掉。这套和混沌工程是同一方法论：稳态假设换成"RTO/RPO 承诺成立"，注入的故障换成"生产数据面整体消失"。一句话收尾：**没被演练过的灾备预案，是科幻小说**。

最后补一块系统之外的部分。灾难发生时先瘫的往往是组织不是机器，预案之外还要回答四个问题：

- **谁宣布灾难状态**：预先授权，如"核心服务全失联 30 分钟，值班负责人可直接宣布切异地"，而不是层层请示——每级请示都在消耗 RTO。
- **通讯树怎么走**：对内谁在 15 分钟内被呼叫、备用渠道是什么（办公 IM 本身可能就在故障域里）。
- **依赖清单**：上游支付通道、短信、DNS，以及"依赖的依赖"——机房断电时你的服务器没事，但运维通道全在同一个机房。
- **人员冗余**：每个关键恢复步骤至少两人会做，恢复脚本不依赖某个人的笔记本。

这份预案的维护节奏和演练绑定：架构大改后更新清单，演练后修订决策表。

## 五、成本账：同城双活 vs 异地灾备

先上层级菜单，RTO/RPO 和代价一目了然：

| 层级 | RTO | RPO | 相对成本 | 适用 |
|---|---|---|---|---|
| 冷备 | 天级 | 24h+ | 低 | 边缘系统、可重算数据 |
| 热备 | 小时级 | 分钟级 | 1.5~2 倍 | 大多数生产系统 |
| 同城双活 | 分钟级 | 0 | 2 倍 | 核心交易链路 |
| 异地灾备 | 小时级 | 分钟级 | 高 | 抗城市/Region 级灾难 |
| 异地多活 | 分钟级 | 秒级 | 最高 | 超大规模、合规要求 |

定位一句话：**同城双活抗机房级故障，异地灾备抗城市/Region 级故障**。前者是性价比最高的容灾——同城 AZ 间延迟只有 1~3ms，同步复制扛得住；后者贵一个数量级，只保核心业务。

经典拓扑是"两地三中心"：

```text
       城市 A（生产）                        城市 B
中心1 ◄──1~3ms 同步──► 中心2                 中心3（standby）
 双活承载       RPO=0      双活承载 ──异步──► 备份 + 核心子集
                                            RPO=分钟级
A 城故障 → 流量自动全切中心2（分钟级）
A 城 + 中心2 同时失联 → 人工决策切中心3（小时级）
```

三个工程要点：

- **流量入口**要能按健康度全局切换（GTM/智能 DNS），否则"双活"只是两套各自等死的系统。
- **数据分层**：核心库同步复制、普通库异步、可重算数据只做备份。全量同步的成本没人付得起。
- **切换决策**：双活是同步复制（RPO=0），自动切换不丢数据，可以交给机器；异地是异步复制，切过去就是**主动放弃未复制完的数据**——丢多少、值不值，是业务权衡不是技术判断，必须人拍板。自动化只负责把决策所需数据（延迟、损失量、剩余选项）在一分钟内摆到人面前。

双活的暗面是脑裂：心跳断了但两边都活着，两边同时升主，双写之后冲突无法自动消解。防线三条——仲裁（第三方站点/quorum，etcd 的多数派就是这么设计的）、fencing（接管前先隔离对端）、写路径单点化（多数"双活"实际是双跑单写）。

顺带提醒选了冷备的团队：异地机房设备常年不通电，切换那天才发现硬件、镜像、证书悄悄全过期了。冷备也要月度巡检——机器可开机、镜像可拉、证书未过期，这三条本身就是巡检清单。

再预埋一个反驳："那一步到位上异地多活不就完了？"看表：成本最高、复杂度极高，而且 RPO 也只是秒级不是 0——跨 Region 同步复制的延迟和可用性代价巨大。答案永远是数据分层：只有核心交易表配得上同步，其余按对账表降级。

## 六、两条真实恢复路径

### etcd：20 分钟，从快照到集群读回旧数据

K8s 控制面的数据全在 etcd，CKA 把 backup/restore 列为明确考点。备份是在线操作，TLS 参数一个不能少（任何时候显式带 `ETCDCTL_API=3` 都不会错）：

```bash
# [master] 快照：全套 TLS，证书路径是 kubeadm 默认值
sudo mkdir -p /opt/etcd-backup
sudo ETCDCTL_API=3 etcdctl \
  --endpoints=https://127.0.0.1:2379 \
  --cacert=/etc/kubernetes/pki/etcd/ca.crt \
  --cert=/etc/kubernetes/pki/etcd/server.crt \
  --key=/etc/kubernetes/pki/etcd/server.key \
  snapshot save /opt/etcd-backup/snap.db

# [master] 验证"读得出"：status 只需要文件本身，不用连 etcd
sudo ETCDCTL_API=3 etcdctl snapshot status /opt/etcd-backup/snap.db -w table
# 输出列：HASH / REVISION / TOTAL KEYS / TOTAL SIZE
# TOTAL KEYS 为 0、或体积只有几 KB——这份快照救不了你，重新备
```

恢复是另一副面孔：**离线文件操作，TLS 参数一个都不需要**——它只从快照文件重建一个数据目录，全程不碰任何 etcd 进程。但先划一条红线：**下面的流程只适用于单 master 集群（stacked 单节点 etcd）**。3 master 集群绝不能每个成员各自 restore——restore 会以全新集群身份重建数据目录，各自 restore 会得到三份 cluster ID 各不相同的数据目录，成员间无法组成一个集群，控制面当场分裂。多 control plane 的正确做法是：只在一个成员上 restore（并显式指定 `--name`、`--initial-cluster`、`--initial-advertise-peer-urls` 等集群拓扑参数），其余成员清空数据后用 `etcdctl member add` 重新加入，具体步骤以 etcd 官方 disaster recovery 文档为准。

```bash
# [master] 目标目录必须为空或不存在
sudo rm -rf /var/lib/etcd-drill
sudo ETCDCTL_API=3 etcdctl \
  --data-dir=/var/lib/etcd-drill \
  snapshot restore /opt/etcd-backup/snap.db
```

然后改 `/etc/kubernetes/manifests/etcd.yaml`，**两处**一起改：command 里的 `--data-dir`，和 hostPath（连同 mountPath），都指向 `/var/lib/etcd-drill`。只改一处是最经典的翻车——表面看"恢复没生效"，实际 etcd 读的还是旧目录。kubelet 监视 manifests 目录，保存即自动重建 Pod：

```bash
# [master] 验证：对象回来了，写入也正常
kubectl get nodes
kubectl create cm restore-check --from-literal=t=$(date +%s)
kubectl get cm restore-check -o yaml | grep t:
```

全程约 20 分钟。想让这次演练带上"通过标准"，前面加两步：快照前先造一个对象，快照后删掉它，恢复后看它复活——

```bash
# [master] 1) 造一个"只能靠快照找回"的对象
kubectl create ns etcd-drill
kubectl -n etcd-drill create configmap precious --from-literal=data=before-snapshot

# [master] 2) 执行上面的快照命令，然后"误删"
kubectl delete ns etcd-drill --wait=false
kubectl get ns etcd-drill
# Error from server (NotFound): namespaces "etcd-drill" not found

# [master] 3) 走完恢复三步后验证：它回来了，演练才算通过
kubectl -n etcd-drill get cm precious
# NAME       DATA   AGE
# precious   1      3m

# [master] 4) 收尾：恢复实验现场——不做这步，集群从此一直跑在演练目录上
sudo vim /etc/kubernetes/manifests/etcd.yaml   # 把 --data-dir 和 hostPath 改回 /var/lib/etcd
# 等 kubelet 自动重建 etcd Pod、apiserver 恢复正常后，再清理：
kubectl -n etcd-drill delete cm precious
kubectl delete ns etcd-drill
sudo rm -rf /var/lib/etcd-drill
```

收尾这一步是演练的一部分，不是可选项：**删 `/var/lib/etcd-drill` 之前必须先把 manifest 指回 `/var/lib/etcd` 并确认 etcd Pod 已在新目录上重建**，否则删掉的就是 etcd 正在使用的数据目录，运行中的集群当场损坏。忘了收尾还有个隐性炸弹：下次重做演练时，第一条 `sudo rm -rf /var/lib/etcd-drill` 会把在用的数据目录直接删掉。

模型一句话：**恢复不修集群，只是把数据目录从快照重建出来，再让 etcd 挪过去读**——apiserver 全程是被牵着走的那个。

泼盆冷水：etcd 快照只救**声明**，不救**数据**。Deployment、Service 这些 API 对象回来了，但 PVC 里的文件、数据库的数据、ConfigMap 之外的配置，快照统统救不了。灾备是分层的，每层要有自己的恢复手段和演练。

### MySQL：全备 + binlog，把 RPO 压到最后一笔事务

数据库的账更好算：只恢复备份文件，最多回到备份那一刻，每日全备的 RPO 就是 24h。要压到"任意时间点"，靠物理备份 + binlog 的 PITR 组合——这时决定 RPO 的其实是 binlog 保留策略。

```bash
# 全备（XtraBackup，文件级物理备份，恢复快）
xtrabackup --backup --target-dir=/data/backup/full \
  --user=root --password=root123 -H127.0.0.1 -P3306

# 恢复前必须 prepare，输出最后应是 "completed OK!"
xtrabackup --prepare --target-dir=/data/backup/full

cat /data/backup/full/xtrabackup_binlog_info
# 形如：./binlog.000003  1570   ← 这就是恢复的起点位点
```

prepare 完的目录挂给一个新实例拉起——隔离环境，别覆盖原库，这正是演练要素里的"环境"：

```bash
docker run -d --name mysql-restored \
  -v /data/backup/full:/var/lib/mysql \
  -e MYSQL_ROOT_PASSWORD=root123 -p 3307:3306 mysql:8.0
# docker logs mysql-restored 2>&1 | grep -i "ready for connections"
```

备份只能回到"昨晚 2 点"，误删发生在"上午 10 点"，中间的差距由 binlog 重放补齐，stop-position 停在误删语句前一瞬：

```bash
# 位点与文件名按你的 binlog 实际情况替换
mysqlbinlog --start-position=1570 --stop-position=52311 \
  /var/lib/mysql/binlog.000003 | mysql -h127.0.0.1 -P3307 -uroot -proot123
```

只要 binlog 齐全，RPO 可以压到"最后一笔事务"。但"齐全"两个字是要花钱的：binlog 保留时间短于备份周期，PITR 就会差一截——保留时长要大于备份间隔加排障窗口（8.0 用 `binlog_expire_logs_seconds` 控制，默认 30 天）。

顺手把第一节那张表里"RPO=秒~分"的机制也落地：纯异步复制下，主库提交后不等从库，主库宕机时未发送的 binlog 事务就永久丢了；半同步让主库提交后**至少等一个从库确认收到 binlog** 才向客户端返回成功。这就是"异步复制→秒级 RPO"背后的真实含义——它保护的是复制链路，不是备份文件，两条线别再混了。

而这条路径的 RTO——prepare 多久、拉起多久、重放多久——同样只有计时演练过才算数。

## 结尾：现在就能做的三件事

1. 找到你团队最近一次 etcd 备份文件，跑一遍 `etcdctl snapshot status /opt/etcd-backup/snap.db -w table`（路径换成你的），看 TOTAL KEYS 是否非零、且与集群规模同数量级（新装集群几千、长期运行的生产集群上万）。文件大小和 db 规模匹配即可——快照大小约等于 etcd db size，与对象数和使用时长强相关：全新 kubeadm 集群几 MB 完全正常，别拿"几十 MB"当验收线把自己健康的备份判死；长期运行的生产集群才是几十 MB 起。TOTAL KEYS 为 0 的"成功备份"，今晚就该重做。
2. 生产集群只做纸面推演：挑个低峰时段，把恢复依赖链、账号权限、备份位点三查一遍并记录。完整走一遍并计时，去演练集群或隔离环境做——你会得到自己系统的实测 RTO，这个数字，大多数团队从没测过。
3. 填一张三行对账表：对象、实测 RPO、实测 RTO、承诺、差距。空白就是差距，差距就该有动作和期限。

三件事加起来不到一小时，换来的是下一次故障会上你敢说出口的那句"我们测过"。
